# Sweet Home 3D — UI layout, workflow, modes, shortcuts, first-run (competitor research for CasaPlazAI)

Job folder: `09-09-ui-workflow-shortcuts` · Target: Sweet Home 3D 7.5 (eTeks / Space Mushrooms, GPL) — desktop app, "Sweet Home 3D JS Online" web build, and mobile app.
Evidence tags: **OBSERVED** = seen directly in a page/DOM/script/asset I captured (evidence file given). **DOCUMENTED** = stated in vendor docs/manual (URL given). **INFERRED** = my reasoning from the two above, not directly stated by the vendor.

---

## 1. Summary

- **Four panes, one window, one toolbar (DOCUMENTED/OBSERVED).** The desktop app is a single window split into four resizable panes — furniture catalog, home furniture list, home plan, home 3D view — with one toolbar across the top and one menu bar. The **Online** build deliberately drops the menu bar and the file buttons, keeping the same four panes, one toolbar and contextual menus instead.
- **Everything is a mode, not a tool dialog (OBSERVED).** Plan editing is a state machine: `SELECT`, `PAN`, `CREATE_WALLS`, `CREATE_ROOMS`, `CREATE_POLYLINES`, `CREATE_DIMENSION_LINES`, `CREATE_LABELS` are mutually exclusive toolbar modes; creation tools are disabled when the selected level isn't viewable.
- **Undo/redo is first-class and typed (OBSERVED).** A `javax.swing.undo.UndoManager` (limit 100) labels each edit, and the toolbar/tooltip text becomes action-specific: "Undo Paste", "Undo Move", "Can't Undo". Copy/paste uses an **internal clipboard only** (never the system clipboard), with extra "Paste style" and "Paste to group" verbs.
- **Escape / Enter / double-click are the universal edit contract (OBSERVED + DOCUMENTED).** Escape (or double-click at the last point) ends any creation series, Enter switches to keyboard entry of exact dimensions, arrow keys nudge the selection 1 unit (Shift = 10), Alt/Ctrl-drag duplicates, Alt (Win)/Cmd (macOS) temporarily bypasses the 15° wall-angle magnetism.
- **First run is a demo chooser, not a coach-mark tour (OBSERVED).** Online opens on a "Select a demo" table of 11 example homes; picking "Empty home" pops an `alert()` warning that nothing will be saved without registering. Tips exist but as dismissible per-tool messages ("Do not display this tip again") that the Online build stubs out entirely.

## 2. Findings

### 2.1 Layout and panes

- **F1 (DOCUMENTED).** "Each Sweet Home 3D window edits the interior design of a home and is divided in four resizable panes, with a tool bar at its top": 1 furniture catalog, 2 home furniture list, 3 home plan (grid + rulers), 4 home 3D view. Tab / Shift+Tab (or a click) moves focus between panes; the focused pane is marked by a coloured rectangle. — User guide, <https://www.sweethome3d.com/users-guide/>; extracted text `raw/userguide.txt`.
- **F2 (OBSERVED).** The Online DOM mirrors this exactly: `#home-pane` > `#application-menu-toolbar`, `#home-pane-toolbar`, then `#catalog-furniture-pane` (`#furniture-catalog` + `#catalog-furniture-splitter` + `#furniture-view`), `#furniture-plan-splitter`, and `#plan-3D-view-pane` (`#home-plan` with `#level-selector` + `#home-plan.canvas`, `#plan-3D-view-splitter`, `<canvas id="home-3D-view">`). — `evidence/studio_dom.html` (356 932 B), `evidence/scenario3.json` (`"ok": true`).
- **F3 (OBSERVED).** Pane geometry is plain CSS, not a JS layout manager: catalog pane `width: 300px; top: calc(52px + 30px)`; plan/3D pane `left: 304px; width: calc(100% - 304px)`; furniture list = bottom 30 % of the catalog pane (`top: calc(70% + 4px)`); plan and 3D stacked 50/50 (`calc(50% - 2px)` each); splitters are 4 px strips with `cursor: ew-resize` / `ns-resize`. — `raw/js/sweethome3djs.css`; styles inline in `evidence/studio_dom.html`.
- **F4 (OBSERVED).** Responsive breakpoints replace re-flow, not re-implementation: `(orientation: portrait)` catalog 160 px; `(min-width: 1024px)` catalog 225 px; `(max-width: 743px), (max-height: 511px)` hide splitters and `#furniture-view`; portrait or aspect ≤ 5/4 turns the catalog into a ~78 px strip at the bottom and moves the toolbar to the bottom; `(max-width: 800px)` hides `.toolbar-optional` buttons (Cut, Pan, Zoom in/out); `@media print` hides toolbars, catalog and splitters. — `raw/js/sweethome3djs.css`.
- **F5 (OBSERVED).** Splitter positions and per-pane viewports are persisted **inside the home document**, not only in global settings: bundle constants `HomePane.MAIN_PANE_DIVIDER_LOCATION_VISUAL_PROPERTY` (`com.eteks.sweethome3d.SweetHome3D.MainPaneDividerLocation`), `CATALOG_PANE_DIVIDER_LOCATION`, `PLAN_PANE_DIVIDER_LOCATION`, plus `PLAN_VIEWPORT_X/Y` and `FURNITURE_VIEWPORT_Y`. — `raw/js/sweethome3d.min.js`.
- **F6 (OBSERVED).** Desktop can detach the 3D view into its own window (`DETACHED_VIEW_VISUAL_PROPERTY = ".detachedView"` plus divider/x/y/width/height properties; actions `DETACH_3D_VIEW` / `ATTACH_3D_VIEW`, menu labels "Display in separate window"/"Display in main window"). The Online build stubs `detachView`/`attachView` to no-ops. — `raw/js/sweethome3d.min.js`; `raw/localization.json`.
- **F7 (OBSERVED).** In the Online build the ribbon-style toolbar is assembled by `HomePane.prototype.createToolBar`, which only adds New / Open / Save / Save As buttons when the `#home-pane-toolbar` element carries the classes `new-home`, `open`, `save`, `save-as`. The online page has none, so those buttons never render; `#application-menu-toolbar` holds a single hamburger button `#toolbar-button-SHOW_APPLICATION_MENU`. — `raw/js/sweethome3d.min.js`; `evidence/studio_dom.html`.

### 2.3 Plan canvas: grid, zoom, rulers, magnetism

- **F14 (OBSERVED).** The grid is **adaptive, not fixed**: metric steps `[1,2,5,10,20,50,100,200,500,1000,2000,5000,10000]` cm and imperial `[2.54,5.08,7.62,15.24, 12·2.54, …]`, chosen so a cell is ≥ 10 px; major lines `[100,200,500,1000,2000,5000,10000]` cm (metric) drawn thicker when ≥ 50 px apart; grid colour derived from canvas background/foreground luminance; painted only in PAINT mode when `preferences.isGridVisible()`. — `raw/js/sweethome3d.min.js`.
- **F15 (OBSERVED).** Zoom changes a model→screen scale factor by ×1.5 per click, clamped to `[0.01, 10]`, and re-centres on the selection; scale is persisted in the document as `PlanController.SCALE_VISUAL_PROPERTY`. — `raw/js/sweethome3d.min.js`.
- **F16 (OBSERVED).** Length units define `getStepSize() = 0.5` (unit-dependent: mm/cm/m/inch/foot variants), `getMagnetizedLength(value, 0.1)`, and min/max lengths 0.1–100000. — `raw/js/sweethome3d.min.js` (`LengthUnit.*`).
- **F17 (DOCUMENTED + OBSERVED).** Magnetism: wall floor angles snap to multiples of 15° by default; the snap can be bypassed at any time by holding Alt (Windows), Cmd (macOS) or Shift+Alt (Linux) while drawing. — `raw/userguide.txt` l. 215–227; bypass bindings confirmed in the bundle (`TOGGLE_MAGNETISM_ON/OFF` on Alt for Windows, Meta for macOS). Toolbar button toggles magnetised snapping globally and swaps icon/action via a property-change listener.
- **F18 (OBSERVED).** Drag feedback is a cursor tooltip, not a dialog: `PlanController.wallLengthToolTipFeedback = "Length: %s"`, `wallAngleToolTipFeedback = "Angle: %d°"`, `wallThicknessToolTipFeedback`, `widthResizeToolTipFeedback`, `depthResizeToolTipFeedback`, `heightResizeToolTipFeedback`, `elevationToolTipFeedback`, `rotationToolTipFeedback`, `diameterToolTipFeedback`, `wallArcRadius/ArcExtent`, `roomSideLength/roomSideAngle/roomDiagonal`, `cameraElevationToolTipFeedback`, `cameraYaw/PitchRotationToolTipFeedback`, `observerHeightToolTipFeedback`, `lightPowerToolTipFeedback`, `polylineSegmentLength/Angle`. — `raw/localization.json`.

### 2.4 Undo/redo and the clipboard

- **F19 (OBSERVED).** One `javax.swing.undo.UndoManager` per home controller, default `limit = 100` edits, `trimForLimit()` discards half the edits when exceeded; `saveUndoLevel()` tracks the save point so the document can report a dirty state. — `raw/js/sweethome3d.min.js`, `raw/js/swingundo.min.js`.
- **F20 (OBSERVED, live).** Undo/redo labels are action-typed and surface in the toolbar/tooltip. Verified live in one session: after a furniture paste the Undo button read **"Undo Paste"**, after undo **"Redo Paste"**, after redo again **"Undo Paste"**; in the keyboard run, an arrow-key nudge produced **"Undo Move"** and a Delete produced **"Undo"**. Empty stacks read **"Can't Undo" / "Can't Redo"** with `[disabled]`. — `evidence/scenario5.json` + `evidence/s5_*_a11y.txt`; `evidence/s6_kbd_arrow_a11y.txt`, `evidence/s6_kbd_delete_a11y.txt`. Bundle holds 73 `undo*Name` presentation keys (`undoCreateWallsName`, `undoAddLevel`, `undoModifyFurnitureName`, `undoPasteStyleName`, `undoSplitWallName`, `undoWallArcExtentName`, `undoImportBackgroundImageName`, `undoHideBackgroundImageName`, …) under `HomeController.*`.
- **F21 (OBSERVED).** Copy/paste is an **internal clipboard**: `HomePane.prototype.createClipboardAction` — COPY stores `Home.duplicate(home.getSelectedItems())` and sets `clipboardEmpty=false`; CUT = copy + `controller.cut(...)`; PASTE = `controller.paste(Home.duplicate(clipboard))`. Additional verbs: `PASTE_TO_GROUP` (paste into the group selected in the list) and `PASTE_STYLE` (apply the copied item's style to the selection; both sets must be the same type). — `raw/js/sweethome3d.min.js`; shortcut sheet (Ctrl+Shift+V / Ctrl+Alt+V, DOCUMENTED).
- **F22 (DOCUMENTED).** Copy has context-dependent payloads: Copy in the **furniture list** copies a text of the selected furniture, and Copy in the **plan** copies an image of the selection. The list can also be exported to CSV (`HomeView.ActionType.EXPORT_TO_CSV = 93`). — Shortcuts sheet `research/raw/SweetHome3DShortcuts.txt` (© 2022 eTeks, v7.0) and history notes `raw/history.txt` ("Added the ability to copy selected furniture to the clipboard at CSV format, when furniture list has focus").
- **F23 (DOCUMENTED).** Menus enable/disable in edit groups: Delete, Undo, Redo, Copy, Cut, Paste and Modify are enabled *between* the creation of two series of walls or two dimensions (i.e. creation states suspend cross-object edits). — `raw/history.txt`.
- **F24 (OBSERVED).** Plan-level right-click menu order observed live: Undo / Redo / Delete selection / Cut / Copy / Paste / Paste style / Select all / Select all at all levels / Modify furniture… / Group / Ungroup / Reset elevation / Modify compass… / Modify walls… / Join walls / Reverse walls direction / Split wall / Modify rooms… / Modify polylines… / Modify dimension lines… / Modify texts… / Modify text style ▸ / Import background image… / Modify/Hide/Show/Delete background image / Add level / Add level at same elevation / Modify level / Delete level. Furniture-list context menu = Cut/Copy/Paste/Paste to group/Paste style, Modify furniture…, Group/Ungroup, Align/Distribute, Reset elevation, Sort, Display-property; catalog = Add furniture / Add to group; 3D view = View from top / View from observer / Modify observer… / Store point of view / Go to point of view ▸ / Delete points of view / Display all levels / Display selected level / Modify 3D attributes. — `evidence/s4_context_menu_a11y.txt`, `evidence/s5_ctx_plan_a11y.txt`, `evidence/s5_select_row_a11y.txt`, `raw/js/sweethome3d.min.js`.

### 2.7 Background image tracing

- **F34 (DOCUMENTED).** Wizard flow: `Plan > Import background image…` → *Choose image* (BMP/JPEG/GIF/PNG, or drag-and-drop into the frame) → *Continue* → **define scale** by dragging the two ends of a coloured line to match a known length and typing "Length of drawn line" in real life at the current unit (Shift while dragging forces the line horizontal/vertical) → *Continue* → **define origin** (click the point that is plan (0,0), or type X/Y) → *Finish*. The image then renders behind the plan grid; `Plan > Modify background image…` re-opens the same wizard to fix scale/position; the guide explicitly warns that the entered length is the **real** length, not the on-screen length. — `raw/userguide.txt` ("Importing home blueprint"); `raw/faq.txt`; `raw/localization.json` (`BackgroundImageWizardStepsPanel.*`: `imageChoiceLabel.text`, `scaleLabel.text`, `originLabel.text`, `scaleDistanceLabel.text = "Length of drawn line (%s):"`, `xOriginLabel/yOriginLabel`).
- **F35 (OBSERVED).** The wizard is a 3-step controller `BackgroundImageWizardController` with `Step = {CHOICE: 0, SCALE: 1, ORIGIN: 2}` and step states `imageChoiceStepState`, `imageScaleStepState`, `imageOriginStepState`. Importing and modifying are separate undoable edits (`undoImportBackgroundImageName`, `undoModifyBackgroundImageName`); hide/show/delete are their own actions (124–128 in `HomeView.ActionType`); background images can be per-level (`level.setBackgroundImage`) as well as per-home. Oversized images trigger a modal offer: "The image you selected is %dx%d pixels… Should it be reduced to %dx%d pixels?" with *Reduce size* / *Keep unchanged* / *Cancel*. — `raw/js/sweethome3d.min.js`; `raw/localization.json` (`BackgroundImageWizardStepsPanel.reduceImageSize.*`).
- **F36 (OBSERVED/DOCUMENTED).** Walls are drawn semi-transparent while a background image is active (so the blueprint stays visible), and there is a 3D-side option `BACKGROUND_IMAGE_VISIBLE_ON_GROUND_3D`. — `raw/history.txt`; `raw/js/sweethome3d.min.js`.

### 2.10 Cross-cutting inferences (all tagged INFERRED)

- **F51 (INFERRED).** The four-pane split layout is a *deliberate* invariant across desktop, online and tablet rather than an accident of the Swing toolkit: the same DOM ids and CSS classes (`#catalog-furniture-pane`, `#plan-3D-view-pane`, `.pane-splitter`) are used in the web build (F2, F3), and the mobile blog describes tablets as getting "the desktop-like 4-pane arrangement" (F49). The phone layouts are adaptive re-flows of the same four regions, not a different information architecture.
- **F52 (INFERRED).** Splitter positions living inside the home document (F5) rather than in a user profile implies the product treats "how I was looking at this home" as part of the home, which is why a shared `.sh3d` reopens with the same panes. For a web app with localStorage autosave (CasaPlazAI), copying that choice would make the saved state self-describing.
- **F53 (INFERRED).** The typed undo/redo labels (F20) are generated from localized `undo*Name` templates rather than from stored action objects, so adding a new undoable operation costs one resource string rather than a new UI code path. That is the cheap way for CasaPlazAI to get a labelled history.
- **F54 (INFERRED).** The `isPropertyEditable("<KEY>") && false` pattern (F32) is the mechanism that lets one preference dialog serve three products; the online dialog is not a separate design, it is the desktop dialog with controls switched off. Any CasaPlazAI preference surface should be keyed so a hosted/limited deployment can subtract controls without forking markup.
- **F55 (INFERRED).** Because accelerators are read from the localization bundle and `HomePane.keydownListener` resolves them before the component `inputMap` (F27, F29), the reference app gets OS-correct bindings (Cmd vs Ctrl) and localizable shortcuts from one table. This is also the most likely reason my Ctrl-modifier press on the furniture list did not behave as the plan-level keys did (F30): the accelerator path and the component input-map path are two different routes, and I only exercised the list half of the first route.
- **F56 (INFERRED).** The online build's stubs (`showActionTipMessage` returning `false`, `help = function(){}`, `detachView`/`attachView` no-ops, alert-based messages — F13, F45) mean the web edition deliberately ships *without* the desktop's learning aids and secondary surfaces. Sweet Home 3D Online therefore competes on "the same editor, simpler" rather than "the same editor, plus guidance" — a gap CasaPlazAI can take with dismissible in-app tips (F33) at low cost.

## 3. Ideas for CasaPlazAI (ranked by value / effort)

Ranking = value for a single-workspace web floorplanner, then effort. Each item names the finding it comes from.

| # | Idea | Why (finding) | Value | Effort |
|---|------|----------------|-------|--------|
| 1 | **Persist pane geometry and per-pane viewport state inside the document** (splitter %, plan zoom/pan, list scroll + sort + visible columns), alongside localStorage autosave. | F5, F40 — this is what makes a four-pane workspace feel like *your* workspace on reload. | High | Low |
| 2 | **Type every undo entry and show it in the UI** ("Undo Move wall", "Undo Delete door"), with "Can't undo" as a disabled state. | F19, F20 — cheap, and it turns an opaque stack into a self-teaching history. | High | Low |
| 3 | **Make Escape/Enter/double-click a single, documented contract**: Escape or double-click ends a wall/room/measure series; Enter switches that same series to typed-dimension entry; a second finger / second click cancels. | F25, F29, F34, F49 — one rule covers every creation tool, keyboard or touch. | High | Low |
| 4 | **Temporary magnetism bypass on a modifier key** (Alt/Cmd while drawing), on top of a persistent toggle, plus a snap-step of 0.5 m already in CasaPlazAI. | F17 — users need precision without leaving the mode or opening preferences. | High | Low |
| 5 | **Replace the fixed 1 m/0.5 m grid with adaptive steps** (0.1/0.2/0.5/1/2/5 m chosen so a cell is ≥ ~10 px), with a thicker major line and a luminance-safe grid colour; keep 0.5 m snapping as the *snap* step, not the *drawing* step. | F14, F16 — a fixed grid becomes useless when zoomed out over a whole flat. | High | Low–Med |
| 6 | **Live dimension readout near the cursor while dragging** ("Length: 3.42 m", "Angle: 90°", "Width: 1.20 m") instead of a dialog or a static label. | F18 — the single most-used feedback channel in the reference app. | High | Med |
| 7 | **Background-image tracing as a 3-step wizard** (Choose → Scale by typing the *real* length of a draggable line → Set origin), plus re-open to modify, and hide/show/delete as separate undoable actions; downscale-overly-large-images prompt. | F34, F35 — this is the reference app's on-ramp for renovating an existing home, and the "real length, not screen length" check is the exact field that catches users out. | High | Med–High |
| 8 | **Keep the furniture list, but make it earn its space**: sortable Name/Width/Depth/Height columns, a per-row visibility checkbox, column + sort choices saved with the document, and a CSV export as the escape hatch. | F39, F40, F22 — CasaPlazAI's palette is small, but a sortable list is where users audit what is in the room. | Med–High | Med |
| 9 | **Mode-based toolbar that greys out illegal actions** (e.g. creation tools while a locked/non-editable level is selected; grouping with <2 items), instead of hiding buttons. | F11, F23 — discoverability: the button's existence teaches the capability. | Med | Med |
| 10 | **First-run demo chooser instead of an empty canvas**, with one tiny "starter flat", and an explicit "this is only stored in your browser" notice plus a `beforeunload` guard. | F42, F43 — a blank 2D grid is the main first-run drop-off; the reference app's answer is 11 prebuilt homes plus an alert. | Med–High | Med |
| 11 | **One-shot "Paste style"** (copy a wall's/room's colour + thickness + height, apply to a same-type selection) and a "paste into group" variant; do **not** promise system-clipboard paste across tabs. | F21, F22 — the reference clipboard is internal; matching that expectation avoids a whole class of bug reports. | Med | Med |
| 12 | **Ship a keyboard-shortcut surface that is localizable and discoverable**: route accelerators through a resource table (so `Cmd` vs `Ctrl` is data, not code), put the combination in the tooltip, and publish one shortcut sheet. | F27, F29 — the reference app derives accelerators from its localization bundle, which is why macOS gets `cmd` variants for free. | Med | Low–Med |
| 13 | **Responsive rule set rather than a second UI**: stack/hide panes at documented breakpoints (<800 px hides secondary toolbar actions; portrait moves the catalog into a bottom strip and the toolbar to the bottom). | F3, F4, F49 — cheap CSS mirrors of the reference behaviour, and the mobile blog confirms the same breakpoints are the intended contract. | Med | Low–Med |
| 14 | **Dismissible per-tool tips with a global "Reset the display of tips"**, rather than a modal tour. | F33, F42 — the Online build stubs tips out entirely, which is a *missed* opportunity; desktop-style dismissible tips fit a single-workspace web app well. | Med | Low |
| 15 | **Levels as tabs with lower-level objects ghosted**, added as a later tab next to the existing rectangle/polygon tools. | F18 (guide), F40, F50 — multi-floor is out of scope today, but the tab metaphor + ghosting is the pattern to copy when it arrives. | Med (later) | High |
| 16 | **Play the reference app's restraint on desktop-only features**: no detached 3D window, no photo/video renderer, no plug-in API, no print preview in v1. | F6, F44, F45 — the reference app itself ships the web edition without them; each is a large surface for near-zero floorplanner value. | N/A (negative rec.) | — |

## 4. Unknowns / what I could not verify

- **Why the clipboard accelerators didn't fire in the Online build.** In my headless run `Ctrl+C/Ctrl+V/Ctrl+Z/Ctrl+Y` with the furniture list focused left the undo stack untouched, while plan-level `ArrowRight`/`Delete` worked (F30). It may be a focus/selection precondition, a modifier-key mapping difference in the GWT event layer, or the accelerator path simply not being wired in the browser build. I could not isolate the cause, and I could not test the native app (no desktop installer allowed in this job).
- **Slider/keyboard behaviour of the splitters**, and whether pane sizes respond to keyboard (the shortcut sheet documents only Tab/Shift+Tab focus transfer, not resize keys).
- **3D-view mode details.** I confirmed the two actions (`VIEW_FROM_TOP`, `VIEW_FROM_OBSERVER`), their toolbar toggles and the 3D input map, but not the on-screen affordance set (the visitor indicator widgets described in the guide) beyond the guide text, since the 3D canvas is WebGL and not represented in the accessibility tree.
- **Whether the Online context menus are complete.** I read the context menus from bundle code and from the accessibility tree; two menu items ("Modify observer…", "Modify 3D attributes") were not opened live, so their exact online labels/order rest on bundle strings (`HomePane.MODIFY_OBSERVER.Name`, `MODIFY_3D_ATTRIBUTES.Name`).
- **Mobile app UI** is from the vendor's blog post only — the app is paid and I did not install or run it, so gesture timings, breakpoints and menu contents there are vendor claims, not my observations.
- **Version drift.** The shortcut sheet I have is labelled "Version 7.0 © 2022 eTeks" while the product page advertises 7.5 (last update May 2025). Newer combos may exist that are not in that sheet; the bundle I analysed is the current online build, so shortcut keys sourced *only* from the sheet should be treated as of-7.0.
- **Non-English behaviour and locale-specific accelerators** were not exercised (the app ran with `userLanguage = "en"`).
- **Earlier scenario evidence is incomplete.** `evidence/scenario1.json` timed out (exit 124) and `evidence/scenario2.json` failed at its pick step (`strict mode violation: locator('#demo-choice img.demo-image') resolved to 9 elements`); only `scenario3`–`scenario6` are clean runs. Screenshots in `screenshots/` could not be visually inspected (the model has no image input in this session), so anything that is only in a screenshot is not asserted here.
- **Two delegated research subagents were still running when the budget expired** (research on shortcuts/menus/preferences and on the online/mobile versions). Their raw fetches are under `research/raw/` (including `SweetHome3DShortcuts.pdf/.txt`, `localization.json`, mobile blog pages, `actiontypes.txt`); their drafted `research/*.md` files did not exist at write time, so every claim in this report is sourced to `raw/`, `evidence/` or `research/raw/` directly.
