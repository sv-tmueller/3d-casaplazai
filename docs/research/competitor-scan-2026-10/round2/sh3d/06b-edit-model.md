## 1. Summary (5 bullets)

- **Undo is a controller-layer concern, not a model concern.** `Home.java` (the data model) contains **zero** references to undo; the entire undo machinery lives in `com.eteks.sweethome3d.viewcontroller`. `HomeController` owns one `javax.swing.undo.UndoableEditSupport` (subclassed to drop insignificant compound edits) plus one `UndoManager`, and passes that **same** `undoSupport` instance into every sub-controller (Plan, Furniture, HomeFurniture, Room, Wall, Level, Label, DimensionLine, Polyline, 3D). Result: one global undo stack across all tools. **OBSERVED** (`evidence/src/model_Home.java` has 0 undo hits; `viewcontroller_HomeController.java:199–210, 429–455`).
- **There are 89 distinct `*UndoableEdit` type names, 76 of them concrete subclasses of a tiny `LocalizedUndoableEdit extends javax.swing.undo.AbstractUndoableEdit`** that only overrides `getPresentationName()` to read a resource-bundle key. Edits are **command/memento hybrids**: they either call back into the controller with captured old+new state (e.g. `WallsCreationUndoableEdit` stores `JoinedWall[]` + old/new selection + `basePlanLocked`), or hold a per-object memento (`ModifiedPieceOfFurniture.reset()` restores every field). **OBSERVED** (89 class names extracted from `sweethome3d.min.js`; `evidence/src/viewcontroller_LocalizedUndoableEdit.java`; `evidence/src/viewcontroller_HomeFurnitureController.java:1798, 2135`).
- **The model is a plain observable graph.** `Home` holds seven typed `CollectionChangeSupport<T>` (furniture, levels, walls, rooms, polylines, dimensionLines, labels) + one `PropertyChangeSupport`; every `HomeObject` carries a stable UUID `id`, a user property bag, and a **lazily created** `PropertyChangeSupport`. Views never poll and never diff: each view registers a collection listener for ADD/DELETE and, on ADD, attaches a per-item property listener bound to a specific `Property.*` enum name. **OBSERVED** (`evidence/src/model_CollectionChangeSupport.java`, `model_HomeObject.java`, `viewcontroller_PlanController.java:2440–2596`, `swing_PlanComponent.java:760–1110`).
- **2D, 3D and the furniture list are three independent subscribers to the same events.** `PlanComponent` maps a property name to `revalidate()` vs `repaint()` and invalidates named caches; `HomeComponent3D` keeps a `Map<Selectable,Object3DBranch>` and calls `objectBranch.update()`; `FurnitureTable`'s tree-table model fires `fireTableRowsInserted/Deleted` or a full re-filter/re-sort. 3D updates are **coalesced** into a deferred batch (`EventQueue.invokeLater` in Java, `setTimeout(…,0)` in the JS build) so a burst of property events produces one geometry pass. **OBSERVED** (`swing_HomeComponent3D.java:3689–3714`, `swing_FurnitureTable.java:660–770, 2655–2700`, `evidence/js_HomeComponent3D_updateObjects.js.txt`).
- **Edit granularity and action routing are both state-machine driven.** `PlanController` is a `ControllerState` machine whose `Mode` (`SELECTION/PANNING/WALL_CREATION/ROOM_CREATION/…`) is a deliberately *open* set of named constants, not a closed `enum`; `HomeController.focusedViewChanged(View)` re-enables a ~140-member `ActionType` enum based on which view has focus (catalog / furniture list / plan / 3D). A drag mutates the model live but posts **exactly one** UndoableEdit on pointer release (`postPieceOfFurnitureMove`, `postWallResize`, `postRoomResize`). Multi-step actions are wrapped with `undoSupport.beginUpdate()/endUpdate()`. `HomeController` tracks `saveUndoLevel` (edits since last save) and a separate `notUndoableModifications` flag for changes outside the stack (stored cameras, photo/video settings); the stack is *not* cleared on save but is **hard-capped at 100 edits** by the Swing `UndoManager` default. **OBSERVED** (`viewcontroller_PlanController.java:290–360, 7037, 7204, 7308, 11322, 14518`; `viewcontroller_HomeController.java:1111–1133, 1458–1491, 1496–1505, 693–732`).

Two edit styles coexist — **OBSERVED**:

1. **Controller-callback edits.** The edit stores only the *deltas/descriptors* and calls a private `doXxx()` method back on the controller for redo/undo. Example (`evidence/src/viewcontroller_PlanController.java:6987–7035`, described in my own words):

   `ItemsMovingUndoableEdit` holds `Selectable[] items`, `Selectable[] oldSelection`, `boolean allLevelsSelection`, `float dx, dy`;
   `undo()` → `controller.doMoveAndShowItems(items, oldSelection, -dx, -dy, allLevelsSelection)`;
   `redo()` → `controller.doMoveAndShowItems(items, items, +dx, +dy, allLevelsSelection)`.

   The `doXxx` helper is the same code the live interaction calls, so apply and invert cannot drift apart — an important robustness property.

2. **Memento edits.** `ModifiedPieceOfFurniture` snapshots every field of a piece in its constructor and `reset()` writes them all back (`name`, `nameVisible`, `description`, user property map, price/VAT/currency, x/y/elevation/angle/roll/pitch, movable, w/d/h, `widthInPlan/depthInPlan/heightInPlan`, model transformations, color, texture, `modelMaterials`, shininess, visible, modelMirrored). `ModifiedDoorOrWindow` extends it with the wall-embedding ratios (`boundToWall`, `wallThickness`, `wallDistance`, `wallWidth`, `wallLeft`, `wallHeight`, `wallTop`); `ModifiedFurnitureGroup` extends it for groups. `FurnitureModificationUndoableEdit` aggregates an **array** of these mementos plus the old/new selection and the scalar field-level changes from the inspector form. **OBSERVED** (`viewcontroller_HomeFurnitureController.java:1798–2135+`).

3. **Edits are deliberately *not* anonymous inner classes.** `FurnitureModificationUndoableEdit`'s own comment says: *"This class isn't anonymous to avoid being bound to controller and its view."* In Java an anonymous inner class implicitly captures the enclosing controller (and through it the view), so a long undo history would pin the whole UI graph in memory. SH3D instead makes each edit a `private static class` holding only the model references it needs (`home`, the mementos, the scalars) and the `UserPreferences` needed for localization. **OBSERVED** (`viewcontroller_HomeFurnitureController.java:1794–1798`). **INFERRED:** this is why the codebase has 76 separate static nested edit classes instead of dozens of one-off anonymous `AbstractUndoableEdit`s.

**INFERRED:** the memento style is chosen exactly where a single user gesture in a modal/inspector form may change many fields at once; the callback style is chosen where the underlying operation is a controller algorithm (join walls, split wall, distribute furniture) that is easier to re-run than to encode as data.

### 2.2 The undo stack, compound edits and save-point tracking

All in `HomeController` — **OBSERVED** (`evidence/src/viewcontroller_HomeController.java`):

- The support object is an anonymous subclass (lines 199–208) that overrides `protected void _postEdit(UndoableEdit edit)` and drops any `CompoundEdit` that `!isSignificant()`. This is how a compound edit that ended up empty/insignificant never reaches the stack.
- `this.undoManager = new javax.swing.undo.UndoManager(); this.undoSupport.addUndoableEditListener(this.undoManager);` (209–210) — the stock Swing `UndoManager` (itself an `UndoableEditListener` and a `CompoundEdit`).
- Sub-controllers receive the support via `getUndoableEditSupport()` (453–455) and every lazy sub-controller constructor takes it as an argument (Plan 432–433, Furniture 420–421, 3D 444–445), so there is exactly **one** stack per open home.
- **Compound edits** group several low-level posts into one logical step via `beginUpdate()` / `endUpdate()`:
  - `cut(items)` (1496–1505): `beginUpdate` → `planController.deleteItems(items)` → `postEdit(new LocalizedUndoableEdit(…, "undoCutName"))` → `endUpdate`. The extra edit exists only to override the compound's presentation name.
  - deletion (5729–5760): `ItemsDeletionStartUndoableEdit` … `ItemsDeletionEndUndoableEdit`, bracketed by begin/end.
  - item addition (6216–6229): `ItemsAdditionEndUndoableEdit`.
  - dropping onto a different level (1557–1587): `LevelModificationUndoableEdit` + the drop edit + rename, one compound.
- **Signalling the UI.** A listener added in `addUndoSupportListener()` (1111–1123) runs on every posted edit: enables `UNDO` (but only when `!planController.isModificationState()`), disables `REDO`, sets both menu labels from `getUndoPresentationName()`/`getRedoPresentationName()`, increments `saveUndoLevel`, and calls `home.setModified(true)`.
- **Save point as a counter, not a cleared stack.** `saveUndoLevel` counts undoable edits since the document was last saved; `undo()` decrements it and `redo()` increments it (1470, 1489); after either, `home.setModified(saveUndoLevel != 0 || notUndoableModifications)` (1471, 1490). A `Home.Property.MODIFIED` listener resets the counter to 0 when the home is marked unmodified (1124–1132). I did **not** find any `discardAllEdits()` call in the downloaded sources — the stack is kept, only the counter moves. **OBSERVED** (grep over `HomeController`, `PlanController`, `FurnitureController`, `RoomController`, `WallController`, `LevelController`, `LabelController`, `HomeController3D`: 0 hits) — but see Unknowns §4.
- **Non-undoable modifications** are tracked separately (693–732): listeners on `Home.Property.STORED_CAMERAS` and on `HomeEnvironment` properties (observer-camera elevation adjustment, video width/aspect/frame-rate/quality, camera path, ceiling light colour, photo quality/aspect/width/height) and on both cameras' `TIME`/`LENS` set `notUndoableModifications = true` and `home.setModified(true)`. These change the document without an undo entry.
- **The stack is a from-scratch JS port of `javax.swing.undo` that the page loads as its own file.** The round-1 network graph lists `https://www.sweethome3d.com/libjs/swingundo.min.js?version=7.5.2`; I fetched it (16 792 bytes, HTTP 200) and it defines `javax.swing.undo.{UndoableEdit, AbstractUndoableEdit, CompoundEdit, UndoManager, UndoableEditSupport, CannotUndoException, CannotRedoException, StateEdit, StateEditable}` and `javax.swing.event.UndoableEditEvent`. This is strong evidence the browser build runs the *same* undo algorithms as the desktop Swing app rather than a web-only reinvention. **OBSERVED** (`evidence/swingundo.min.js`).
- **`UndoManager` has a hard default cap of 100 edits, and the app never changes it.** The port initialises `this.limit = 100`, implements `setLimit`/`getLimit`/`trimForLimit` (trimming oldest edits when the limit is exceeded, adjusting `indexOfNextAdd`), but grepping the whole application bundle for `setLimit`/`getLimit`/`trimForLimit` yields **0** occurrences. So CasaPlazAI-style unbounded growth is *not* what SH3D does: **the undo history is bounded to 100 edits**. **OBSERVED**.
- **`discardAllEdits()` is implemented but never called.** The port's `UndoManager.discardAllEdits` walks `this.edits`, calls `die()` on each, resets `edits = []` and `indexOfNextAdd = 0`; the application bundle contains **0** occurrences of the name. Combined with the previous point this resolves the round-2 question left open by Unknown §2: SH3D never clears the stack on save — it only trims it to the newest 100 edits. **OBSERVED**.
- **Undo/redo are the textbook Swing walk.** `editToBeUndone()` scans backwards from `indexOfNextAdd` for the first `isSignificant()` edit; `editToBeRedone()` scans forwards; `undoTo(edit)` calls `edit.undo()` repeatedly, `redoTo(edit)` calls `edit.redo()`; `CompoundEdit.isSignificant()` returns true if **any** contained edit is significant — which is exactly why `HomeController._postEdit`'s filter (`drop CompoundEdit that !isSignificant()`) correctly discards empty batches. **OBSERVED** (`evidence/swingundo.min.js`).
- **Plug-in contract (DOCUMENTED).** The official developer's guide states the `Plugin` class "gives you access to an `UndoableEditSupport` instance through its `getUndoableEditSupport` method. As soon as you modify a home or its objects (furniture, walls…) in the `execute` method of a `PluginAction` instance, you should also post an `UndoableEdit` object to the undoable edit support returned by `getUndoableEditSupport` method, otherwise users won't be able to undo/redo correctly the changes you made." — i.e. undo correctness is a **documented responsibility of every mutator**, not something the model infers. **DOCUMENTED** (`docs_html_plugin.html`).

### 2.3 `LocalizedUndoableEdit` — the one shared base (49 lines)

**OBSERVED** (`evidence/src/viewcontroller_LocalizedUndoableEdit.java`): it extends `javax.swing.undo.AbstractUndoableEdit` and holds `(UserPreferences preferences, Class<? extends Controller> controllerClass, String presentationNameKey)`. Everything it adds is:

`getPresentationName() → preferences.getLocalizedString(controllerClass, presentationNameKey)`

So an edit's user-visible label is derived from *controller class + key*, existing translations are reused, and no edit class ever hard-codes English. `AbstractUndoableEdit` supplies the default `undo()`/`redo()`/`die()`/`isSignificant()` behaviour, meaning an edit that only needs to say "something happened" (like the compound rename edit) can be a bare instance. **INFERRED** (behaviour of the stock Swing class + the observed usages).

### 2.4 Property-change listener architecture

**The model is a pure observable graph; the controllers/views do all reacting.** Three tiers — **OBSERVED**:

1. **`HomeObject`** (`evidence/src/model_HomeObject.java`) is the base of everything selectable: a **stable `id`** (`createId(prefix)` = `prefix-` + `UUID.randomUUID()`, `@since 6.4`; older files get one on deserialisation via `readObjectNoData()`), a **user property bag** (`Map<String,Object> properties`, values restricted to `String` or `Content`), and a **lazily created** `PropertyChangeSupport` that is set back to `null` when its listener count reaches 0. `duplicate()` clones and re-issues an id with the same prefix; `clone()` keeps the id and drops the listener support.
2. **Collections on `Home`** (`evidence/src/model_Home.java:79–113, 436–444`): seven `CollectionChangeSupport<T>` — furniture, levels, walls, rooms, polylines, dimensionLines, labels — plus one `PropertyChangeSupport` for scalar home properties (`MODIFIED`, `SELECTED_LEVEL`, `ALL_LEVELS_SELECTION`, `CAMERA`, `STORED_CAMERAS`, `BACKGROUND_IMAGE`, `FURNITURE_SORTED_PROPERTY`, …). `CollectionChangeSupport.fireCollectionChanged(item, index, type)` (88 lines) **copies the listener array before dispatch** so "a listener can modify safely listeners list"; `CollectionEvent.Type` is `ADD | DELETE` and carries the optional insertion index.
3. **Per-object enums as event names.** Each model class exposes a `Property` enum whose `name()` is the event name — e.g. `Wall.Property.{X_START,Y_START,X_END,Y_END,WALL_AT_START,WALL_AT_END,THICKNESS,ARC_EXTENT,LEVEL,HEIGHT,HEIGHT_AT_END,LEFT_SIDE_BASEBOARD,RIGHT_SIDE_BASEBOARD}`, `HomePieceOfFurniture.Property.{X,Y,WIDTH,DEPTH,HEIGHT,WIDTH_IN_PLAN,DEPTH_IN_PLAN,HEIGHT_IN_PLAN,ANGLE,ROLL,PITCH,ELEVATION,LEVEL,VISIBLE,MODEL,MODEL_MIRRORED,MODEL_ROTATION,COLOR,TEXTURE,PLAN_ICON,ICON,SHININESS,MODEL_MATERIALS}`, `HomeDoorOrWindow.Property.{WALL_THICKNESS,WALL_DISTANCE,WALL_WIDTH,WALL_LEFT,WALL_CUT_OUT_ON_BOTH_SIDES,CUT_OUT_SHAPE}`, `Level.Property.{VISIBLE,VIEWABLE,ELEVATION,ELEVATION_INDEX,BACKGROUND_IMAGE,FLOOR_THICKNESS,HEIGHT}`. Views `switch` on these exact strings.

**The wiring idiom repeats verbatim in every view** — **OBSERVED** in `PlanComponent`, `HomeComponent3D`, `FurnitureTable` and `PlanController`:

```
for each existing item:            item.addPropertyChangeListener(changeListener)
home.addXxxListener(collectionListener)   // on ADD: attach per-item listener
                                          // on DELETE: detach it
```

`PlanController` demonstrates the "typed listener per role" refinement (`viewcontroller_PlanController.java:2440–2596`): a `selectionListener` (makes selection visible, auto-selects the level of the selected items), a `wallChangeListener` (invalidates geometry caches; **unselects a wall that became unreachable at the selected level**), a `furnitureChangeListener` (drops a cached plan-side table), and a `furnitureSizeChangeListener` (see §2.6). `HomeComponent3D` declares an equally long typed list (`cameraChangeListener`, `backgroundChangeListener`, `groundChangeListener`, `wallsAlphaListener`, `drawingModeListener`, `level/wall/furniture/room/polyline/dimensionLine/label` collection + change listeners) — **OBSERVED** (`swing_HomeComponent3D.java:219–254`).

### 2.5 How 2D, 3D and the furniture list are kept in sync

There is **no central synchroniser and no diffing**: the single source of truth is the `Home` object graph, and each view subscribes to the events it cares about and updates its own derived representation.

**2D plan — `PlanComponent`** (7093 lines) — **OBSERVED** (`evidence/src/swing_PlanComponent.java:760–1110`):
- On a furniture property change it branches on the property name: `HEIGHT_IN_PLAN` → invalidate `sortedLevelFurniture`; geometry/appearance (`PLAN_ICON`,`COLOR`,`TEXTURE`,`MODEL_MATERIALS`,`SHININESS`) → drop the cached top-view icon and `repaint()`; `ELEVATION`/`LEVEL`/`HEIGHT_IN_PLAN` → `repaint()`; door/window wall-ratio fields → `revalidate()` if the door's cut-out cache held it; default `else` → `revalidate()`.
- On wall changes it invalidates `wallAreasCache`, `otherLevelsWallAreaCache(s)`, `doorOrWindowWallThicknessAreasCache` and `revalidate()`s (or just `repaint()`s for height/level, which don't move plan geometry).
- On collection changes it sets `sortedLevelFurniture = null` and `revalidate()`s.
- It also listens to `Home.Property.CAMERA`, the observer camera, the compass, `SELECTION` (`repaint()`), `BACKGROUND_IMAGE`, and `SELECTED_LEVEL`.
- **Deferred icon recomputation:** while a *modification* gesture is in progress (`PlanController.isModificationState()`), invalidated furniture top-view icons are accumulated in `invalidFurnitureTopViewIcons`; a temporary listener on `PlanController.Property.MODIFICATION_STATE` recomputes them all and `repaint()`s as soon as the gesture ends. This is a deliberate quality/perf trade — do not spend icon-render time during a drag.

**3D scene — `HomeComponent3D`** (3918 lines) — **OBSERVED** (`evidence/src/swing_HomeComponent3D.java`):
- Builds `Map<Selectable, Object3DBranch> homeObjects` where `Object3DBranchFactory.createObject3D(home, item, …)` dispatches by type: `HomePieceOfFurniture→HomePieceOfFurniture3D`, `Wall→Wall3D`, `Room→Room3D`, `Polyline→Polyline3D`, `DimensionLine→DimensionLine3D`, `Label→Label3D`. `Object3DBranch.update()` is abstract; each subclass re-derives its geometry from current model values.
- Event handling is **batching**: `updateObjects(Collection<Selectable>)` accumulates into `HashSet homeObjectsToUpdate` and, on the first call of a burst, schedules `javax.swing.SwingUtilities.invokeLater` (Java) / `setTimeout(…,0)` (JS) which iterates the set, calls `objectBranch.update()`, checks the object wasn't deleted meanwhile, then nulls the set. It also clears the printed-image cache and the approximate-bounds/home-height caches.
- The JavaScript build shows the identical algorithm (`evidence/js_HomeComponent3D_updateObjects.js.txt`): `updateObjects` pushes into `homeObjectsToUpdate` unless null, else copies, schedules `setTimeout`, and later iterates calling `d.object3D.update()`; `updateObjectsAndFurnitureGroups` additionally recurses into `HomeFurnitureGroup` children.
- Rich cross-object invalidation: a wall change also `updateObjects(home.getRooms())` (ceilings may change), refreshes the ground when a wall is below elevation 0, recomputes light scope, and nudges the camera when in orthographic projection. A level-visibility change walks **all** home objects and updates those at that level (`isAtLevel`) — 3D rooms depend on rooms at other levels too. A level elevation/index change updates all objects and the ground; a floor-thickness change updates walls+rooms; a level height change updates rooms.
- Selection changes drive `updateObjectsAndFurnitureGroups(oldSelection ∪ newSelection)` — selection is a rendering input (outlines), not just UI state.

**Furniture list — `FurnitureTable`** (3100 lines) — **OBSERVED** (`evidence/src/swing_FurnitureTable.java:660–770, 2636–2700, 2790–2815`):
- A `FurnitureTreeTableModel extends AbstractTableModel implements TreeModel` maintains `filteredAndSortedFurniture`.
- On `CollectionEvent.ADD` it either `filterAndSortFurniture()` (when groups are expanded, the home holds non-viewable furniture, or no index is known) **or** computes the insertion index and fires fine-grained `fireTableRowsInserted(i, i)` + `fireTreeModelChanged()`. `DELETE` is symmetrical with `fireTableRowsDeleted` and also clears the group from `expandedGroups`.
- On **any** property change of a piece it re-runs `filterAndSortFurniture()` and `updateTableSelectedFurniture(home)` — because a property change can alter both sort order and filter membership — then `storeExpandedRows(...)`.
- Sort changes (`Home.Property.FURNITURE_SORTED_PROPERTY` / `FURNITURE_DESCENDING_SORTED`) use the same path. Level add/delete attaches/detaches listeners and updates.
- Selection is bidirectional via `home.addSelectionListener(homeSelectionListener)` (`addSelectionListeners`, lines 193/276) — selecting in the plan selects the row and vice versa.

**The setter contract is uniform: mutate, invalidate own caches, fire only on real change.** `Wall.setXStart` is representative — `if (xStart != this.xStart) { save old; assign; clearPointsCache(); arcCircleCenterCache = null; firePropertyChange(Property.X_START.name(), oldXStart, xStart); }`. **OBSERVED** (round-1 capture, `docs_src/Wall.java:145–153`). Two consequences matter for CasaPlazAI: (a) a `no-op` write never wakes the views, and (b) each setter explicitly names the derived caches it invalidates, i.e. **cache invalidation is co-located with mutation rather than centralised**. The event payload also carries both old and new values, which is what lets listeners like `HomeComponent3D`'s clone-and-revert-a-door trick work at all.

**How the three stay consistent — INFERRED from the evidence:** consistency is guaranteed by (a) every mutation going through a setter that fires a named `PropertyChangeEvent`, (b) each view binding that name to the minimal recompute, and (c) caches being explicitly invalidated by the same events. The risk this design accepts is that a view must remember every relevant property name; the benefit is that no view pays for another's changes. The batching layer (`homeObjectsToUpdate`) and the modification-state deferral are the perf valves.

### 2.6 Subtle synchronisation mechanisms worth naming

**View → model feedback (not just model → view).** In `PlanController` the `furnitureSizeChangeListener` reacts to `WIDTH`/`DEPTH`/`HEIGHT`/`MODEL`/`MODEL_MIRRORED`/`MODEL_ROTATION`/`ROLL`/`PITCH` by asking the **2D view** for the new plan footprint and writing it back into the model:

```
float[] size = getView().getPieceOfFurnitureSizeInPlan(piece);
if (size != null) { piece.setWidthInPlan(size[0]); piece.setDepthInPlan(size[1]); piece.setHeightInPlan(size[2]); }
else if (property is WIDTH) { scale widthInPlan/depthInPlan/heightInPlan proportionally }
```

**OBSERVED** (`viewcontroller_PlanController.java:2514–2540`). This is exactly the "cache the rotated plan AABB on the piece" idea the round-1 report derived from the XML format (`widthInPlan`/`depthInPlan`/`heightInPlan`); here we see it is **maintained incrementally by a listener**, with the 2D renderer as the authority on rotated footprint. The `else` branch is a defensive fallback for when the view cannot answer.

**Derived state computed by a listener (level visibility cascade).** `HomeController3D.addModelListeners` installs a `SELECTED_LEVEL` / `ALL_LEVELS_VISIBLE` listener that recomputes every level's `visible` flag top-down:

```
boolean visible = true;
for (i over levels) { levels[i].setVisible(visible); if (levels[i] == selectedLevel && !allLevelsVisible) visible = false; }
```

**OBSERVED** (`evidence/src/viewcontroller_HomeController3D.java:156–171`). Note these `setVisible` calls fire further events, which the 3D view consumes — a deliberate, bounded event cascade.


**Opening ↔ wall coupling is recomputed geometrically, not via stored foreign keys.** This is the runtime counterpart of the round-1 format finding that `doorOrWindow` has no `wallId`. **OBSERVED**:

- `Wall3D.updateWallSideGeometry` builds each wall side as a 2D `Area`, then subtracts the `Area` of **every furniture piece that `intersects` it** — obtained from a `List<HomePieceOfFurniture> intersectingDoorOrWindows` computed by geometric intersection, **not** by asking a door which wall it belongs to (`j3d_Wall3D.java:313, 320–350, 545–561`). Doors/windows are recognised by `piece instanceof HomeDoorOrWindow`, and `isParallelToWall(wall)` filters out pieces merely crossing the wall at an angle.
- The door's stored wall-embedding ratios are then used to *enlarge* the cut-out: if `isWallCutOutOnBothSides()` the code clones the piece and adds `4 * wall.getThickness()` to its plan depth so the hole opens on both faces; baseboards are handled by adding `2 * baseboard.getThickness()` (`j3d_Wall3D.java:325–338`). This is precisely what the `wallThickness`/`wallDistance`/`wallCutOutOnBothSides` XML attributes are for.
- When a door/window moves, `HomeComponent3D.furnitureChangeListener` must repair **both** the old and the new neighbourhood. For X/Y/WIDTH/DEPTH/ANGLE it clones the piece, **resets the changed property to its old value**, and calls `updateIntersectingWalls(oldPiece, piece)` (`swing_HomeComponent3D.java:3204–3233`). For pure wall-embedding attributes (`CUT_OUT_SHAPE`, `WALL_CUT_OUT_ON_BOTH_SIDES`, `WALL_WIDTH`, `WALL_LEFT`, `WALL_HEIGHT`, `WALL_TOP`) it calls `updateIntersectingWalls(piece)` once.
- `updateIntersectingWalls(...)` computes the approximate bounding rectangle of the moved pieces, then linear-scans **all** home walls for `wall.intersectsRectangle(...)`, collecting the hits and passing them to `updateObjects(...)`. It short-circuits if the pending update set already contains as many walls as the home has (`swing_HomeComponent3D.java:3729–3766`).
- A wall's own change additionally pulls in its **explicit joins**: `updateWall(wall)` builds `{wall, wall.getWallAtStart(), wall.getWallAtEnd()}` and updates all three (nulls skipped), so a corner stays watertight when one wall moves (`swing_HomeComponent3D.java:3767–3780`).

**INFERRED:** this is the price and the payoff of the SH3D opening model. The payoff is that any wall can host any opening with zero re-linking and `cutOutShape`-driven holes come almost free; the price is an O(pieces × walls) intersection pass on every opening move plus a clone-and-revert on every geometric drag — acceptable at house scale, but something a web planner with a 0.5 m grid and many walls should implement with a broad-phase index or, alternatively, keep CasaPlazAI's explicit `roomId`+`segmentIndex`+`tCenter` reference (cheap to resolve, and already in the frozen schema).

### 2.7 Edit granularity: the `PlanController` state machine

**OBSERVED** (`evidence/src/viewcontroller_PlanController.java`):
- `ControllerState` defines `enter()/exit()`, `getMode()`, `isModificationState()`, `isBasePlanModificationState()`, and gesture hooks `pressMouse(x,y,clickCount,shiftDown,duplicationActivated)`, `moveMouse(x,y)`, `releaseMouse(x,y)`, `setEditionActivated(boolean)`, `updateEditableProperty(EditableProperty, Object)`, `zoom(factor)`. A `ControllerStateDecorator` lets behaviour be layered.
- `setState(ControllerState)` (290–318) calls `oldState.exit()`, `state.enter()`, then fires `MODE`, `MODIFICATION_STATE` and `BASE_PLAN_MODIFICATION_STATE` property changes only when they actually changed. `Mode` and `MODIFICATION_STATE` are consumed by the whole UI (undo enablement, cursor, action lists).
- **The state machine is fine-grained: 48 `*State` classes, not one state per tool mode.** Extracted from the bundle, `PlanController.*` contains 48 nested `…State` types: seven near-identical creation states (`WallCreationState`/`WallDrawingState`, `RoomCreationState`/`RoomDrawingState`, `PolylineCreationState`/`PolylineDrawingState`, `DimensionLineCreationState`/`DimensionLineDrawingState`, `LabelCreationState`), a `SelectionState`/`SelectionMoveState`/`RectangleSelectionState`/`PanningState`/`DragAndDropState` family, and then a dedicated state **per direct-manipulation gesture**: `WallResizeState`, `WallArcExtentState`, `RoomResizeState`, `RoomAreaRotationState`, `RoomAreaOffsetState`, `RoomNameRotationState`, `RoomNameOffsetState`, `PieceOfFurnitureResizeState`, `PieceOfFurnitureRotationState`, `PieceOfFurniturePitchRotationState`, `PieceOfFurnitureRollRotationState`, `PieceOfFurnitureElevationState`, `PieceOfFurnitureHeightState`, `PieceOfFurnitureNameRotationState`, `PieceOfFurnitureNameOffsetState`, `LabelRotationState`, `LabelElevationState`, `DimensionLineResizeState`, `DimensionLinePitchRotationState`, `DimensionLineElevationState`, `DimensionLineHeightState`, `DimensionLineOffsetState`, `PolylineResizeState`, `CompassResizeState`, `CompassRotationState`, `CameraYawRotationState`/`CameraPitchRotationState`/`CameraElevationState`, `LightPowerModificationState`, plus `AbstractWallState`/`AbstractRoomState`/`AbstractPolylineState`/`AbstractModeChangeState` bases and a `ControllerStateDecorator`. **OBSERVED** (`evidence/all_classes.txt`).
- **Each state owns its own edit class and its own commit point.** The edit-type list and the state list line up almost one-to-one (`WallResizeState`→`WallResizingUndoableEdit`, `CompassResizeState`→`CompassResizingUndoableEdit`, `RoomAreaRotationState`→`RoomAreaRotationUndoableEdit`, `LightPowerModificationState`→`LightPowerModificationUndoableEdit`, …), which is how "one gesture = one correctly-labelled edit" is achieved without a central switch: the gesture *is* the object that knows how to invert itself. **OBSERVED** (`evidence/undo_types.txt` vs `evidence/all_classes.txt`).
- **One gesture = one edit.** The state captures old values on press, mutates the model directly during the drag, and posts a single edit on release: `postPieceOfFurnitureMove(...)` at 7037 (called from the move state at 9825), `postWallResize(...)` at 7204 (called at 11322), `postRoomResize(...)` at 7308 (called at 14518). The editors of these edits are guarded: e.g. `postPieceOfFurnitureMove` only posts when `dx!=0 || dy!=0 || angle/depth/elevation changed`.
- Because `isModificationState()` is true during the gesture, `HomeController`'s undo listener keeps the Undo action disabled mid-drag, and `PlanComponent` defers icon invalidation; when the gesture ends those flush. **INFERRED** from the two observed facts.
- **Selection is part of undoable state.** Many edits store `oldSelection`/`allLevelsSelection` and restore them in `undo()` (`WallsCreationUndoableEdit`, `WallsJoiningUndoableEdit`, `ItemsMovingUndoableEdit`, `LevelModificationUndoableEdit`). So undo restores not only geometry but the selection/level context in which the user made the change. **OBSERVED**.

### 2.8 Modes, focus routing and inline editable properties

Three more cogs complete the architecture — **OBSERVED**:

- **Tool modes are extensible named constants, not a closed enum.** `PlanController.Mode` deliberately does **not** use Java's `enum` ("Don't qualify Mode as an enumeration to be able to extend Mode class") and exposes `SELECTION`, `PANNING`, `WALL_CREATION`, `ROOM_CREATION`, `POLYLINE_CREATION`, `DIMENSION_LINE_CREATION`, `LABEL_CREATION` as `public static final Mode` instances with a `name()`. Plug-ins can therefore define their own modes. **OBSERVED** (`viewcontroller_PlanController.java:85–111`). This maps directly onto CasaPlazAI's redesign vocabulary ("Plan / 3D / Walk modes" + tool card): a mode is *what pointer gestures mean*, and it is independent of which surface is showing.
- **Action enablement is routed by which view has focus.** `HomeController.focusedViewChanged(View)` stores the focused view and re-runs `enableActionsBoundToSelection()`, `enablePasteAction()`, `enablePasteToGroupAction()`, `enablePasteStyleAction()`, `enableSelectAllAction()`. Those methods then branch on `focusedView == furnitureCatalogView | furnitureListView | planView | view3D`, so COPY/CUT/DELETE/MODIFY_FURNITURE are enabled for the exact combination of focused surface and current selection. `HomeView.ActionType` is a single ~140-member enum covering menu, toolbar, sort, display-column and tool actions, and `HomeController` toggles them via `view.setEnabled(ActionType.X, bool)`. **OBSERVED** (`viewcontroller_HomeController.java:872–930, 1973–1980`; `viewcontroller_HomeView.java:38–82`).
- **Inline "editable distance" editing shares the same state machine.** `EditableProperty` is a small enum `{X, Y, LENGTH, DIAGONAL, ANGLE, THICKNESS, OFFSET, ARC_EXTENT}`; the active state advertises which of them are editable at the current selection via `planView.setToolTipEditedProperties(...)`, and typed values arrive through `updateEditableProperty(EditableProperty, Object)` which the state machine forwards (`this.state.updateEditableProperty(...)`). So "type a wall length while dragging" is just another controller-state hook, not a separate subsystem. **OBSERVED** (`viewcontroller_PlanController.java:114–116, 426–427, 9382–9384, 10945, 11035, 13019, 14289`).

Editor-only state (snap settings, measurement annotations, blueprint underlay) is deliberately **outside** the schema, under separate localStorage keys. **OBSERVED** (shared schema file).
