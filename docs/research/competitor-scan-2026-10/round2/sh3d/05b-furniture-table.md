## 1. Summary

- **The list is a custom "tree-table", not a grid and not editable.** In the web build it is a `<div class="tree-table">` with `[header]/[body]/[row]/[cell]` divs rendered by `JSTreeTable` + `FurnitureTablePanel`; the desktop build uses a Swing `JTable`. In **both** builds the cells are **read-only** — there is no cell editor anywhere (`isCellEditable` / `setValueAt` / `DefaultCellEditor` do not exist in the JS bundle) [OBSERVED, `evidence/table_region.pretty.js`, live DOM `evidence/live_table_probe*.json`; OBSERVED, no editor in `evidence/SH3D_FurnitureTable.java`].
- **23 sortable properties exist but only 5 columns are visible by default**, in this exact order: **Name, Width, Depth, Height, Visible** — measured live on a 48-piece demo home and matching the `Home` constructor's default list. Hidden columns are re-inserted **at the canonical position** when re-shown, and the visible set can never become empty [OBSERVED, live `evidence/live_table_probe5.json`, `evidence/live_table_probe7.json`; OBSERVED, `evidence/SH3D_Home.java` lines 161–166].
- **Sorting is three-state and stored on the document.** Clicking a column header cycles **ascending → descending → off (insertion order)**; the state lives on `Home` (`FURNITURE_SORTED_PROPERTY` / `FURNITURE_DESCENDING_SORTED`) and therefore travels with the saved file and is tracked by the web recorder. The header shows an ascending/descending arrow [OBSERVED, live `evidence/live_table_interactions.json`; OBSERVED, `evidence/SH3D_FurnitureController.java` `sortFurniture`].
- **"Visibility" is a per-row checkbox, but it is a selection-driven action, not an inline edit.** The checkbox is enabled only for top-level rows (disabled on group children) and clicking it calls "toggle visibility of the **selected** piece", so on an unselected row the **first click only selects** and the second click hides — reproduced live [OBSERVED, `evidence/live_table_probe7.json`, `evidence/live_table_probe8.json`; OBSERVED, `evidence/table_region.pretty.js` `renderBooleanCell` + `isRootPieceOfFurniture`].
- **Selection is two-way and multi-select is real**, using the platform multi-select modifier (Ctrl / ⌘), with group parents counting as one selected row but expanding to their children: live `setSelectedFurniture([...])` selected 47 pieces and the DOM showed all 49 rows highlighted, because one expanded group contributes its 2 children to the same selection [OBSERVED, `evidence/live_table_probe2.json`, `live_table_probe5.json`, `evidence/SH3D_FurnitureTable.java` `updateTableSelectedFurniture`].

## 2. Findings

All live observations were made against the **real running web app** (`https://www.sweethome3d.com/SweetHome3DJSOnline.jsp`) in headless Chromium with the page's own JS reached over CDP. The page exposes `viewHome(url)` and `window.application`, whose `homeControllers` map gives the live `Home` / `FurnitureController` / `PlanController` objects. Scripts: `evidence/probe_table*.cjs`; raw results: `evidence/live_table_*.json`. This closes round-1 Unknowns #2–#4 for the table (round 1 could not populate it).

### 2.1 Structure and rendering of the list

[OBSERVED, `evidence/table_region.pretty.js`; `evidence/sweethome3djs.css`; live DOM dumps]

- `FurnitureTablePanel` is created by the view factory for the DOM element **`#furniture-view`** and delegates to `JSTreeTable`, which builds `div.tree-table` → a `[header]` row plus a `[body]` of `[row]` elements (each row is a flex row of `[cell]` divs). The CSS gives the header a dark background, per-cell `data-name` attributes, an `:after` ascending/descending arrow, right-aligned `.number` cells, a centered `.boolean`/`.color` cell, a 1.2 em icon before the name, and `#BBDDFF` for `[row].selected`.
- The DOM probe of a live **Studio** demo home showed one `.tree-table` and **48 top-level rows** on a freshly loaded page (`evidence/live_table_probe2.json`, `live_table_probe7.json` `tableCount: 1`); after grouping two pieces the row count became 49 (the group row) (`evidence/live_table_probe6.json`). When I called the page's `viewHome()` **a second time in the same page**, a second `.tree-table` appeared, so probes that followed an earlier load saw two copies (e.g. the header array had 10 entries = 2 × 5 columns in `evidence/live_table_interactions.json`). Later probes therefore scoped to the last `.tree-table`. I did not verify the app's lifecycle semantics for repeated `viewHome()` calls — one list per loaded home is the observed normal case.
- Row identity: each row element keeps the model piece on `row._model.value`; cells are re-rendered individually on a property change (`updateRowData`) and the whole body is regenerated on sort/visible-property/collection/level change.

### 2.2 The column set and the **correction** to round 1

[OBSERVED, live `evidence/live_table_probe5.json`, `evidence/live_table_probe7.json`; OBSERVED, `evidence/SH3D_Home.java`; DOCUMENTED, userguide]

- The `FurnitureTable` resource family defines **23** column identifiers: `CATALOG_ID, NAME, DESCRIPTION, CREATOR, LICENSE, WIDTH, DEPTH, HEIGHT, X, Y, ELEVATION, ANGLE, LEVEL, MODEL_SIZE, COLOR, TEXTURE, MOVABLE, DOOR_OR_WINDOW, VISIBLE, PRICE, VALUE_ADDED_TAX_PERCENTAGE, VALUE_ADDED_TAX, PRICE_VALUE_ADDED_TAX_INCLUDED` [OBSERVED, `evidence/table_region.pretty.js`; `evidence/SH3D_FurnitureTable.java` `createAvailableColumns`].
- **Correction.** Round-1 §2.6 said the *default visible* set is the 23-column canonical list. That is wrong: the default visible set is **`[NAME, WIDTH, DEPTH, HEIGHT, VISIBLE]`**, and the 23-item list is only the **re-insertion order** used when a hidden column is re-shown. I verified this two ways: the `Home` constructor assigns exactly those five defaults (`evidence/SH3D_Home.java` lines 161–166; the same five in the JS bundle at byte ~1132000), and the live app's home reports `getFurnitureVisiblePropertyNames() === ["NAME","WIDTH","DEPTH","HEIGHT","VISIBLE"]` with the header rendering exactly those five `data-name` cells (`evidence/live_table_probe5.json` init step, `evidence/live_table_probe7.json` initial step).
- **Web build trims the menu.** The live context-menu "Display column" submenu offers **18** checkboxes: Name, Description, Creator, License, Width, Depth, Height, Abscissa, Ordinate, Elevation, Angle, Level, Model size, Color, Texture, Movable, Door/Window, Visible (`evidence/live_table_probe6.json`). `Catalog ID` and the three Price/VAT columns are absent — consistent with the desktop rule that Price/VAT columns are only accepted when a currency is configured and VAT is enabled, and with the web build offering no currency preference [OBSERVED live; OBSERVED, `evidence/SH3D_FurnitureTable.java` `isPropertyAccepted`; INFERRED for the exact reason Catalog ID is hidden in the web menu].
- **Re-showing a column restores canonical order, not append order.** Live: start `NAME,WIDTH,DEPTH,HEIGHT,VISIBLE` → set visible to `NAME,WIDTH,DEPTH,HEIGHT,X,Y,VISIBLE` → DOM header follows exactly → toggle WIDTH off → header `NAME,DEPTH,HEIGHT,X,Y,VISIBLE` → toggle WIDTH on → header back to `NAME,WIDTH,DEPTH,HEIGHT,X,Y,VISIBLE` (WIDTH returned between NAME and DEPTH, not at the end) [OBSERVED, `evidence/live_table_probe5.json`].
- **The visible set can never be empty.** Live: setting visible to `[NAME]` then toggling NAME off leaves `[NAME]` in place — the guard re-adds Name [OBSERVED, `evidence/live_table_probe5.json` last step; OBSERVED, `evidence/SH3D_FurnitureController.java` lines 733–741, and the JS equivalent `toggleFurnitureVisibleProperty`].
- **Column widths: desktop persists, web does not.** The desktop table stores a comma-separated `ColumnWidths` visual property on the home on every width change and restores it on load [OBSERVED, `evidence/SH3D_FurnitureTable.java` `updateTableColumnsWidth` / `addTableColumnModelListener`]. In the web build the literal `ColumnWidths` does **not** occur in the bundle and the live home property read back `null`, while each column carries a CSS `defaultWidth` (`CATALOG_ID`/`NAME` 4/14 rem, etc.) that is fixed [OBSERVED, live `evidence/live_table_probe5.json` `colWidths: null`; OBSERVED, `evidence/table_region.pretty.js` `defaultWidth`; INFERRED that the web build simply does not persist user column widths].
- **Desktop also allows column drag-reorder; the web build does not.** The desktop table writes the new visible-property order whenever the user moves a column [OBSERVED, `evidence/SH3D_FurnitureTable.java` `columnMoved`]; the JS bundle contains no `setDragEnabled` / reordering symbol, and the only way to reorder in the web build is via the controller (which the menu does not expose as drag) [OBSERVED for the absence; INFERRED for the consequence].

### 2.3 Sorting: three-state, header-driven, persisted

[OBSERVED, live `evidence/live_table_interactions.json`; OBSERVED, `evidence/SH3D_FurnitureController.java`; `evidence/table_region.pretty.js`]

- **Cycle.** Clicking a header cell sorts by that column ascending; clicking it again sorts descending; a third click **clears** the sort and the rows fall back to insertion order. This was reproduced live on the `WIDTH` column: initial `NAME:asc` → `WIDTH:asc` (first rows became `Cylinder, Cylinder, Spotlight`) → `WIDTH:desc` (first rows became `Slider window, Square table, Sliding doors`) → third click removed the sort marker and the first rows returned to insertion order (`Armchair, Square table, Plant`). The controller's documented contract is identical [OBSERVED, `evidence/SH3D_FurnitureController.java` `sortFurniture(String)`].
- **State lives on the home, not in the widget.** After the live header click the home reported `{prop: "DEPTH", desc: false}`; the initial home already reported `sortedProp: "NAME", descending: false`, and `DEFAULT_TRACKED_HOME_PROPERTIES` in the web bundle includes `FURNITURE_SORTED_PROPERTY`, `FURNITURE_DESCENDING_SORTED` and `FURNITURE_VISIBLE_PROPERTIES`, so the sort and column layout are part of the autosaved/recorded home [OBSERVED, `evidence/live_table_probe3.json`, `live_table_interactions.json`; OBSERVED, JS bundle `IncrementalHomeRecorder.DEFAULT_TRACKED_HOME_PROPERTIES`].
- **Headers show direction** via an ascending/descending arrow image (CSS `:after`, and an `ascending.png`/`descending.png` icon on the desktop header renderer) [OBSERVED, `evidence/sweethome3djs.css`; OBSERVED, `evidence/SH3D_FurnitureTable.java` `getHeaderRenderer`].
- **Only sortable properties sort.** A header click only acts when the column identifier is a `SortableProperty` (or a home additional property) [OBSERVED, `evidence/SH3D_FurnitureTable.java` `addTableHeaderListener`; OBSERVED, `evidence/table_region.pretty.js` `sortTable`/`sortChanged`].
- **Comparators are per-property and locale-aware**: numbers compare numerically, names/dates/text through a `Collator`, booleans false-before-true, and ties fall back to the name [OBSERVED, `evidence/SH3D_HomePieceOfFurniture.java` `SORTABLE_PROPERTY_COMPARATORS`; `evidence/SH3D_FurnitureTable.java` `getFurnitureComparator`].

### 2.4 Inline editing: there is none — the table is read-only

[OBSERVED, `evidence/SH3D_FurnitureTable.java`; OBSERVED, JS bundle symbol scan]

- **No cell editor.** The desktop class overrides no `isCellEditable`, `setValueAt` or `getCellEditor`, and the JS bundle contains **zero** occurrences of `isCellEditable`, `setValueAt`, `getCellEditor` or `DefaultCellEditor`. Every column has a `TableCellRenderer` (a cell *painter*) but no editor [OBSERVED, `evidence/SH3D_FurnitureTable.java` `getColumnRenderer`; `evidence/table_region.pretty.js` `renderCell`].
- **The two interactive affordances are painted widgets, not editors:**
  1. the **Visible** checkbox, handled by a table-level mouse listener that checks whether the click landed on the rendered component and then calls the controller (§2.5), and
  2. a small **information icon** in the Name cell when a piece carries `information`, opening an HTML popup; the popup's hyperlinks open in the browser [OBSERVED, `evidence/SH3D_FurnitureTable.java` `addMouseListener` / `showInformationPopup`].
- **Editing is done elsewhere:** double-clicking a row calls `modifySelectedFurniture()` → the shared *Modify furniture* dialog. Live, a synthetic double-click opened a visible dialog titled "Modify furniture" with the full field set (name, description, price, X/Y/elevation, mirrored shape, part of base plan, color/texture, orientation, size, shininess, visible) [OBSERVED, `evidence/live_table_probe2.json` `afterDbl`]. The same dialog is reachable from the context menu ("Modify furniture…") [OBSERVED, `evidence/live_table_probe4.json`].
- **The other edit surfaces are the plan indicators and drag-and-drop**, not the table: on-plan rotation/elevation/height/size indicators, and dragging a piece from the catalog onto the plan **or onto the list** [DOCUMENTED, userguide lines 218–231].
- **Read-only cells are also visually inert:** `MOVABLE` and `DOOR_OR_WINDOW` render as **disabled** checkboxes; live, with columns `NAME,WIDTH,HEIGHT,MOVABLE,DOOR_OR_WINDOW,VISIBLE`, the `MOVABLE` and `DOOR_OR_WINDOW` checkboxes had `disabled: true` while `VISIBLE` had `disabled: false` [OBSERVED, `evidence/live_table_probe8.json` `disabledColumnsDom`; OBSERVED, `evidence/SH3D_FurnitureTable.java` `getBooleanRenderer` (`BooleanRenderer(false)` for MOVABLE/DOOR_OR_WINDOW, `true` for VISIBLE)].

### 2.5 Visibility toggles — a selection-coupled checkbox (with a real UX gotcha)

[OBSERVED, `evidence/SH3D_FurnitureTable.java`; OBSERVED, live `evidence/live_table_probe7.json`, `live_table_probe8.json`; DOCUMENTED, userguide line 231]

- The **Visible** column renders an interactive checkbox. Clicking a *selected* single piece's checkbox flips that piece's visibility. Live: row 7 `Chair` was selected first, then its checkbox was clicked → the model piece's `isVisible()` went `true → false`, the checkbox became unchecked, and the row **stayed in the list** while the piece left the plan/3D (`invisibleModel: ["Chair"]`). This is exactly the user-guide promise: *"Invisible furniture isn't drawn in the home plan and 3D view, but it will still appear in the furniture list to let you make it visible again later."*
- **The gotcha, reproduced live.** On an **unselected** row, the first checkbox click only **selects** the row; the model's visibility is unchanged. A second click on the same checkbox then hides it. Sequence observed on row 5 `Box`: initial `{cb:true, modelVisible:true, rowSelected:false}` → 1st click `{cb:false, modelVisible:true, rowSelected:true}` (checkbox repainted from the still-visible model) → 2nd click `{cb:false, modelVisible:false, rowSelected:true}` [OBSERVED, `evidence/live_table_probe8.json`].
  Cause [OBSERVED in code]: the click handler calls `toggleSelectedFurnitureVisibility()`, which by contract acts only when **exactly one** piece is selected, and it goes through the undoable `HomeFurnitureController` path so it can be undone; the row-click listener that updates the selection fires in the same gesture.
- **Group children are not directly toggleable.** Live, after grouping two pieces and expanding the group, the parent "Group -1-" row's Visible checkbox was `disabled:false` while both child rows' checkboxes were `disabled:true` [OBSERVED, `evidence/live_table_probe7.json` `afterExpand`; OBSERVED, `evidence/SH3D_FurnitureTable.java` `getBooleanRenderer` VISIBLE case — "Enable component only for root children to avoid the complexity of managing partially visible groups"].
- **Group visibility semantics** are derived, not stored: a group is visible if any child is visible, and it is movable only if all children are movable [OBSERVED, `evidence/SH3D_HomeFurnitureGroup.java`; matches round-1 §2.7].
- In the desktop build the same effect is available as a menu/undoable action, and `toggleSelectedFurnitureVisibility` also exists in the JS controller — the web build drives it from the checkbox [OBSERVED for the method in both].

### 2.6 Multi-selection and its link to the plan

[OBSERVED, live `evidence/live_table_probe2.json`, `live_table_probe5.json`, `live_table_probe7.json`; OBSERVED, `evidence/SH3D_FurnitureTable.java`; `evidence/table_region.pretty.js`]

- **Modifier.** A plain row click replaces the selection; holding the platform shortcut modifier (**⌘ on macOS / Ctrl elsewhere**) adds or removes that row. Live on macOS: plain click row 1 → `["Armchair"]`; ⌘-click row 2 → `["Armchair","Bed"]`; ⌘-click row 3 → `["Armchair","Bed","Bedside table"]`; and the same three rows were highlighted in the DOM (`selNames` matched `["Armchair","Bed","Bedside table"]`) [OBSERVED, `evidence/live_table_probe2.json`].
- **Table → model.** The table's list-selection listener builds the selected piece list from the selected rows (`getValueAt(row, 0)`), skips pieces that are already inside a selected group so a parent and its children are not both sent, and calls `controller.setSelectedFurniture(pieces, singleSelection)`. The controller replaces the home selection for a plain click and merges/toggles it for a modifier click (the merge path removes pieces already selected and appends the new ones) [OBSERVED, `evidence/SH3D_FurnitureTable.java` lines 251–275; `evidence/SH3D_FurnitureController.java` `setSelectedFurniture(List, boolean)`].
- **Model → table.** A home selection listener calls `updateTableSelectedFurniture`, which expands the path to each selected piece, maps each piece to its row in the *currently sorted* model, and re-applies a row selection interval (merging adjacent indices) while suppressing its own listener to avoid a loop [OBSERVED, `evidence/SH3D_FurnitureTable.java` `updateTableSelectedFurniture`].
- **Round trip verified live.** `selectAll()` set 47 selected home items and the DOM showed all 49 rows highlighted (one expanded group contributes its 2 children to the same selection); selecting `h.getFurniture()[2]` from the model highlighted exactly `Plant` in the DOM [OBSERVED, `evidence/live_table_probe5.json` `syncForward`/`syncForwardDom`; `evidence/live_table_probe7.json` `selRoundTrip`/`selRoundTripDom`].
- **Plan ↔ list.** The plan and the list share the *same* `Home.getSelectedItems()` list, so a selection made in the plan pane immediately selects the corresponding rows in the list and vice-versa. The plan-side selection API is on `PlanController` (`selectAll`, `selectAllAtAllLevels`, `selectItem`, `toggleItemSelection`, `deselectAll`, `isItemSelectedAt`, rectangle selection…) and the furniture side on `FurnitureController` (`setSelectedFurniture`, `selectAll`, `getMovableSelectedFurniture`) [OBSERVED, live `evidence/live_table_probe7.json` `planToTable.pcProto`; `evidence/SH3D_FurnitureTable.java`].
- **Selecting a group row selects its children (in the plan) but is one list row.** When the selected group row is expanded, the row-selection logic also highlights the group's child rows; the controller receives the group as a single item, and re-selecting through the table strips children that are covered by the group [OBSERVED, `evidence/SH3D_FurnitureTable.java` lines 309–320; `evidence/table_region.pretty.js` `selectRowAt` recursion; live `evidence/live_table_probe6.json` showed `selectedCount: 3` for a group row plus 2 children].
- **Selection is scrolled into view** when it did not come from the user, and the list also expands the group containing a selected row [OBSERVED, both implementations].
- **Base-plan lock filters selection.** When the home's base plan is locked, the controller strips pieces that belong to the base plan (non-movable or door/window) out of any selection [OBSERVED, `evidence/SH3D_FurnitureController.java` `setSelectedFurniture` + `getFurnitureNotPartOfBasePlan`].

### 2.7 Grouping shown as collapsible tree rows inside the same table

[OBSERVED, live `evidence/live_table_probe6.json`, `live_table_probe7.json`; OBSERVED, `evidence/table_region.pretty.js`; `evidence/SH3D_FurnitureTable.java`; DOCUMENTED, userguide]

- Group rows are ordinary rows carrying `group`; collapsed rows carry `collapsed`. The name cell gets a **twisty** drawn before the text (CSS `:before` with the descending arrow, rotated −90° when collapsed) and the click handler treats a click in the **first 16 px** of the name cell as the expand/collapse gesture (`if (m.clientX < 16)`) [OBSERVED, `evidence/table_region.pretty.js` `generateRowElement`; `evidence/sweethome3djs.css`].
- **Indentation** encodes depth: top-level rows render `padding-left: 15px`, child rows `25px` (15 + 10 per level) [OBSERVED, live `evidence/live_table_probe7.json` `afterExpand`; OBSERVED, `evidence/table_region.pretty.js` `main.style.paddingLeft = (15 + indentation*10) + "px"`].
- **Expanded groups are persisted on the home** as `com.eteks.sweethome3d.SweetHome3D.ExpandedGroups` (a comma-separated list of row indices, saved only for home format ≥ 5000). Live: expanding a group wrote `expandedProp: "22"`; collapsing it wrote `""`; the group's persisted index is its row index in the current sorted list, so it is positional rather than identity-based [OBSERVED, live `evidence/live_table_probe5.json`, `live_table_probe6.json`; OBSERVED, `evidence/SH3D_FurnitureTable.java` `storeExpandedRows`; JS equivalent in `evidence/table_region.pretty.js`].
- **Groups count toward the "never empty column" and sort interactions** as single rows; a group is one row until expanded, then its children appear beneath it, and children are sorted/filtered with the same comparator as top-level rows [OBSERVED, `evidence/SH3D_FurnitureTable.java` `getFilteredAndSortedFurniture` / `FurnitureTreeTableModel`].
- The desktop build renders the tree through a real `JTree` used as the name-cell renderer (with the twisty handles); the web build reimplements the same idea with divs and CSS [OBSERVED, both sources; INFERRED that the desktop twisty is the JTree's own handle].

### 2.8 Menu surfaces around the table, and what the web build drops

[OBSERVED, live `evidence/live_table_probe6.json`; OBSERVED, `evidence/SH3D_HomePane.java`; unbundled-symbol scan]

- The web build has **no menu bar** (matches round-1 §2.1), so all list commands live in a **context menu on the list**. The live menu tree (read from the actual `.popup-menu` DOM) is:
  - `Cut`, `Copy`, `Modify furniture…`, `Group furniture`, `Ungroup furniture`,
  - `Align or distribute furniture ▸` (Align on top / bottom / left / right / front side / back side / left side / right side / Align side by side / Distribute horizontally / Distribute vertically),
  - `Reset elevation`,
  - `Sort by ▸` (20 radio items: Name…Visibility plus **Descending order**),
  - `Display column ▸` (18 checkboxes: Name…Visible).
  [OBSERVED, `evidence/live_table_probe6.json` `menuTree`, `evidence/live_table_probe4.json` `contextMenuItems`]
- The desktop equivalent builds the same two submenus as real menu items plus the same context-menu copy, with the check state driven by a special toggle model that reads `home.getFurnitureVisiblePropertyNames()` live — so the checkmarks always reflect the document [OBSERVED, `evidence/SH3D_HomePane.java` `createFurnitureDisplayPropertyMenu` / `updateDisplayPropertyMenu`].
- **Web-only omissions in the list area [OBSERVED for the symbol scan, INFERRED for the UX consequence]:** the web bundle has no `ColumnWidths` persistence, no `setDragEnabled`/row-reorder, and no price-total footer (`totalPriceLabel` count 0). The desktop `FurnitureTablePanel` adds a **totals footer** (total price, total VAT, price incl. VAT) that sums the currently filtered pieces and blanks itself when prices use mixed currencies, and can print/export the table as **CSV** (`exportToCSV`, `EXPORT_TO_CSV` action; the action symbol *is* present in the web bundle at four sites, but the CSVs of the export path are a desktop/print feature per the guide's *Print* section).
- **The list is also what gets printed**: by default a print job includes the furniture list, the plan and the current 3D view, and printable renderers blank the sort arrows and turn boolean cells into `"x"`/`""` text [OBSERVED, `evidence/SH3D_FurnitureTable.java` `print`; DOCUMENTED, userguide line 310].

## 3. Ideas for CasaPlazAI

Ranked by value ÷ effort. Each ties to a finding above and, where relevant, to CasaPlazAI's `FloorplanData` schema (furniture entry = `id`, `type` (7-value enum), `roomId`, `position`, `rotationDeg`, `footprint`).

| # | Idea | Ties to | Value | Effort |
|---|---|---|---|---|
| 1 | **Two-way selection between the plan and a furniture list panel.** CasaPlazAI already has a home model and a plan; a list that highlights the same selection the canvas has (and vice versa) is the single highest-value table idea and needs only one shared `selectedIds` array in editor state — not in `FloorplanData`. | §2.6 round trip; §2.5 group-aware selection | High | Low |
| 2 | **Three-state header sorting that persists per plan.** Click = asc, click = desc, click = off/creation order; store `{sortKey, sortDir}` next to the autosaved plan (a dedicated `casaplaza.list.settings.v1` key is enough — do **not** widen `FloorplanData`). | §2.3 cycle + `FURNITURE_SORTED_PROPERTY` on the home | High | Low |
| 3 | **Column show/hide with canonical re-insertion order and a never-empty guard.** Ship a small default set — `Name, Width, Depth, Height, Visible`-equivalent for CasaPlazAI (`type`, `footprint.a`, `footprint.b`, `rotationDeg`, `visible`) — and re-insert a re-shown column at its canonical slot rather than appending. | §2.2 default set + re-insertion; §2.2 never-empty guard | High | Low |
| 4 | **An explicit per-item `visible` flag that hides on canvas but stays listed.** CasaPlazAI's `FurnitureItem` has no visibility field; keep it **out of `FloorplanData`** (a `casaplaza.list.hidden.v1` id set) so the 2D/3D contract is untouched, exactly as the schema keeps snap/underlay state out. | §2.5 invisible-but-listed; schema's "out-of-schema editor state" convention | High | Low |
| 5 | **Make the visibility toggle act on the row, not on the selection.** Sweet Home 3D's checkbox is selection-coupled, which produced the observed first-click-selects-second-click-hides gotcha. CasaPlazAI should bind the toggle straight to the row's `id` and make the two-click behaviour impossible. | §2.5 gotcha (anti-pattern to avoid) | High | Low |
| 6 | **Row-type-aware enablement for derived/read-only fields.** Sweet Home 3D disables `Movable`/`Door-or-window` checkboxes and disables the visibility checkbox on group children. CasaPlazAI should render `type` and constraint-derived fields as non-interactive text and reserve interaction for `visible`. | §2.4 disabled booleans; §2.5 group children | Med–High | Low |
| 7 | **Double-click a row to edit it in the inspector.** Instead of building inline cell editors (Sweet Home 3D has none), route a double-click on a list row to CasaPlazAI's new inspector panel for the furniture item — consistent with the in-progress Plan/3D/Walk + inspector redesign, and cheaper than per-cell editors. | §2.4 no inline editing; §2.4 double-click → dialog | Med–High | Low |
| 8 | **Nested groups as collapsible list rows with persisted expansion.** If grouping lands in CasaPlazAI (round-1 idea #5), represent a group as one row with a twisty, indent children by depth, and persist expanded group ids (by **id**, not by row index — Sweet Home 3D stores positional indices, which drift when the list re-sorts). | §2.7 indentation, twisty-at-16px, persisted `ExpandedGroups`; §2.7 positional-index weakness | Med | Med |
| 9 | **A totals/derived row or footer.** Sweet Home 3D's desktop list carries a totals footer and blanks it on mixed currencies. CasaPlazAI could show e.g. count per `roomId`, total occupied area from `footprint`, or a level filter — cheap and immediately useful while the palette is small. | §2.8 totals footer | Med | Low–Med |
| 10 | **Sort/column layout travels with the plan (or with the editor profile).** Sweet Home 3D stores layout on the home so a shared file opens looking the same. Decide deliberately: either the same as CasaPlazAI's autosaved editor state, or per-user — but if it is in the autosaved plan, it must also be survivable across schema migrations. | §2.3 tracked home properties; schema `migrate()` convention | Med | Low–Med |
| 11 | **Keyboard-and-modifier multi-select parity with the canvas.** Implement ⌘/Ctrl-toggle on rows and expose `selectAll`; ensure a group row and its children never both enter the selection (Sweet Home 3D strips duplicates). | §2.6 modifier, group-aware stripping | Med | Low–Med |
| 12 | **CSV / print export of the list.** Sweet Home 3D prints the list with the plan and has a CSV export path. CasaPlazAI already exports PNG/JPEG; a "list as CSV" is a small, clearly-scoped addition that avoids reusing any GPL code. | §2.8 print + CSV; §2.8 printable renderers | Med | Med |

**Anti-patterns to avoid (each observed):** (a) the selection-coupled visibility checkbox (§2.5) — bind toggles to row identity; (b) storing expanded groups as **row indices** (§2.7) — re-sorting shifts them, so persist ids; (c) offering 23 columns at once in the menu (§2.2) — the web build already hides 5 of them behind preference checks, which is confusing; (d) tying price/VAT columns to a currency preference that then silently disappears from the menu (§2.2) — prefer an explicit disabled-with-reason state over vanishing UI.

## 4. Unknowns / what I could not verify

1. **The macOS desktop app was not run** (no installers permitted). All desktop-specific behaviour — the totals footer, CSV export dialog, column drag-reorder with `ColumnWidths` persistence, the `reorderingEnabled` system property, and printing the list — is established from the GPL sources in `evidence/SH3D_*.java` and the user guide, i.e. **DOCUMENTED/OBSERVED-in-source, not observed running**.
2. **The "Catalog ID" column is missing from the web context menu but present in the JS `createTableModel` column table.** I infer the web menu simply never registers that action for the online build; I did not find the exact registration site. The **23-vs-18 column** counts are therefore: 23 declared, 5 default-visible, 18 offered in the web menu [OBSERVED for each number].
3. **Column-width persistence in the web build is inferred negative.** I observed the live home property `ColumnWidths` is `null`, and the literal does not appear in the web bundle — but I did not resize a column through a real user drag to confirm nothing is stored.
4. **I could not click a real group twisty through Playwright-class input.** I dispatched a synthetic `mousedown/click` at `clientX = left+4`; the group did toggle and `ExpandedGroups` changed, but the expand/collapse in some runs also left rows hidden in ways the row-count probe did not fully characterize (the probe counts DOM rows, including `display:none` ones). The 16-px twisty hit zone is read from code, not measured precisely.
5. **Cross-platform multi-select modifier.** I reproduced ⌘-click on macOS Chromium. The code branches on `OperatingSystem.isMacOSX()` to use Meta vs Ctrl; I did not verify the Ctrl path on Linux/Windows.
6. **The `information` popup** (an HTML popup with clickable links, shown by a click on the info icon in the Name cell) is described from source; no demo home in the examples set carried `information`, so it stayed unobserved live.
7. **"Additional columns" from the home file format** (`ObjectProperty`, e.g. a plugin-defined property shown as a column and sortable) were not exercised on any live home: none of the example homes had additional properties, and the web "Display column" menu showed none.
8. **The `FurnitureView.FurnitureFilter` mechanism** (a view-level filter that can restrict which pieces a list shows, used by the plan/list pairing in the desktop `HomePane`) exists in the source; I did not see it engaged by any user-visible control in the web build.
9. **Exact desktop row drag-and-drop reordering** (`FurnitureTransferHandler` MOVE action, `moveSelectedFurnitureBefore`, insert-row drop mode) is read from source; it is disabled whenever the list is sorted, which I confirmed only by reading the focus listener, not by dragging.
10. **Unverified:** whether any of these list behaviours differ in the mobile (iOS/Android) builds, and whether the online "registered/autosave" variant records the list layout differently from the anonymous session I used.
