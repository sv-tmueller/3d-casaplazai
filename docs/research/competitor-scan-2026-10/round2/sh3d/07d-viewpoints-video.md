## 1. Summary

- **A stored point of view is a full camera snapshot, not just a position.** Each one carries `name, x, y, z, yaw, pitch, fieldOfView, time, lens, renderer, id` plus arbitrary user properties, and it is a duplicate of whichever camera was active: stored from the virtual-visitor side it is an `ObserverCamera` (so "Go to" returns to eye-level mode), stored from the aerial side it is a plain camera (so "Go to" returns to aerial mode). **[OBSERVED]** live probe (`rea-out/probe1.json`, `probe8.json`) + `src-java/Camera.java`, `src-java/HomeXMLExporter.java`.
- **Hard limit: 50 stored points of view per home, enforced by eviction, not by refusal.** The cap comes from `UserPreferences.getStoredCamerasMaxCount()` (raised from an earlier value to 50 in version 4.5), and `storeCamera()` silently drops the *oldest* entries until the list is at or below 50; storing is also **de-duplicated** by name *or* by identical full pose. **[OBSERVED]** live (`probe3.json`), **[DOCUMENTED]** history + javadoc.
- **The video camera path is a separate, uncapped list of camera snapshots** stored under the home environment (`videoCameraPath`), recorded by a red button in a non-modal "Create video" pane; there is **no 50 entry limit** — a live probe set and read back 5 000 points with no complaint. **[OBSERVED]** `rea-out/probe12.json` + `src-java/VideoPanel.java`, `src-java/HomeEnvironment.java`.
- **Video creation is a three-stage pipeline:** record sparse keyframes → expand them into a dense per-frame path with a **linear interpolation whose step budget is `max(distance, yaw, pitch, FOV, time)` steps**, driven by a global movement speed in m/s (default 2400/3600 ≈ 0.667 m/s ≈ 2.4 km/h) → render each frame through the photo renderers and mux to a **QuickTime `.mov`** with no audio. **[OBSERVED]** `src-java/VideoPanel.java` (`getVideoFramesPath`), `probe1.json`.
- **The browser edition keeps the whole stored-viewpoint / camera-path model but stubs every consumer.** The web bundle parses and writes `storedCamera` and `cameraPath` XML, exposes the same 50 cap and the same classes, yet `createPhoto`, `createPhotos` and `createVideo` are empty no-ops in the web controller and the view factory returns a dummy dialog, so the actions silently do nothing. **[OBSERVED]** live (`probe5.json`, `probe10.json`) + bundle grep + German user guide §"Die Online-Version ... mit Ausnahme ... der Erstellung von Fotos und Videos".

## 2. Findings

### A. Stored point-of-view data model

**What is stored.** A stored point of view is a whole `Camera` snapshot, not an index into a preset list. The camera type exposes: `name`, position `x/y/z`, orientation `yaw` (body rotation, horizontal) and `pitch` (head rotation, vertical), `fieldOfView` (radians), `time` (epoch millis used for sun position / time-of-day), `lens`, `renderer`, an `id`, and a free-form property bag (`setProperty`/`getProperty`/`getPropertyNames`). **[OBSERVED]** `src-java/Camera.java`; live round-trip of pose + time + lens + user property in `rea-out/probe8.json`.

- `Camera.setCamera(other)` copies **only** the pose (`x, y, z, yaw, pitch, fieldOfView`) — it does **not** copy `time`, `lens`, `renderer` or `name`. Copying a viewpoint therefore has to be done field-by-field (that is exactly what the observer/top camera "go to" states do, and what makes `duplicate()` useful). **[OBSERVED]** source.
- `Camera.duplicate()` produces a new camera with a fresh unique id and the same class and pose; used by the video recorder for every recorded keyframe. **[OBSERVED]** `probe8.json`.

**Class of a stored viewpoint.** A stored viewpoint is created by `duplicate()`-ing the **currently active camera**, so its class and its `id` prefix follow the active camera: stored while the virtual visitor is active it is an `ObserverCamera` with id `observerCamera-<uuid>` (the common case, and the one the Studio demo shows — all three of `Entrance`, `Bedroom`, `Kitchen` report `instanceof ObserverCamera === true`); stored while the aerial camera is active it is a plain camera with id `camera-<uuid>`. Live probes confirmed both: storing from the top-camera side produced an entry for which `instanceof ObserverCamera` was **false**, and navigating to it correctly switched the view to the aerial mode. **[OBSERVED]** `probe1.json` (three observer-class viewpoints), `probe3.json` (`isObserver:false` for the stored entry on one run), `probe4.json` (`topStoredIsObserverClass = false`, then `afterGoToTop_activeIsTop = true`), `probe8.json`; `src-java/HomeController3D.storeCamera` (`home.getCamera().duplicate()`).

Consequence (see B): the class of a stored viewpoint is exactly what `goToCamera` uses to decide whether to navigate to eye level or to the aerial view, so a viewpoint remembers not just *where* the camera was but *which mode* it was in when saved.

**The three camera slots of a home.**
1. `observerCamera` — the virtual visitor (eye level); in the live model its id is the fixed string `observerCamera-homeObserverCamera`.
2. `topCamera` — the aerial/plan camera; fixed id `camera-homeTopCamera`.
3. `storedCameras` — an ordered `List<Camera>` of saved viewpoints.
In addition the environment holds `videoCameraPath`, an ordered `List<Camera>` for the video. **[OBSERVED]** `probe1.json`, `probe4.json`; `src-java/Home.java`, `src-java/HomeEnvironment.java`.

The home also exposes a `camera` root attribute that names which of the two live cameras is active (`observerCamera` or `topCamera`). **[OBSERVED]** `src-java/HomeXMLExporter.java`.

**Serialization.** The XML exporter writes one element per camera, where **the element name is the camera's class name (lower-cased first letter) and the `attribute` value names the role** — so an observer-class stored viewpoint and the live observer camera share the element `<observerCamera>` and differ only by `attribute`, and a top-camera-derived stored viewpoint would serialize as `<camera>` like the live aerial camera. Roles:
- `attribute="observerCamera"` for the live virtual-visitor camera, `attribute="topCamera"` for the live aerial camera (the observer camera additionally carries `fixedSize`);
- `attribute="storedCamera"` for each saved viewpoint — the observed `Studio.sh3x` shows `1 × <observerCamera attribute='observerCamera'>`, `1 × <camera attribute='topCamera'>` and `3 × <observerCamera attribute='storedCamera'>` (the three named viewpoints), i.e. the role discriminator is the attribute, exactly as expected;
- `attribute="cameraPath"` for each video keyframe, written **inside the `<environment>` element** rather than at home level.
Written per-camera attributes: `id` (written only when the role is neither `observerCamera` nor `topCamera`, i.e. for stored cameras and path keyframes), `name`, `lens`, `x`, `y`, `z`, `yaw`, `pitch`, `fieldOfView`, `time`, `renderer`, plus `fixedSize` for an `ObserverCamera`; each camera may also carry `property` children. Children order at home level: observer camera, top camera, then each stored camera in list order; in the observed `Studio.sh3x` the three stored viewpoints are named `Entrance`, `Bedroom`, `Kitchen`. **[OBSERVED]** `src-java/HomeXMLExporter.java`, `src-java/ObjectXMLExporter.java` (tag from class simple name); `sh3x/Home.xml` (round-1 artifact, read-only).

**Reading it back in the browser build.** The web XML parser's `endElement` handles the camera element and switches on `attribute`: `cameraPath` → append to `home.getEnvironment().getVideoCameraPath()` then `setVideoCameraPath`; `topCamera`/`observerCamera` → `setCamera` + `setTime` + `setLens` (+ `setFixedSize`); `storedCamera` → append to `getStoredCameras()` then `setStoredCameras`. A shared `setCameraAttributes` additionally applies `setName`, `setRenderer`, `setLens(Camera.Lens[token])` and `setTime(parseInt(...))`. **[OBSERVED]** shipped `libjs-sweethome3d.min.js` (round-1 artifact).

**Equality / change semantics.** The `videoCameraPath` property fires a `VIDEO_CAMERA_PATH` change; `setVideoCameraPath` always copies into a fresh list (and treats `null` as "empty list"), and `getVideoCameraPath()` returns an unmodifiable view, so the model defensively copies in both directions. `Home.clone()` deep-clones every camera in the path (separate objects, identical values). The stored-camera list fires a `STORED_CAMERAS` change (one event per mutation; 2 mutations → 2 events). `Home.getHomeObjects()` includes the top camera, the observer camera, all stored cameras **and** the video-path cameras, so the path cameras are first-class scene objects for bookkeeping. **[OBSERVED]** `probe4.json`, `probe12.json`; `src-java/HomeEnvironment.java`.

**Lens / aspect-ratio vocabulary.** `Camera.Lens = {PINHOLE, NORMAL, FISHEYE, SPHERICAL}` — "pinhole" is the plain straight-line perspective used for video frames; "normal" adds depth of field for stills. Aspect ratios: free, view-3D, 4:3, 3:2, 16:9, 2:1, 2.40:1, square. FISHEYE forces a square output and SPHERICAL forces an equirectangular 2:1 output. **[OBSERVED]** `src-java/Camera.java`; `src-java/AbstractPhotoController.java`, `PhotosPanel`/`PhotoPanel` sources.

### B. Stored point-of-view UI and limits

**Actions.** The 3D-view toolbar/menu exposes (labels read from the live action map, English build): `Store point of view...`, `Delete points of view...`, `Create photos at points of view...`, `Create photo...`, `Create video...`, plus a "Go to point of view" submenu whose entries are the stored viewpoints' names; the live map held 159 actions in total. **[OBSERVED]** `probe9.json`.

**Storing.** `HomeController.storeCamera()` prompts the user with the exact message `"Give a name to the current point of view:"` and a default value equal to the localized short current date (observed default `10/31/2026`). Cancelling the prompt stores nothing (verified). On confirm the new viewpoint is inserted **at the front** of the list. The snapshot is a `duplicate()` of whichever camera is active at that moment, so storing from the aerial camera produces a plain (non-observer) camera entry and storing from the virtual visitor produces an `ObserverCamera` entry. **[OBSERVED]** `probe3.json`, `probe4.json`, `probe8.json`, `probe9.json`; `src-java/HomeController3D.java`.

**De-duplication.** Storing a pose that matches an existing entry (same name **or** identical full pose across `x, y, z, pitch, yaw, fieldOfView, time, lens, renderer`) does not grow the list — but the *new* name replaces the old one, so a re-store acts as a rename/refresh. Concretely, a probe re-stored the same pose under a different name and the count stayed the same while the visible name changed. **[OBSERVED]** `probe3.json`.

**The 50 cap.** `UserPreferences.getStoredCamerasMaxCount()` returns **50**; the history entry for version 4.5 reads "Increased to 50 the maximum count of stored points of view", so an earlier, smaller cap preceded it. Insertion is followed by an eviction loop that removes from the *end* while the list is longer than the cap, i.e. the cap is enforced by silently discarding the oldest points of view. Live stress: 60 consecutive stores produced exactly 50 entries, the newest ones retained, the oldest evicted. This is a **silent** loss — the UI does not warn. **[OBSERVED]** `probe1.json` (`getStoredCamerasMaxCount() = 50`), `probe3.json`; **[DOCUMENTED]** `history.txt` (round-1 artifact), javadoc of `UserPreferences`.

**Navigating.** `goToCamera(camera)` dispatches on class: `ObserverCamera` → view-from-observer (virtual visit), otherwise → view-from-top (aerial), then copies the pose into the corresponding live camera and **moves that viewpoint to the front** of the stored list (so the list self-sorts by recency of use). The live camera is a *different object* from the stored one (`activeIsStoredObject === false`), so editing the current view after "go to" does not mutate the saved viewpoint — good isolation. **[OBSERVED]** `probe4.json`, `probe8.json`.

**Deleting.** `showDeletedCamerasDialog()` builds a real DOM dialog titled `Delete points of view` with the message `Points of view to delete:` and one checkbox per stored viewpoint (live DOM observed); confirming uses a `<b>Do you really want to delete the selected<br>points of view?</b>` prompt with `Delete` / `Do not delete` buttons. In the empty state the pane can show the key `HomePane.NoStoredPointOfView` ("No stored point of view"). The delete and create-photos-at-viewpoints actions are enabled only when `!home.getStoredCameras().isEmpty()`. **[OBSERVED]** `probe9.json`, `src-java/HomeController.java`; **[DOCUMENTED]** localization table (round-1 artifact).

**Rounding / clamping.** When a pose is applied to the live 3D camera, pitch is clamped to ±π/2 and field of view to 2°–120°. The top-camera "go to" additionally recomputes the aerial framing from the home bounds (`updateCameraFromHomeBounds`), so a stored aerial viewpoint re-frames rather than reproducing an exact orthographic box. **[OBSERVED]** `src-java/HomeController3D.java`; shipped JS (`updateCameraFromHomeBounds`). Also note the ObserverCameraState "go to" copies `time`, `lens` and `renderer` in addition to the pose, so a saved viewpoint restores the time-of-day and lens as well. **[OBSERVED]** source.

### C. "Create photos at points of view"

This is the batch sibling of "Create photo": it renders one still per selected stored viewpoint. **[OBSERVED]** `src-java/PhotosController.java`, `src-java/PhotosPanel.java`; `probe5.json`.

- The controller snapshots `home.getStoredCameras()` at open time and **defaults the selection to all of them**; it subscribes to `Home.Property.STORED_CAMERAS` so the list stays fresh while the pane is open. Verified live: `getCameras()` returned the stored names and `getSelectedCameras()` defaulted to all. **[OBSERVED]** `probe5.json`.
- The pane is a checkbox list (each row a checkbox labelled with the camera name; click or SPACE toggles, single-selection model), a file-format combo (`PNG`, `JPEG` at quality 0.3 / 0.5 / 0.7 / 0.9), an overwrite confirmation, a progress label of the form `Computing %1$d / %2$d photos` and an end message `Photos created with success`. The start button is enabled only while at least one camera is selected. **[OBSERVED]** source + localization.
- Rendering uses a **clone** of the home; per camera it sets that camera active, then uses the photo renderer instance for the camera's `renderer` at quality `LOW`/`HIGH` when the quality level is ≥ 2, otherwise it grabs the 3D view's off-screen image. FISHEYE → square image; SPHERICAL → width × width/2 equirectangular. **[OBSERVED]** source.
- Output filenames are `<home name> - <camera name><extension>`, with `/ \ : ;` and the path separator replaced by `-`, so camera names double as filenames and are sanitized. **[OBSERVED]** source.

### D. Camera-path / video data model

**Storage.** The video path lives on the home **environment** as `videoCameraPath` (`List<Camera>`), not on the home itself, and is persisted as repeated `cameraPath` children inside `<environment>`. The same environment element also persists the video preferences: `videoWidth`, `videoAspectRatio`, `videoQuality`, `videoSpeed`, `videoFrameRate` (plus photo equivalents). Live defaults observed on the Studio demo: `videoWidth = 320`, `videoAspectRatio = RATIO_4_3`, `videoQuality = 0`, `videoFrameRate = 25`, `videoSpeed = 0.666666…`. The observed `Studio.sh3x` shipped those four but **no** `cameraPath` children, i.e. an unrecorded path is simply absent. **[OBSERVED]** `probe1.json`, `sh3x/Home.xml`, `src-java/HomeEnvironment.java`, `src-java/HomeXMLExporter.java`.

**What each path point holds.** The recorder takes the current camera, and if the pose differs from the previous point (pose comparison covers `x, y, z, yaw, pitch, fieldOfView, time`), it appends a `duplicate()` with a fresh id, **forces `lens = PINHOLE`** (path points are always plain perspective), and stamps the current time-of-day. Only the **first** recorded point also captures the renderer. So, for the video, the renderer is a property of the recording session inferred from its first keyframe, while every subsequent frame is a pinhole camera. Recording a pose identical to the previous one is skipped (the red button is idempotent at the same location). **[OBSERVED]** `src-java/VideoPanel.java`.

**No cap.** Unlike stored viewpoints, no maximum path length exists in the code paths examined; a live probe set a 5 000-point path and read back 5 000 with no truncation and no measurable cost (deep-copy semantics confirmed). **[OBSERVED]** `rea-out/probe12.json`.

**Path point classes.** A path recorded while the virtual visitor is active yields `ObserverCamera` instances (same class as stored viewpoints); a path recorded from the aerial camera yields top-camera instances. The 3D controller forces the view into observer mode before opening the video pane, so in practice a user-recorded path is observer-class. Lenses read back as `PINHOLE` (enum index 0) and names read back as empty (`null`) — path points are anonymous. **[OBSERVED]** `probe10.json`, `probe12.json`.

**Persistence.** On the web edition, homes are stored in **IndexedDB** rather than `localStorage` (the latter held only an unrelated `user_pseudo_id`), so the model survives reloads through the same XML/IndexedDB recorder the desktop app uses; the writer for the path lives on the shared XML exporter prototype and the parser restores `cameraPath` into the environment. **[OBSERVED]** `probe11.json`, bundle grep.

### E. Video UI and controls

**Pane.** "Create video" opens a **non-modal** dialog (explicitly non-modal so the user can still move the 3D camera between recordings). Top: a miniature plan on which the recorded path is drawn. Below it, the transport row, then the video-format combo, then the same quality slider / renderer / date-time fields as the photo pane. **[DOCUMENTED]** official help page `help-creatingVideos.html`; **[OBSERVED]** `src-java/VideoPanel.java`.

**Plan canvas.** The pane's plan paints the recorded path: a translucent (25 % alpha) polyline through all points, a filled circle per point (radius `7 / scale`), a field-of-view wedge per point (two rays at ±`fieldOfView/2`, drawn between 1.2× and 2.5× the radius), and 2-pixel connectors between consecutive points. It appends a synthetic `ObserverCamera` per path point to the painted-item list so the mini-plan's bounds expand to contain the path even when it leaves the home footprint. **[OBSERVED]** `src-java/VideoPanel.java`.

**Transport controls, in order.** Delete camera path | separator | skip-backward, seek-backward, **Record** (red), play/pause, seek-forward, skip-forward | separator | delete-last-record. Playback runs on a `Timer` at 1 000/12 ms (≈12 fps preview, independent of the chosen output frame rate) and drives the main 3D view; importantly, the preview **re-runs the very same keyframe→frame expansion with `frameRate = 12`**, so preview and render share one algorithm and the same movement speed. Seek moves 10 steps; skip repeats until the end. Playback is enabled only once the path has more than one point, and Create/Save only once the path is playable. **[OBSERVED]** `src-java/VideoPanel.java`.

**Tooltip / guidance.** The pane's tooltip is the workflow in one sentence: *"Move in the 3D view and click on the red button at the main locations where the camera should go by during the video. Then click on Create and Save to generate a video file from the path you drew."* **[OBSERVED]** localization table.

**Formats.** A fixed preset list of 15 JPEG video formats (resolution @ fps): 176×132@12, 320×240@25, 480×360@25, 640×480@25, 720×540@25, 1024×768@25, 1280×960@25, 720×405@25 (16:9), 1280×536@25 (2.40:1), 1280×720@25, 1920×800@25, 1920×1080@25, 3840×2160@25, 4096×1728@25, 7680×4320@25; the label format is `"%1$dx%2$d pixels - %3$s - %4$d frames/second"`. Choosing a preset sets width/height/frame-rate together (the aspect ratio then follows from width/height). **[OBSERVED]** `src-java/VideoPanel.java`.

**Advanced fields (quality ≥ 2 only).** A date spinner, a time spinner with a day/night icon (day when the sun elevation is above the horizon), a renderer combo populated from the installed renderers, and an "Add ceiling lights" checkbox that sets a fixed ceiling light colour or none. The quality slider spans levels 1..`getQualityLevelCount()` (4) and is described by `qualityN.jpg` illustrations plus per-level description text; if the host cannot produce off-screen images, the slider is forced to at least the third level. **[OBSERVED]** `src-java/VideoPanel.java`, localization.

**Quality semantics (four levels).** 0 = "Same rendering as in the 3D view"; 1 = real-time rendering plus shadows under floor-level furniture; 2 = "Fast global illumination ... (might take a long time to compute)"; 3 = "Global illumination ... (might take hours to compute)". The same four levels drive the still-photo pane. **[DOCUMENTED]** localization table; `help-creatingPhotos.html`.

### F. How video creation consumes the path (interpolation, timing, speed)

**Keyframe → frame expansion.** The recorded sparse path is expanded into a dense per-frame path by a pure function of `(speed, frameRate)`. For each *segment* between two consecutive recorded cameras, the code computes a per-frame budget from a global movement speed (m/s) and the target frame rate:

- a "move distance per frame" derived from `speed * 100 / frameRate` (converting m → cm),
- a "move angle per frame" derived from `speed / frameRate` (a yaw/pitch angular budget),
- an "elapsed time per frame" derived from `345600 / frameRate * 25`, i.e. it treats a full day as 250 frames at 25 fps (a 24 h pan compressed to 10 s of video),
- a segment frame count = `max(distance-steps, yaw-steps, pitch-steps, FOV-steps, time-steps)`,

then it emits that many frames with **linear deltas** on `x, y, z, yaw, pitch, fieldOfView` and a rounded per-frame `time` increment. Every emitted frame is forced to `lens = PINHOLE`. The result is a constant-speed, constant-turn, smoothly interpolated path in which *any* changing property (including the time of day) can drive the frame count — which is why a stationary camera with a changing hour produces a day-to-night timelapse. **[OBSERVED]** `src-java/VideoPanel.java` (`getVideoFramesPath`), `probe1.json`.

**Speed.** Speed is stored on the environment as `videoSpeed` in m/s and serialized as `videoSpeed`, defaulting to `2400/3600 ≈ 0.667 m/s` (≈ 2.4 km/h, a brisk walking pace); it is only written when it differs from that default. `VideoController` mirrors it as a `SPEED` property and writes it back to the environment; `getSpeed()` is the single source of truth used by both the render pipeline and the frame-count maths. **No user-facing speed control exists:** the complete `VideoPanel.*` key set in the shipped string table contains quality/size/format/date/time/renderer/ceiling-light labels and transport tooltips but **no** speed key, and the web build has no `getVideoSpeed` preference accessor either. The speed is therefore a per-home environment value that the current UI never exposes — a knob present in the model and in the file format but unreachable from the interface. **[OBSERVED]** `src-java/VideoController.java`, `src-java/HomeEnvironment.java`, `src-java/VideoPanel.java`, localization table (`VideoPanel.*` keys), `probe12.json`.

**Duration estimate.** Before rendering, the pane shows a start label of the form `"%1$d images to generate - Video duration: %2$s"`; during rendering it shows `"%1$d / %2$d - Estimated remaining time: %3$s"`. The frame count from the expansion above is therefore known up front and drives the estimate. **[OBSERVED]** localization + `src-java/VideoPanel.java`.

**Async, non-blocking compute.** Starting creation disables the editing controls, clones the home on a background executor, expands the path, sets the cloned home's active camera to the first frame, and only then begins generating frames. Stopping early prompts with *"The rendering process of the video isn't finished. Are you sure you want to stop it?"*; running out of memory raises the message "No more memory to complete". **[OBSERVED]** source.

**Renderer choice by quality.** For quality ≥ 2 the frames go through the low/high photo image generator; for quality 0/1 they go through the real-time 3D off-screen image generator and are only doubled/soft-shadowed at level 1. **[OBSERVED]** source.

### G. Export / output

- The computed frames are written to a **temporary QuickTime `.mov`** file through a `JPEGImagesToVideo`-style muxer fed by an image data source that renders each frame on demand; saving then copies/moves that temporary file to the user-chosen destination. The help page states output is a Quicktime file playable in tools such as VLC and translatable to other formats. **No audio track** is produced. **[OBSERVED]** `src-java/VideoPanel.java`; **[DOCUMENTED]** `help-creatingVideos.html`.
- The still-photo path saves PNG or JPEG at one of the four quality levels, using the same generators; batch "photos at points of view" reuses the naming rule described in C. **[OBSERVED]** source, localization.
- Both creation panes are deliberately **non-modal**, and their dialogs are made resizable and bounded in height for small screens. **[DOCUMENTED]** history (round-1 artifact).

### H. Web-edition status

The browser edition of Sweet Home 3D (same Java core transpiled to JS, ~2.6 MB minified bundle, version 7.5.2) **keeps the stored-viewpoint and camera-path model but has no working consumers**:

- Live: `preferences.getStoredCamerasMaxCount()` returns 50; stored cameras load as `ObserverCamera` with `observerCamera-<uuid>` ids; `storeCamera` inserts and de-duplicates exactly as on desktop; `goToCamera` reorders; `env.setVideoCameraPath` / `getVideoCameraPath` work; `Home.clone()` deep-clones the path. **[OBSERVED]** `probe1.json`–`probe4.json`, `probe12.json`.
- Live: the web `HomeController.createPhoto`, `.createPhotos` and `.createVideo` are **empty function bodies** (`function(){}`), and the view factory's `createVideoView`/`createPhotosView`/`createPhotoView` all return a shared `dummyDialogView` whose `displayView` does nothing. Firing `createVideo()`/`createPhotos()` therefore does **not** throw and produces no dialog; `createVideo()` still switches the view to the observer camera first. The browser build also contains **no** `VideoPanel`, `PhotosPanel`, `PhotoPanel`, `getVideoFramesPath`, `JPEGImagesToVideo`, `ImageDataSource`, `FrameGenerator`, `PhotoImageGenerator` or `Image3DGenerator`, and no `VideoFormat`/format-preset strings (so the 7680×4320 preset list does not exist there). **[OBSERVED]** `probe5.json`, `probe10.json`, bundle keyword counts.
- The German user guide is explicit: the online version has no menu bar, and all menu items are reachable via context menus or the toolbar **"mit Ausnahme des Imports von 3D-Modellen sowie der Erstellung von Fotos und Videos"** — except 3D-model import and photo/video creation. OBJ export is likewise absent online. **[DOCUMENTED]** `de-userguide.txt`.
- The web controller does expose the XML writer for the path (`writeCamera` on the home-exporter prototype, plus parse handling), so the data model round-trips even though nothing renders from it. **[OBSERVED]** bundle grep; `probe11.json`.
- A live attempt to drive the exporter with a hand-rolled writer failed on overload dispatch (`invalid overload at ... writeElement`), i.e. the web GWT-ish runtime requires a properly overloaded XML writer instance; the observed `writeCamera` overloads were resolved by name from the minified bundle. **[OBSERVED]** `probe11.json`, `probe13` attempt (browser died before returning).

### I. Data-model cheat sheet

| Concept | Where it lives | Fields | Serialization | Cap |
|---|---|---|---|---|
| Virtual visitor camera | `Home.observerCamera` | pose + fov + time + lens + renderer + `fixedSize`, fixed id | `<observerCamera attribute="observerCamera">` | – |
| Aerial camera | `Home.topCamera` | pose + fov + time + lens + renderer, fixed id | `<camera attribute="topCamera">` | – |
| Stored point of view | `Home.storedCameras` (ordered list) | pose + fov + time + lens + renderer + name + fresh id + free properties; class = class of the active camera when saved (observer or plain) | element named for the class (`observerCamera` or `camera`) with `attribute="storedCamera"`, inside home | **50**, oldest evicted, dedup by name or full pose |
| Video keyframe | `Home.environment.videoCameraPath` | pose + fov + time, lens forced PINHOLE, anonymous, fresh id, renderer on first point only | `cameraPath` element (named for the class) inside `<environment>` | **none found** (5 000 ok live) |
| Video preferences | `Home.environment` | `videoWidth`, `videoAspectRatio`, `videoQuality`, `videoSpeed` (m/s), `videoFrameRate` | attributes on `<environment>` | – |
| Active camera selector | `Home` root | `camera = observerCamera` or `topCamera` | root attribute | – |

Values verified live on the Studio demo: `videoWidth=320`, `videoAspectRatio=RATIO_4_3`, `videoQuality=0`, `videoFrameRate=25`, `videoSpeed=0.6667`, `camera` observed poses use `time=1491480000000` (2017-04-06 12:00 UTC), observer eye height ≈ 152.757 cm, fov ≈ 1.5708 rad.

## 3. Ideas for CasaPlazAI

CasaPlazAI's schema (`casaplazai-schema.md`, read-only) has `schemaVersion`, `units: "meters"`, `wallHeight/wallThickness`, `rooms[]`, `openings[]`, `furniture[]` and **no camera/viewpoint concept at all**. Stored viewpoints and camera paths are therefore a new, additive concern. The cheapest correct shape is a new optional top-level `viewpoints[]` plus a `cameraPaths[]` (or a `viewpoints[]` with an inline `path`), version-gated so v1 files still load — mirroring Sweet Home 3D's decision to put the camera path *inside the environment* (session/export state) while stored viewpoints live at home level. Ranked by value ÷ effort:

**Tier 1 — high value, low effort**

1. **Full camera snapshot as a "viewpoint" object.** *Ties to A, I.* Store `{id, name, position:{x,y,z}, yaw, pitch, fov, mode:"walk"|"orbit", timeOfDay, lens, version}` — not just a position — and restore **all** of it on recall. SH3D's `setCamera` copying only the pose (`A`) is exactly the bug class to avoid: a bookmark that forgets the lens or the time of day surprises users. *Effort: low. Value: high.*
2. **De-duplicate and cap by eviction, with a visible count.** *Ties to A, B.* Copy SH3D's semantics: a save whose pose matches an existing viewpoint renames/refreshes instead of growing the list; cap at a documented number (SH3D uses 50) and evict the oldest. The one improvement worth making: SH3D's eviction is silent — show "50 of 50 saved viewpoints; the oldest was removed" so the loss is visible. *Effort: low. Value: high.*
3. **"Create photos at points of view" as the batch-render analogue.** *Ties to C.* CasaPlazAI already exports PNG/JPEG from the 3D view; a checkbox list of saved viewpoints defaulting to *all selected*, one still per viewpoint into a `<plan name> - <viewpoint name>.png` file, reusing the same renderer, is a small feature that makes a viewpoint list immediately useful. Sanitize viewpoint names into filenames exactly as SH3D does (`/ \ : ;` → `-`). *Effort: low. Value: medium-high.*
4. **Viewpoint reordering by use.** *Ties to B.* SH3D moves the viewpoint you navigate to to the front so the "Go to" menu self-sorts by recency. Cheap, and it keeps long menus usable (SH3D also had to add up/down scroll arrows to a long "Go to" menu — do the scrolling in the menu from day one). *Effort: very low. Value: medium.*

**Tier 2 — high value, medium effort**

5. **Camera-path recording with a red-button keyframe model.** *Ties to D, E.* A dedicated Walk/Record mode: a red button appends a keyframe snapshot of the current camera (plus the time-of-day as an optional animated channel), a mini-map draws circles + FOV wedges + a connecting polyline so the path is legible, and a transport row offers preview playback / delete-last / clear. Force keyframe lens to plain perspective (SH3D forces PINHOLE) so interpolated frames are geometrically consistent. *Effort: medium. Value: high.*
6. **Keyframe → frame expansion as a pure, testable function.** *Ties to F.* The most reusable algorithmic insight here: derive the frames of each segment from a **step budget = max(distance-steps, yaw-steps, pitch-steps, fov-steps, time-steps)** with a global movement speed in m/s and a target frame rate, then linearly interpolate every channel. This makes the frame count — and the "N frames, estimated duration/remaining time" copy — computable *before* rendering, gives constant apparent speed regardless of segment length, and lets a stationary camera animate time-of-day (a 24 h sun study). CasaPlazAI already has a day/night lighting model, so the time channel is nearly free. *Effort: medium. Value: high.*
7. **Expose the movement speed in the UI.** *Ties to F.* SH3D stores `videoSpeed` per home (default ≈ 0.667 m/s ≈ 2.4 km/h) but has no visible slider, so users cannot tune walking pace without hand-editing; `VideoController.Property.SPEED` exists but nothing sets it. CasaPlazAI should surface a "walking speed" slider (m/s) in the video pane, persisted with the plan. *Effort: low-medium. Value: medium-high — a small fix for a real competitor rough edge.*
8. **Non-modal creation pane, background compute, honest time estimates.** *Ties to E, F.* Do the render in a worker/offscreen pass, keep the pane non-modal so the user can keep moving the camera between recordings, show `N frames · estimated duration`, a progress `i / N`, an estimated remaining time, and an explicit confirm when stopping early. *Effort: medium. Value: high.*
9. **Export video, not just frames.** *Ties to G.* SH3D muxes JPEG frames to QuickTime `.mov` with no audio; in a browser the natural equivalent is MediaRecorder/the WebCodecs `VideoEncoder` to WebM/MP4 (or a `.webm` blob), which avoids a server and keeps the no-backend architecture. Offer the same honest size/fps presets (SH3D ships 15, from 176×132@12 to 7680×4320@25; the 25 fps everywhere is a simplifying choice CasaPlazAI can copy or improve). *Effort: medium-high. Value: high.*

**Tier 3 — valuable, higher effort**

10. **Lens presets that also constrain aspect ratio.** *Ties to A.* Plain perspective / depth-of-field / fisheye (square) / spherical (2:1 equirectangular) map cleanly onto a Three.js `PerspectiveCamera` plus a cube/equirect render; copy SH3D's hard aspect constraints for fisheye and spherical so exports never come out distorted. Spherical/2:1 output feeds VR viewers and 360° embeds. *Effort: medium-high. Value: medium.*
11. **Path as first-class scene objects.** *Ties to D.* SH3D includes top camera, observer camera, stored viewpoints **and** path cameras in `getHomeObjects()` and deep-clones the path on `Home.clone()`. CasaPlazAI should keep path keyframes as immutable snapshots (structurally cloned on save) so repeated rendering never mutates the plan, and so undo/share can reason about them. *Effort: medium. Value: medium.*
12. **Schema-versioned viewpoints.** *Ties to I.* Because `schemaVersion` is a single integer and the editor already keeps some out-of-schema state (snap settings, annotations, underlay) and share links omit such state by construction, decide up front: are viewpoints part of the shared plan (schema v2, additive) or local editor state (like snap settings)? Videos and photos are personal, but viewpoints that describe the home are plausibly shareable; SH3D persists them in the file, so file-level is the safer default, with share links opting in. *Effort: low to decide, medium to implement. Value: cross-cutting.*

**Explicit anti-patterns to avoid (learned from SH3D's rough edges)**

- **Don't ship a visible action whose dialog is a stub.** SH3D's web build keeps `CREATE_PHOTO`/`CREATE_PHOTOS_AT_POINTS_OF_VIEW`/`CREATE_VIDEO` wired to empty functions and a dummy dialog, so the buttons silently do nothing (`probe10.json`); round 1 even got a wedged modal trying it. Hide or disable unsupported actions.
- **Don't silently drop a stored viewpoint at the cap.** 50 is fine as a limit; silent eviction is not. Tell the user.
- **Don't store a viewpoint without its lens, time and renderer.** A "bookmark" that restores only the pose surprises users (SH3D's `setCamera` copies only the pose, so the surrounding code has to remember the rest).
- **Don't leave the walking speed invisible.** A stored-but-unexposed `videoSpeed` is a knob users cannot find.

## 4. Unknowns

1. **Live rendering of the video/photo panes.** They are Swing dialogs in the desktop build; I read their exact behaviour from the GPL source, the shipped localization table and the official help pages, but never saw the desktop panes render. Pane *layout* (exact ordering of quality/size/lens/renderer/date/time) is therefore assembled from source and string names.
2. **Real render times and the actual `.mov` output.** "Minutes to hours" is a vendor/UI statement; I did not render a video on desktop or web, and did not inspect a produced `.mov`, so the container/codec details come from source and help rather than from a file.
3. **Whether a user-recorded path ever contains camera classes other than `ObserverCamera`.** The recorder duplicates whatever camera is active and the 3D controller forces observer mode before opening the pane, so I could not produce a real top-camera path through the UI; I could only construct one programmatically (probe12), which the model accepted. (By contrast, a *stored viewpoint* from the aerial side is confirmed to be a non-observer camera in `probe4.json`.)
4. **The `1280×536` "2.40:1" preset vs the `RATIO_2_1` enum.** Two different ratios exist in the model and UI; I did not confirm how the 2.40:1 preset is represented internally when re-loaded (it may be derived from width/height rather than stored as an enum).
5. **The `videoSpeed` UI claim.** I found `VideoController.Property.SPEED` and `setSpeed`/`getSpeed`, and confirmed no speed slider/setting string in the bundle, but I could not construct a live `VideoController` in the web build (its preferences lack `getPhotoRenderer`), so I did not observe the desktop pane's full control list to be 100 % sure there is no speed control in some version.
6. **Web persistence of stored viewpoints / paths across a real reload.** The recorder writes XML and the web app stores homes in IndexedDB, and the parser restores `storedCamera`/`cameraPath`; but the browser died before I could complete a save → reload → read round-trip, so the end-to-end persistence on the web edition is inferred from parser/writer code, not observed as a full cycle.
7. **Exact XML writer output.** A live attempt to capture the exporter's XML for the camera path failed on the web runtime's overload dispatch (needs a properly overloaded XML writer instance), so the `cameraPath` element shape is read from the GPL exporter source and the shipped parser, not captured as a real fragment (the round-1 `Studio.sh3x`, which had no path, was observed directly).
8. **Behaviour when the browser build has no WebGL context.** Round 1 already noted headless Chromium often lacked a usable context; I did not characterise whether stored viewpoints/`goToCamera` still function without a renderer.
9. **`ObserverCamera` fixed-size (`fixedSize`) semantics.** The observer camera serializes a `fixedSize` flag; how it interacts with navigation/clamping was not probed.
10. **Whether a share-link (viewer `camera`/`selectableCameras` parameters) can preselect a stored viewpoint on load.** History mentions viewer parameters for `camera`/`selectableCameras`/`level`; I did not test the viewer page, so the URL-driven viewpoint selection is documented-but-unobserved.
