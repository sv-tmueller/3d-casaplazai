## 1. Summary (5 bullets)

- **The app does fully load headless with software WebGL.** With `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`, the live 3D canvas reports `WebGL 1.0 (OpenGL ES 2.0 Chromium)` and unmasked renderer `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (LLVM 10.0.0) (0x0000C0DE)), SwiftShader driver)`; the patched GL counters recorded **12 820 `drawArrays`, 154 `clear`, 4 shaders, 2 programs, 2 `texImage2D`, 0 GL errors** for the Studio demo. **OBSERVED** — `evidence/pw-observe.json`, `evidence/pw-probe2.json`
- **The cause of Round 1's unfinished Playwright observation is Playwright's `serviceWorkers: 'block'`.** Round 1's `tools/observe-online.js` set exactly that; the page calls `navigator.serviceWorker.register('/resourceCache.js')` then, if `!navigator.serviceWorker.controller`, immediately `window.location.reload()`. With the worker blocked the controller is never set, so the page reloads forever (I measured 264 navigations and no `#demo-choice a`, which is precisely why that script "did not complete"). With `serviceWorkers: 'allow'` the page loads in **2 navigations**, and the full editor then loads too. **OBSERVED** — `evidence/observe-run1.log` (loop), `evidence/observe-run2.log`, `evidence/diag3-sw-allow.log`, and Round 1's own `tools/observe-online.js`
- **Opening the Studio demo fetches 294 unique model assets and renders both views.** 730 network responses in the first session; 555 of them under `/models/` — **261 PNGs fetched twice each** (once as an `<img>` thumbnail, once as XHR) plus 33 ZIP model archives, i.e. 294 unique files. Behind `/models/` sit many contributor namespaces (`scopia` 88, `contributions` 58, `reallusion` 24, `lucapresidente` 15, `blendswap-cc-by` 11, `katorlegaz` 10, `blendswap-cc-0` 17, …). Catalogs are `FurnitureCatalog.json` (**805 pieces / 12 categories**) and `TexturesCatalog.json` (**389 / 9**). **OBSERVED** — `evidence/pw-observe.json`, `evidence/pw-probe4.json`
- **Storage stays tiny and contains no app data for the anonymous demo.** `localStorage` = only `user_pseudo_id`; `sessionStorage` = `first_visit_logged`, `ip_address`; IndexedDB = only Firebase `firebase-heartbeat-database` and `firebase-installations-database`; Cache Storage empty (the resource service worker never populated it in this run). No `SweetHome3DJS` / `Recovery` object store appeared even after a model edit and a 75 s wait, consistent with Round 1's inference that the anonymous demo has no server recorder and that auto-recovery only engages for **modified, saved** homes. **OBSERVED** — `evidence/pw-observe.json`, `evidence/pw-probe3.json`, `evidence/pw-probe5.json`
- **`window.application` is reachable and introspectable without any patching**, and it exposes the real Studio model (16 walls, 5 rooms, 48 furniture, 8 dimension lines, 1 label, 5 doors/windows, wall height 250 cm), a complete preferences object, and a **3-level demo home** with a live level selector (Basement −150 / 1st floor 112 / Roof 374). Also confirmed by REA's own storage probe of the same origin: `usage_bytes: 13975`, `quota_bytes: 596766093312`, `local_storage_keys: ["user_pseudo_id"]`, `session_storage_keys: ["first_visit_logged","ip_address"]`, `indexed_db_names: ["firebase-heartbeat-database","firebase-installations-database"]`, `cache_names: []`. **OBSERVED** — `evidence/rea-inspect-live.json`, `evidence/rea-inspect-editor.json`

**This is now directly explained, not inferred.** Reading `window.application.configuration` live shows the *entire* anonymous configuration is exactly five keys — `furnitureCatalogURLs: ["/libjs/resources/FurnitureCatalog.json"]`, `furnitureResourcesURLBase: "/models/"`, `texturesCatalogURLs: ["/libjs/resources/TexturesCatalog.json"]`, `texturesResourcesURLBase: "/textures/"`, `userLanguage: "en"`. There is **no** `autoRecovery`, no `readHomeURL`, no `writeHomeURL`, no `writeHomeEditsURL`. Correspondingly `application.autoRecoveryManager` is **false/absent** (never constructed), and `getHomeRecorder()` returns a plain `HomeRecorder` (constructor name observed) whose `hasEdits` is `undefined` (the bundle defines `hasEdits` only on `IncrementalHomeRecorder`). So the page's own `beforeunload` guard is inert for an anonymous demo design. **OBSERVED** — `evidence/pw-probe5.json`

Two further nuances observed in the same run: (a) `application`'s own properties are **lazily populated** — before a home is opened it exposes only `homes`, `homesChangeSupport`, `homeControllers`, `configuration`, and only after the demo loads do `homeRecorder`, `preferences` and `viewFactory` appear; (b) mutating `wall.setThickness()` directly did **not** set `home.isModified()` (`false` before and after) and did **not** make `undoManager.canUndo()` true — a model write only becomes an "edit" when it goes through the app's controller/undo pipeline. **OBSERVED** — `evidence/pw-probe5.json`

**Preferences are also not persisted.** Setting `setGridVisible(false)`, `setMagnetismEnabled(false)` and `setNewWallThickness(12)` changed the live values immediately, but `localStorage` still contained only `user_pseudo_id` afterwards — the anonymous demo keeps preferences in memory for the session only. **OBSERVED** — `evidence/pw-probe9.json`

The nine demo entries are real `viewHome("/examples/<Name>.sh3x")` handlers on the chooser, in this order: Empty home, Studio, 1-Bedroom apartment, 2-Bedroom apartment, 3-Bedroom apartment, Apartment with bow window, 2-Bedroom house with basement, 3-Bedroom house with attic, 3-Bedroom house with mezzanine. Each non-empty one also fires `fbEvent(event,"wce_onlinetool_select demo")`. **OBSERVED** — `evidence/pw-probe9.json`

**This matches the vendor's own copy.** Selecting the empty home raises the literal alert *"Keep in mind that your design won't be saved! If you want to save it, go first to Online page and register for free."*, and both the page FAQ and the German manual state that saving requires a free account and that the browser edition requires WebGL. **DOCUMENTED** — vendor page `https://www.sweethome3d.com/SweetHome3DJSOnline.jsp` and German manual `https://www.sweethome3d.com/de/`, read-only copies in the Round-1 folder (`SweetHome3DJSOnline.jsp.html`, `manual_de.html`)

### 2.9 Reusable method notes (for future rounds)

- The **only** launch configuration that reaches the editor headless is: full Chrome-for-Testing binary + `serviceWorkers: 'allow'` + `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`. `chrome-headless-shell` was not required.
- `rea capture-browser-scenario` rejected `browser.launch_arguments` and `browser.args` as `unknown_argument`; its accepted schema (from Round 1's own scenario JSON) has `browser.mode/headless/executable_path`, `environment.service_workers`, actions `goto|wait_for|click|wait_for_timeout`. A `wait_for` step on `#demo-choice a` followed by a CSS `:has-text("Studio")` click is the working pattern; role-locators were unreliable in Round 1 and were not needed.
- Synthetic `element.click()` inside `page.evaluate`, plus the page's **own global helpers** (`window.viewHome('/examples/Studio.sh3x')`), worked reliably; this is the "prefer calling the page's own exposed JS APIs" lesson from the task brief.
- `rea inspect-web-page` needs `--allowed-origins` as a **bare origin** (`https://www.sweethome3d.com`), not a JSON array with a path; a JSON array of one bare origin is also accepted, an origin with a path is rejected with `invalid_value`.

## 3. Ideas for CasaPlazAI (ranked by value/effort)

Ranking: **V** = value for the current single-workspace redesign (1–5), **E** = implementation effort (1 = trivial, 5 = large). Score = V − E. Each idea is tied to a finding above and, where relevant, to the two schemas: `~/dsh-workspaces/rea2-shared/casaplazai-schema.md` (read-only) and the Round-1 competitor notes.

| # | Idea | Tied to finding | CasaPlazAI schema touchpoint | V | E |
|---|---|---|---|---|---|
| 1 | **Never block first paint on a worker/registration reload.** Sweet Home 3D's own loader reloads the whole page once when a service worker is not yet controlling; behind a blocking environment that becomes an infinite loop. If CasaPlazAI ever adds a service worker for offline assets, make the registration non-blocking (no `location.reload()` gate; apply SW only on a later visit) and add a reload guard (max one reload per session, `sessionStorage` flag). | §2.2 | n/a (app boot) | 4 | 1 |
| 2 | **Expose a single, documented runtime root (`window.app`) with read APIs** for the plan state (`getWalls/getRooms/getFurniture/getLevels` shape). The competitor's `window.application` made this whole round possible; CasaPlazAI gets free automation, bug-report dumps and e2e assertions from one typed facade behind a dev flag. | §2.5 | `Plan` aggregate accessors | 5 | 2 |
| 3 | **Store a per-room label offset and area-visibility flag, and derive area from the polygon.** The live Studio home keeps `nameXOffset/nameYOffset` per room (where the user dragged the label) and `areaVisible`, alongside `floorColor`; area is computed geometry (`Bathroom 42971.66 cm²`). CasaPlazAI's `Room` already has `name` + `polygon`; `labelOffset` and `areaVisible` are additive, and area stays derived (never stored) exactly as the schema already treats derived facts. | §2.6 | `Room` (additive fields) | 5 | 1 |

| 9 | **Lazy-load 3D model assets keyed by catalog id — and dedupe the palette-thumbnail path against the model-load path.** Observed behaviour: 294 unique assets produced 555 responses because all 261 PNGs were fetched twice (as `<img>` *and* as XHR). CasaPlazAI's schema has no model refs today; if it grows them, fetch on first placement, cache by id, and serve the palette thumbnail from the same cache entry as the 3D icon so bytes are pulled once. | 10 | **Surface the undo state in words** (`Can't Undo` → `Undo Delete level`) by naming each command. | 11 | **Keep the 2D plan at device-pixel-ratio ×2** (`HIDPI_SCALE_FACTOR = 2`: a 1296 css-px pane produced a 2592-px canvas) and revalidate on resize. Cheap, and it is the difference between crisp and blurry dimension lines. | §2.1 | render layer | 4 | 1 |

## 4. Unknowns

1. **Auto-recovery was not observed to fire, and its trigger is now precisely bounded.** No `SweetHome3DJS` / `Recovery` IndexedDB store appeared even after a model edit and a 75 s wait, although `getAutoSaveDelayForRecovery()` is 60000 ms in live preferences. The live configuration contains no `autoRecovery` key and `application.autoRecoveryManager` is absent; the bundle gates `AutoRecoveryManager` on `configuration.autoRecovery && configuration.writeHomeEditsURL === undefined`. Whether a *registered* (logged-in) session sets `autoRecovery` and creates that store was not observed (no account was created, by rule). **UNRESOLVED (out of scope by rule)**
2. **The service worker cache was never populated.** Registration succeeded and `navigator.serviceWorker.controller` became true, but `caches.keys()` stayed empty across several minutes and many `/models/` fetches. Whether `/online/readResource.jsp` is in use at all on this new page, and which URLs `resourceCache.js` is meant to cache, remains read-from-source only (Round 1 unknowns #6). **PARTIAL**
3. **`hasEdits` never existed on the anonymous recorder**, so the page's `beforeunload` guard is inert here. The exact condition under which the page would warn a user about unsaved work (only after a server recorder is configured) is inferred from bundle text, not observed. **PARTIAL**
4. **No exact per-demo asset manifest.** I recorded counts and samples per demo load (first Studio open: 91 `/models/` responses; `2BedroomHouseWithBasement.sh3x`: 86; a third switch back to Studio: 31) but did not persist the full deduplicated per-home asset list, nor which assets are shared vs unique between demos. Note that the 31 responses captured on the third switch included mezzanine/loft-bed assets, so the slice is contaminated by the model loader still fetching for the previous home; the per-demo manifest is therefore genuinely unresolved. A follow-up could dump the model cache keys after each load.
5. **Texture fetch and rendering were not exercised end-to-end.** The `TexturesCatalog.json` loads (389 entries, verified live) and a texture can be attached to a room in the model, but assigning one raised `RangeError: Maximum call stack size exceeded` in the transpiled render path under SwiftShader and produced **zero** `/textures/` requests. Whether that is a genuine product bug, a software-GL-specific edge case, or an artefact of my programmatic call (bypassing the normal texture dialog and repaint scheduling) is undetermined. All nine demo homes appear to use colours rather than textures, so a texture pipeline claim cannot be made. **UNRESOLVED**
6. **The 3D walkthrough was driven only through the API, not as a user.** `viewFromObserver()` was called and the draw-call counter rose, but I could not read the numeric observer camera x/y/z/yaw/pitch (the state object's getters did not expose them in the transpiled build and it serialises circularly), and I did not press the mouse handlers to walk. The interior-view *rendering* is therefore proven alive, its exact camera state is not.
7. **Interaction-level behaviour (draw, snap, drag, collision) was not exercised.** This round targeted load/network/storage/JS state only; the editor was opened and read, plus one API-level wall-thickness change and camera moves.
8. **`rea capture-browser-scenario` was not completed with the working configuration.** Its schema rejected `browser.launch_arguments` and `browser.args` as `unknown_argument`, so the SwiftShader flags could not be supplied through it; REA-native scenario evidence for the *editor* is therefore limited to `inspect-web-page` (which did succeed on a manually launched SwiftShader Chrome). Round 1's scenario JSON remains a valid template, and its `environment.service_workers: "allow"` is exactly the setting that avoids the reload loop.
9. **The model-loader cache could not be introspected by name.** The minified build erases class names inside the model-loading layer, so a recursive scan of `window` found no `ModelManager`-named object; the de-duplication claim (33 ZIP downloads for 48 furniture instances sharing 33 catalog ids) rests on the network trace, not on reading the cache object itself.
10. **Licence boundary unchanged from Round 1.** Sweet Home 3D is GPL-2.0-or-later; everything here describes behaviour, data shapes and UX in my own words. No source code was copied into this report or into any CasaPlazAI-facing artefact.
