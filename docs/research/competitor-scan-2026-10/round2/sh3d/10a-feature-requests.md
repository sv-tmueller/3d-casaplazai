# Sweet Home 3D — Top 50 open feature requests (SourceForge tracker) ranked by votes & comments, grouped by theme

Round 2, narrow question for **CasaPlazAI** (single-page web 2D/3D floorplanner, TypeScript/Three.js, no backend, localStorage autosave, 0.5 m grid snap, shared walls, seven furniture types, roofs via per-segment `leanDeg`).
Competitor: **Sweet Home 3D** (GPL Java desktop + JS browser edition built from the same core).
Round-1 report reused read-only: `rea-sweethome3d-2026-10/10-10-community-plugins-feedback/report.md`.

**Evidence tags:** `OBSERVED` = seen directly in a page/JSON captured in this folder (evidence file named); `DOCUMENTED` = vendor docs; `INFERRED` = my analysis.
**Read-only folder notice:** nothing under `rea-sweethome3d-2026-10/…` was modified. Round-1 evidence is cited where reused.

## 1. Summary

- **The tracker is long-tail, not vote-driven.** 1,230 of the 1,255 FR tickets were captured with their `votes_up`/`votes_down`, status and dates (this folder: `raw/fr_all_tickets.json`). Only **21 %** (261) carry ≥1 vote, only **21** carry ≥5, and the maximum is **12** votes on a 2013 ticket. The "top 50 by votes" therefore ends in a **43-ticket tie at 2 votes**, so ranks 47–50 are statistically indistinguishable from hundreds of others. `OBSERVED`
- **Discussion activity is a better signal than votes, and it points elsewhere.** Across the **176 voted tickets** whose comment threads I successfully pulled (447 posts), the most-discussed items are a hi-DPI bug thread (#727, 20 comments), 3D‑mouse support (#281, 19), GitHub migration (#572, 14), online import (#248, 13) and a 1-vote dimensioning ticket (#1003, 9) — while per-ticket discussion inside the top-50 open set is only **123 comments total**, with 10 of the 50 tickets having no discussion at all. `OBSERVED` (`raw/thread_posts.json`)
- **Theme mix (top 50 open, one theme per ticket by my classification; vote masses sum to the 221 top-50 total):** rendering & 3D view **36 votes/7 tickets**; parametric shell (roof, stair, terrain) **32 v/5**; dimensions & quantities **31 v/7**; walls/rooms/snapping geometry **29 v/8**; export/print/2‑D output **28 v/6**; levels/layers/visibility/catalog **26 v/7**; electrical/plumbing/networks **20 v/5**; editor ergonomics & meta **19 v/5**. No single theme dominates; the top 10 items alone span six different themes. `OBSERVED` + `INFERRED` (`raw/top50_open_enriched.json`, `raw/top50_open_table.md`)
- **Every top-voted item is a request the maintainer has declined, deferred, or worked around.** Grid/cursor snapping (#407) was explicitly refused — *"Sorry I don't believe in the use of snapping to the grid or to a value… walls have almost never round values"* — layers (#158, #956) were closed as *"implemented as levels at the same elevation… don't hope for another solution"*, and roofs/stairs have been answered with *"try the plug-in"*. This confirms round 1's plugin-ecosystem finding from the *outside*: the highest-demand core features live outside the core. `OBSERVED` (`raw/threads/t_407.md`, `raw/threads/t_158.md`, `raw/threads/t_956.md`, `raw/threads/t_466.md`, `raw/threads/t_618.md`)
- **What actually matters for CasaPlazAI is the *middle* of the list, not the podium.** Requests 3–20 are almost entirely editing ergonomics a web SPA already has or can get cheaply — dimension feedback while drawing, wall-alignment reference edge, group locking, per-object visibility, print/scaled output, list organisation. The only genuinely expensive missing simulators are terrain (#511) and a stairs generator (#618, #997); sloped/height-varying walls (#74, #83) are the third and are already partly modelled by `wallsOverride`. `OBSERVED` + `INFERRED`

## 2. Findings

### 2.1 Method, data and caveats

SourceForge's project pages are behind Cloudflare for plain `curl` (HTTP 403) and its HTML/`search_feed` endpoints return the challenge page. Working path found in this job: **the Allura REST API through the `r.jina.ai` text proxy**, which returns the JSON body inline. Key endpoints and evidence files:

| Purpose | Endpoint | Evidence |
|---|---|---|
| All tickets with votes/status/dates | `https://sourceforge.net/rest/p/sweethome3d/feature-requests/search/?q=*:*&limit=300&page=N&sort=-votes_up` (5 pages) | `raw/jina_search_p0..p4.md` → merged `raw/fr_all_tickets.json` (1,230 tickets) |
| Vote-ordered HTML (cross-check) | `…/feature-requests/?sort=votes+desc&limit=250&page=N` | `raw/jina_votes250_p0..p3.md`, `raw/fr_votes_ranked.json` |
| Per-ticket detail (description, votes, thread URL) | `…/rest/p/sweethome3d/feature-requests/<num>` | `raw/tickets/tk_<num>.md` → `raw/top_descriptions.json` (53 tickets) |
| Comment threads | `…/rest/p/sweethome3d/feature-requests/_discuss/thread/<id>/` | `raw/threads/t_<num>.md` → `raw/thread_posts.json` (176 voted tickets, 447 posts) |
| Tracker statistics | `…/feature-requests/stats/` | **1,255 tickets / 756 open / 499 closed / 2,313 comments total** |

Caveats, all `OBSERVED`:
- **My REST sample is 1,230 tickets, not the 1,255 the stats page reports (98 %).** The API's own `count` returned 1,238–1,244 across pages (it drifts between requests), and page boundaries overlap slightly; uniqueness was enforced by ticket number. Counts are as-of **2026-10-31** and are a lower bound by ≤2 %. `OBSERVED` (`raw/stats.md`)
- **Votes are snapshot values.** `votes_up`/`votes_down` were read once. Only 9 tickets have any down-vote (max 1), so `votes_up` is an effective score.
- **The tracker is effectively dormant.** The stats page reports **0 new tickets and 0 new comments in the last 7 days**, 1 ticket in 14 days, 1 in 30 days. The newest ticket (#1281) is 2026-10-21. Vote signals are historical, not live demand.
- **"Top 50 by votes" is not a stable set.** 225 open tickets have ≥1 vote; the 46 open tickets at ≥3 votes are the defensible "top"; ranks 47–50 are arbitrary members of a 43-ticket tie at 2 votes (tie-broken by ticket number). Rows 1–46 of the table in §2.2 are therefore exactly the ≥3-vote subset, and all 225 ≥1-vote tickets are in `raw/fr_all_tickets.json` for re-cutting.
- **Comment counts are per-thread `posts` arrays**, which include the maintainer's own status-change meta-posts (e.g. `- **status**: open --> closed`) and are capped at 25 posts/page. No thread among the top 50 exceeded the 25-post page, so counts are complete for this set.
- Labels exist but are nearly useless: 287 tickets are tagged **"Other features"** and 195 **"Interface Improvements"**; 300 distinct labels exist mostly as one-offs. My themes are therefore hand-assigned from summary + description + thread, and a ticket can belong to more than one theme. `OBSERVED` (`raw/fr_all_tickets.json`)

### 2.4 Themes

Eight themes, with counts, vote mass and representative tickets. In this classification each of the 50 tickets belongs to **exactly one** theme, so ticket counts sum to 50 and votes to the top-50 total of 221 (comments to 123). Alternative cuts are possible — several tickets, e.g. #407 (snapping) or #609 (sticky dimensions), sit on a boundary — and the exact assignment is in `raw/top50_open_enriched.json`.

**A — Rendering, 3D view, performance, VR** (7 tickets, 36 votes, 15 comments). #593 GPU rendering (12), #856 pan in 3D aerial view (8), #624 Oculus Rift (5), #371 GPU (3), #569 render walls+lights (3), #936 nvidia RTX (3), #204 disable 3D preview (2).
The maintainer's position is on record: the render engines are external JNI code and SunFlow is Java; a commenter who tried to port SunFlow to Aparapi found it *"too complex"* and proposed a RIB/Renderman export instead. This is a desktop-Java architectural dead end — in a Three.js app, GPU rendering *is* the renderer. `OBSERVED` (`raw/threads/t_593.md`, `raw/threads/t_856.md`, `raw/threads/t_569.md`, `raw/threads/t_204.md`)

**B — Walls, rooms & snapping geometry** (8 tickets, 29 votes, 24 comments). #750 draw wall by known dimensions + outside/inside reference (8), #407 cursor/wall snap (4), #832 room auto-update when a wall moves (4), #846 basement/fence walls (3), #919 clockwise wall creation + better snap (3), #1130 wall reference edge (3), #74 sloped-wall angle (2), #83 sloped walls (2).
This is the most *argued* cluster and the most important one for CasaPlazAI. Recurring, verbatim themes:
- The maintainer **rejects fixed-grid snapping on principle**: *"Sorry I don't believe in the use of snapping to the grid or to a value. Have a look to real plans and you'll see that walls have almost never round values."* Users push back: *"This issue is not just about snapping to a grid but snapping wall ends to each other. Perhaps a quarter to half my time using sh3d is spent trying to get walls to line up precisely with each other. It's a huge time waster."* `OBSERVED` (`raw/threads/t_407.md`)
- **Wall thickness vs blueprint alignment is a structural ambiguity with no good fix**: *"I drew a room (which I measured from inside) and created walls by double-clicking… Then I changed the wall thickness to 80 cm (old stone building)… I need to remember to take the wall thickness from the total width or height"* (#750). #1130 offers a community patch to choose left/middle/right wall alignment — never merged. `OBSERVED` (`raw/threads/t_750.md`, `raw/threads/t_1130.md`)
- **Rooms do not follow walls**: users must delete and redraw a room after moving a wall (#832, 0 comments — nobody disagreed).
- Sloped walls can only be authored by *angle*, not by start/end heights: *"In real life, people may know the height of the wall, not the angle"* (#74). `OBSERVED`

**C — Dimensions, measurement & quantities** (7 tickets, 31 votes, 11 comments). #232 show room dimensions (7), #538 material volume & cost (6), #609 "super sticky" dimensions that stay attached (6), #615 show/hide dimensions toggle (3), #647 interior vs exterior dimensions (3), #736 perimeter of rooms (3), #819 automatic dimension text on export (3).
The through-line is **dimensions that persist and describe geometry** rather than free-standing annotation: sticky/attached dimensions, live readout of *which* dimension (inner/outer/centre-line) is being dragged, per-room perimeter, and automatic dimensioning of all walls for print/blueprint export. #615's complaint is the classic: deleting dimensions to work and re-creating them to print. `OBSERVED` (`raw/threads/t_232.md`, `raw/threads/t_615.md`, `raw/threads/t_647.md`, `raw/threads/t_609.md`, `raw/threads/t_736.md`, `raw/threads/t_819.md`)

**D — Electrical, plumbing & networks (MEP)** (5 tickets, 20 votes, 9 comments). #274 electrical installation (5), #835 energy networks (5), #328 electrical components in 2D (4), #421 service-network plug-in (3), #1070 pipe/electrical routing (3).
Users want **wall-mounted symbols with elevation** — sockets, switches, lights — with wiring runs, cable lengths and per-circuit relationships. The maintainer's answer has been to point at plug-ins (the Wirings plug-in, #41) and at the Wall Socket Plugin (#69 in round 1). Notably MEP is *5 of the top 50* — small in votes but persistent since 2009, and structurally absent from a residential floorplanner. `OBSERVED` (`raw/threads/t_274.md`, `raw/threads/t_421.md`, `raw/threads/t_1070.md`) + round-1 §2.1 (`rea-sweethome3d-2026-10/10-10-community-plugins-feedback/raw/sf_plugins_*.json`)

**E — Parametric shell & site (roofs, stairs, terrain)** (5 tickets, 32 votes, 20 comments). #511 terrain editor (10), #618 simple stairs generator (7), #466 easy roofing (6), #864 automatic roofing (6), #997 stairs (3).
This is the highest vote-mass-per-ticket cluster. Evidence of demand:
- **Roofs**: #864 (opened 2018, 6 votes) is the strongest statement — *"only one feature is missing for the program to become complete and perfect: automatic roofing… It is almost impossible to create a nice looking roof through furniture objects."* The maintainer's answer to the older #466: *"the creation of roofs isn't supported yet and the tutorial you mention is some kind of workaround written by a super user… should come in a future version."* The thread then enumerates the wanted taxonomy verbatim: *"There should be a choice: a flat roof, a gable roof, an envelope roof, a multi-pitched roof."* `OBSERVED` (`raw/threads/t_864.md`, `raw/threads/t_466.md`)
- **Terrain**: *"When building houses on a sloped terrain, it should be possible to edit a mesh following the profile of the terrain"* (#511); maintainer points to the Terrain Generator plug-in, and a user replies it is *"cumbersome to use"*. `OBSERVED` (`raw/threads/t_511.md`)
- **Stairs**: *"Stairs are treated like furniture, but it enormous variety doesn't match this, and deforming them according a pretended design isn't very elegant"* (#618); the official answer is the Staircase generator plug-in and the Multiplier plug-in, both forum links. The JS bundle has no stair generator. `OBSERVED` (`raw/threads/t_618.md`)

**F — Organisation: levels, layers, visibility, locking, catalog** (7 tickets, 26 votes, 13 comments). #666 visible checkbox for walls (5), #824 dark mode (5), #972 groupable levels (5), #565 furniture folders (4), #630 furniture folders/sub-folders (3), #726 extra view options incl. hide/lock (3), #878 per-level locks (3).
Two long-running battles:
- **Layers**, rejected four times: *"I don't think there will be any other layer system in Sweet Home 3D because it's a too complicated feature"* (2009, #158) → *"Version 3.4 brought levels that can be used as layers in a way"* → *"Version 5.0 brought the ability to change the viewability of a level"* → *"Layers are implemented as levels at the same elevation… don't hope for another solution"* (#956, 2020). The most articulate objection is from `tylla`: levels and layers are *"orthogonal"*. `OBSERVED` (`raw/threads/t_158.md`, `raw/threads/t_956.md`)
- **Workarounds-as-features**: the community's standard recipe for hiding a class of objects is to put them on a *separate level at the same elevation* and toggle it (#666, #726, #754, #615 all show this advice, sometimes from the maintainer). #878 shows the consequence at scale: *"the level management when you have 50 levels becomes crazy… at least preventing the reordering… would help not to get lost"*. #972: *"eventually finding up to 80 levels per project."* `OBSERVED`
- Catalog organisation remains unresolved: no folders/sub-folders; the workaround in #630 is *"you can add your own categories (simply by typing the new category name)"* plus searchable tags via the FurnitureLibraryEditor. `OBSERVED` (`raw/threads/t_630.md`)

**G — Export, print & 2D output** (6 tickets, 28 votes, 11 comments). #446 export a "pure" floor plan: walls/doors/windows only (7), #607 print to PDF all levels (6), #617 set print area (5), #716 2D sections and elevations (4), #450 façade/section plans (3), #754 hide all furniture on print (3).
The unifying need is **plan-as-drawing, not plan-as-scene**: strip furniture, choose scale and area, batch all levels, and generate architect-style sections/elevations. Workarounds in evidence: toggle object visibility by hand before printing (#446: *"the current workaround of toggling the visibility of the unwanted objects before printing is cumbersome"*), move unwanted items to a hidden same-elevation level (the maintainer's own recipe in #754), or *"make a backup, clear everything other than the base objects and print it"* (#726) — and a community member even shipped a *"Hide furniture"* Tool-menu plug-in to automate it (#754). #607 was partly answered in 7.2 (page setup can pick levels). `OBSERVED` (`raw/threads/t_446.md`, `raw/threads/t_607.md`, `raw/threads/t_726.md`, `raw/threads/t_754.md`, `raw/threads/t_617.md`)

**H — Editor ergonomics, preferences & project meta** (5 tickets, 19 votes, 20 comments). #572 move to git (6), #508 move all objects (3), #1009 parametric constraints (3), #1043 custom shortcut mapping (3), #225 simple 2D annotation drawing (2).
Small but telling: shortcut customisation (#1043: *"q = properties instead of CTRL+ALT+E… would save a lot of time"*), multi-object transforms across levels (#508), and CAD-style geometric constraints/parametric modelling (#1009). #572's 14 comments are a governance argument that no longer exists for a web SPA. `OBSERVED` (`raw/threads/t_1043.md`, `raw/threads/t_1009.md`, `raw/threads/t_508.md`)

### 2.5 What the top 50 adds to round 1

Round 1 established the plugin ecosystem, the monetisation backlash, and the broad 787-ticket theme histogram. Deep-diving the vote/comment layer adds:

1. **The votes are too sparse to be a roadmap.** Round 1 counted 787 tickets by keyword theme; my per-ticket pull shows the vote signal is effectively absent (969 of 1,230 tickets have zero votes, max 12). Any CasaPlazAI prioritisation that says "SH3D users most want X" should be based on the *qualitative thread content* of the top ~50, not on rank position.
2. **The maintainer's vetoes are the real specification.** Round 1 noted dark mode was "promised 2021, still absent"; the tracker shows the same pattern is structural, not accidental — snapping, layers, direct roofs, and GPU rendering were each explicitly refused or deferred by the maintainer on the record, in threads that then became 4–16-comment arguments. The list of *refusals* is the most accurate list of a browser app's opportunities.
3. **The strongest underlying pain is "the plan is not a document".** Round 1 called out organisation; the vote layer refines it: users cannot produce a clean, dimensioned, scaled drawing (#446/#607/#617/#716/#819/#754) and their annotations do not persist against geometry (#609/#232/#647). That is a data-model property, not a UI feature.
4. **Roofs and stairs are the two geometry systems SH3D never shipped.** Round 1 flagged parametric generators as a plugin-market gap. The vote/comment data confirms this is the top vote mass (32 votes over 5 tickets), and the maintainer's own words are that direct roof creation *"isn't supported yet… should come in a future version"* (#466) and that stairs are best served by the Staircase/Multiplier plug-ins (#618). CasaPlazAI's schema *already has roofs* (`rooms[].roofs[{segmentIndex, leanDeg}]`, shed or one gable pair only) — so the open question is stairs, plus exactly which roof compositions are out of scope.
5. **MEP (electrical/plumbing/networks) is a real, decade-old, cross-ticket demand that the vote layer makes visible.** Five tickets (#274, #328, #421, #835, #1070), filed continuously from 2009 to 2022, ask for wall-mounted sockets/switches with elevation, wiring runs with computed lengths, and pipe routing. Round 1 saw only the *plugin* side of this ("Wall Socket Plugin", "Wirings"); the tracker side shows it is a persistent core-app gap too, and the schema currently has no entity for it. `OBSERVED` (this folder) + round-1 §2.1 (read-only)
6. **New in this round: the tracker is dormant** — 0 new tickets and 0 new comments in the last 7 days. The demand picture is frozen; round 1's "stagnating ecosystem" is now quantified.
7. **The vote list and the plugin list are near-duplicates.** Cross-referencing the top-50 FRs against round 1's plug-in tracker (`rea-sweethome3d-2026-10/10-10-community-plugins-feedback/raw/sf_plugins_rest_all.json`, read-only) shows the community has *already built* most of the top-voted gaps as `.sh3p` plug-ins, which is why `puybaret` answers with "try the plug-in": `#60 Advanced Staircase Generator`, `#50 Staircase generator`, `#53 Stair Builder` for #618/#997; `#40 Roof Generator plugin`, `#63 Advanced Shape Generator` for #466/#864; `#67 Terrain Generator` for #511; `#41 Wirings plugin`, `#69 Wall Socket Plugin`, `#59 SweetEnergy3D` for #274/#328/#421/#835/#1070; `#34 AutoDimensioning plugin`, `#7 Calculate room perimeter`, `#5 ComputeWallsSurface`, `#26 Rooms Surfaces`, `#19 Dynamic Total Surface` for #232/#538/#736/#819; `#44 Plugin Manager` and `#4 Advanced plan editing` for #565/#726; `#39 Pan with middle mouse button` for #856. **The top-50 vote list is best read as a map of what the core refuses to own — and the plug-in tracker is the list of who picked it up.** `OBSERVED` (round-1 `rea-sweethome3d-2026-10/10-10-community-plugins-feedback/raw/sf_plugins_rest_all.json`, reused read-only; `raw/top50_open_enriched.json`)
8. **Gaps closed from round 1's Unknowns that touched this question.** Round 1 could not reconcile its 787 feature requests with the site's 756 and could not fetch per-ticket detail or comment text. This round: (a) the authoritative figures are now captured from the stats page — **1,255 total / 756 open / 499 closed / 2,313 comments** — so round 1's 787 is a partial listing snapshot (it matches neither the total nor the open count), while my 1,230 is an all-status REST sample; the residual REST `count` wobble (1,238–1,244) is documented in §2.1. (b) All **50 top-50-open tickets now have their full description** and all 50 have their comment threads; 176 of 261 voted tickets have threads. `OBSERVED` (`raw/stats.md`, `raw/top_descriptions.json`, `raw/thread_posts.json`)

## 3. Ideas for CasaPlazAI (ranked by value / effort)

Ranked value ÷ effort (High first). Each is tied to a finding above and, where relevant, to the CasaPlazAI schema at `~/dsh-workspaces/rea2-shared/casaplazai-schema.md`.

| # | Idea | Tied to finding | Value / Effort |
|---|---|---|---|
| 1 | **Make dimensions a first-class, geometry-attached entity and show them during every edit.** Concretely: render each room segment's length (and running total) while dragging a wall vertex; show inner/outer/centre-line variants; keep a measurement overlay that is *derived* from `rooms[].polygon` + `wallThickness` so it updates when geometry moves (this is SH3D #609 "super sticky dimensions", #232 show room dimensions, #647 inner vs outer, #736 perimeter, #819 auto-dimension on export, all in the top 50). Persist user anchors in the editor-local measurement key (not `FloorplanData`), and re-derive lengths on load. | §2.4 C; §2.4 B (#832) | **High / Low** |
| 2 | **Promote grid snap from a setting to a visible, explained control** — a segmented switch "0.5 m grid / wall end / object edge / free", live X-Y and distance readouts in the status bar, and Shift-drag to suspend it. SH3D's maintainer refuses grid snapping on principle (*"walls almost never round values"*) and users spend *"a quarter to half my time… trying to get walls to line up"* (#407). This is the highest-emotion thread in the dataset and CasaPlazAI already has the feature. | §2.4 B; §2.4 A | **High / Very low** |
| 3 | **Draw walls with an explicit reference edge.** Add a per-wall (or global) "dimension line: inside / centre / outside" toggle that offsets the drawn axis by `wallThickness/2` or 0, with the blueprint underlay staying fixed. This is exactly #750 (*"I need to remember to take the wall thickness from the total width"*) and #1130 (community patch for left/middle/right alignment, never merged, 6 comments). Schema impact: none if implemented as an editor-side offset at insertion time; optionally record the reference edge per segment later. | §2.4 B; schema `wallThickness`, shared-door convention §Opening | **High / Low** |
| 4 | **A "clean plan" export mode: furniture-off, dimensions-on, scaled, all floors at once.** One dialog: which layers (rooms/walls/openings/furniture/labels/dimensions), scale (1:50/1:100), paper size, print area rectangle, and "all floors → multi-page PDF/PNG". SH3D's top export requests are #446 (pure plan), #607 (all levels), #617 (print area), #754 (hide furniture), and users work around it by hand-deleting or moving objects to hidden levels. CasaPlazAI already exports PNG/JPEG, so this is mostly a render-filter + scale/offset pipeline over the existing 2D canvas. | §2.4 G; §2.4 F workarounds | **High / Medium** |
| 5 | **Ship an object/level panel with search, grouping, visibility and lock toggles, built for tens of items.** Columns `Visible` + `Locked`, level folders, multi-select, "search across all floors", and **lock the level order** (SH3D #878: users reorder levels by accident with *"50 levels"*; #972 reports *"up to 80 levels"*; #666 asks for a wall visibility checkbox; #726 asks for hide/lock groups). Locking must prevent both selection and movement — SH3D's #1277/#1265 (round 1 §2.2) ask for exactly this. | §2.4 F; round-1 §2.2 (#1277, #1265) | **High / Medium** |

With walls already extruded in the 3D viewer, a clipped orthographic camera plus dimension overlay is a contained feature. | §2.4 G (#716, #450); §2.4 A | **High / High** |
| 7 | **Parameterise stairs, and close the roof-composition gap deliberately.** Build a stairs generator (straight/L/U with landings) as a *parametric object* rather than 3D furniture — #618 (7 v) and #997 (3 v) are the two stair tickets, and the maintainer's only answers are plug-ins. | 8 | **Smooth, quantitative editing of sloped walls/sloped ceilings.** Where SH3D makes you enter an *angle* and compute heights yourself (#74: *"people may know the height of the wall not the angle"*), expose both — "start height / end height" plus degrees, with both fields live. ## 4. Unknowns

- **Rank 47–50 of the "top 50 by votes" is arbitrary.** 43 open tickets sit at 2 votes; the cut at rank 50 is decided by ticket-number tie-breaking, not by demand. Only the 46 open tickets at ≥3 votes are a defensible "top" set; I shipped both, plus the full 225-ticket open ≥1-vote subset inside `raw/fr_all_tickets.json`, so the reader can re-cut.
- **I obtained comment threads for 176 of the 261 voted tickets (~67 %);** the rest returned HTTP 429 from the text proxy under pacing and were not retried further. All 50 of the top-50-open tickets have threads.
- **The REST sample is 1,230 of the 1,255 tickets the stats page reports (~2 % missing).** Page `count` values drifted (1,238–1,244) between requests, so some tickets were never returned by any page; they are overwhelmingly likely to be zero-vote and open. I could not obtain a stable full enumeration because the API exposes no deterministic cursor.
- **Comment counts depend on thread pagination.** The thread endpoint defaults to 25 posts/page and I fetched page 0 only. No thread in the top 50 reached 25 posts, but the all-status most-commented table (#727 at 20, #281 at 19) is close enough that a 26+-post thread elsewhere could be missed; I did not paginate beyond page 0.
- **Votes were snapshotted once, on 2026-10-31**, and SourceForge gives no vote timestamps. I cannot say whether a 2013 ticket's 12 votes accumulated in 2013 or trickled in later, so "top by votes" cannot be time-normalised.
- **Voting is registered-users-only** and the tracker is dormant (0 votes/comments in 7 days), so vote counts systematically under-represent anyone who only reads the forum. This is the main reason I treat the thread text as the primary evidence and votes as a secondary signal.
- **My themes are hand-assigned.** SourceForge labels are unusable (287 × "Other features", 195 × "Interface Improvements", 300 mostly-singleton labels). In §2.4 I force **one theme per ticket** so the counts sum cleanly; a different analyst would plausibly move boundary tickets (#407 snapping → walls vs geometry, #609 sticky dimensions → dimensions vs 2D output) between buckets, changing vote mass by a few votes. The assignment is reproducible only through the per-ticket `cluster` field in `raw/top50_open_enriched.json`.
- **No Sweet Home 3D desktop app was run in this round.** Descriptions, votes and comments are tracker data; behaviour of the shipped app for the specific features above is taken from the maintainer's own in-thread statements (e.g. "fixed in 6.0", "added in 7.2") which I did not independently verify against a running build. Round 1's JS-bundle observations (`rea-sweethome3d-2026-10/…/bundle/sweethome3d.min.js`) remain the only direct evidence about the shipped core.
- **The desktop GPL line was never executed.** I cannot confirm which of these top-50 items are still absent in the 7.5/7.x SourceForge build as opposed to the paid app-store build; the tracker's "open" status plus the maintainer's comments are my only evidence.
- **Could not read the SourceForge HTML tracker directly** (Cloudflare 403 to `curl` even with a browser UA; headless Chrome also hit the challenge). Everything here went through `r.jina.ai`; a proxy could in principle alter content, so I cross-checked the vote ranking against a second endpoint (the HTML vote-sorted table) and the two agreed.
- **Plugin popularity remains unmeasurable, per round 1.** I did not retry SourceForge download stats for the plug-in folder; the plugin↔feature mapping in §2.5(7) is by ticket title/description, not by adoption.
- **`rea capture-browser-scenario` was not used.** No page needed dynamic rendering: all evidence is JSON/HTML that the proxy returned, and synthetic canvas interaction would add nothing to a tracker question. `rea analyze-web-bundle` was likewise not applicable. Round 1's observation stands: REA's Playwright launch was blocked by the macOS sandbox there, and headless Chrome hit Cloudflare's challenge on SourceForge in this round (`raw/method/cloudflare_block_dom.html`).
