## 1. Summary

- **Sweet Home 3D's browser edition is the desktop Swing app ported class-by-class to JavaScript — not a modern web app.** The 2.6 MB `sweethome3d.min.js` exposes ~79 Java-named class constructors (`PlanController`, `HomeComponent3D`, `HTMLCanvas3D`, `JSTreeTable`, `JSComboBox`), backed by bespoke hand-written shims that reimplement pieces of the JDK (`core.min.js` carries an **OpenJDK 8 / Classpath-exception copyright header** and defines `IllegalArgumentException`, `System.arraycopy`, `PropertyChangeSupport`, `NumberFormat`…). `OBSERVED` (round-1 `bundle/sweethome3d.min.js`, `bundle/core.min.js`)
- **It is a full application runtime in the browser, not an SPA**: the page loads 14 `/libjs/` scripts (plus the small `SweetHome3D.js` helper and `crypto-js` for the online manager) forming a Java-shaped stack (geom, swingundo, graphics2d, triangulator, stroke, jsXmlSaxParser, jszip, gl-matrix, a recorder Web Worker), and the 3D view is a **bespoke WebGL re-implementation of the Java 3D API** — `HTMLCanvas3D`, `BranchGroup3D`, `TransformGroup3D`, `Shape3D`, `Appearance3D`, `IndexedTriangleArray3D` with inline GLSL shaders. Desktop uses real `javax.media.j3d`; the web build swaps in these clones. `OBSERVED` (round-1 `raw/js_online.jsp.html`; note round 1's "23 scripts" count included analytics/consent tags)
- **Its data model is aggregate-rooted and centimetre-based**: `Home` owns parallel lists of `Wall`, `Room`, `HomePieceOfFurniture`, `Polyline`, `DimensionLine`, `Label`, `Level`; walls are **segments with explicit `wallAtStart`/`wallAtEnd` links plus an `arcExtent` for curves**; a room is an **independent polygon**, and **doors/windows are furniture subclasses (`HomeDoorOrWindow`), not cut-outs on a wall's segment**. Internal units are centimetres; `Home.CURRENT_VERSION = 7400`. `OBSERVED` (Java sources)
- **The plan grid is a zoom-adaptive drawing aid, and "magnetism" is not grid snapping.** `PlanComponent.getGridSize()` picks from `{1,2,5,10,20,50,100,200,500,1000,2000,5000,10000} cm` so grid lines stay ≥10 px apart; `getMagnetizedLength()` rounds dimensions to a precision ladder (0.1/0.5/1/5/10/100 cm) and dragging aligns to walls/objects. Both `gridVisible` and `magnetismEnabled` default to **false**. This is the architectural root of round-1's top community complaint ("Damn you snapping grid!!"). `OBSERVED`
- **Open-source web planners cluster into four camps** (details in §2.5), and **none** matches CasaPlazAI's combination of always-on, adjustable 0.5 m grid snap, shared-wall editing, opening cut-outs, multi-floor, walkthrough and a versioned, backend-free save. Three architecturally instructive exemplars: **blueprint3d** (MIT, Three.js, DCEL half-edges with rooms *derived* from wall cycles — but master frozen since 2016 and no grid snap), its live successor **`charmlinn/blueprint3d-modern`** (MIT, Three r181 + Next 15 + IndexedDB, no backend — but multi-floor is an unchecked TODO), and **react-planner** (MIT, walls as vertex pairs with `Hole` children + real ThreeBSP CSG openings, layers-as-storeys, first-person 3D and a snap mask — but master frozen since 2019 and no furniture collision). The most *visible* rival, **Arcada** (Apache-2.0, 424★, active), turns out **not** to be backendless: its catalog and door/window sprites come from an Express/MongoDB server, its `three` dependency is unused (no 3D), and it autosaves only on Ctrl+S — though it does snap to a hardcoded 0.1 m grid by default. `OBSERVED`

## 2. Findings

### 2.1 How the Sweet Home 3D browser edition is actually built

**Evidence:** the round-1 capture of `https://www.sweethome3d.com/SweetHome3DJSOnline.jsp`
(round-1 `raw/js_online.jsp.html` for the script list and DOM markup, `bundle/sweethome3d.min.js` v7.5.2, `bundle/core.min.js`, and the per-module shims named in the page's script list), plus the community JavaScript-port repository `luxvitae-eco/SweetHome3DJS`.

- **Same Java source, translated.** The bundle's method names are the Java class names, fully qualified and mangled, e.g. a PlanController field access appears as
  `this.__com_eteks_sweethome3d_viewcontroller_PlanController_preferences.isMagnetismEnabled()`, and the controller class is referenced as `com.eteks.sweethome3d.viewcontroller.PlanController` style. ~79 top-level constructor functions exist, including `PlanController`, `HomeController`, `HomeComponent3D`, `FurnitureCatalogListPanel`, `ImportedFurnitureWizardStepsPanel`, `HomeXMLExporter`. `OBSERVED` (round-1 bundle; this job's greps recorded in `raw/` — see `raw/sh3d_class_inventory.txt`)
- **The JDK is re-implemented by hand, not by a transpiler.** `core.min.js` (15 KB) opens with `"core.min.js version 7.5.2 … Copyright (c) 1997, 2013, Oracle and/or its affiliates"` and the **OpenJDK 8 Classpath-exception** header, then defines in plain JS: `IllegalArgumentException`, `NullPointerException`, `IllegalStateException`, `NoSuchElementException`, `ParseException`, `System.arraycopy`, `EventObject`, `PropertyChangeEvent`, `PropertyChangeSupport`, `StringWriter`, `Format`, `ParsePosition`, `NumberFormat`. `OBSERVED` (round-1 `bundle/core.min.js`, read in full)
- **No third-party Java→JS toolchain.** I grepped for GWT (`$wnd`, `goog.`, `JSO`), JSweet, TeaVM (`$rt`), Doppio, bck2brwsr, CheerpJ, SwingJS/jmak and Java2Script markers: all absent apart from `java.lang` string literals (520) and `javax.swing` (113). The port is bespoke; the class-name mangling (`__com_eteks_…`) is a custom convention. `OBSERVED`/`INFERRED`
- **The whole desktop stack is present in layers.** The page loads, in order: `big.min.js`, `gl-matrix-min.js`, `jszip.min.js`, `jsXmlSaxParser.min.js`, `core.min.js`, `geom.min.js`, `stroke.min.js`, `swingundo.min.js`, `batik-svgpathparser.min.js`, `triangulator.min.js`, `graphics2d.min.js`, `recorderworker.min.js`, `sweethome3d.min.js` (13 core modules; `mobile-detect.min.js` and `SweetHome3D.js` are the other two `/libjs/` scripts) — i.e. arbitrary-precision maths, 3D matrices, ZIP, XML-SAX, JDK core, `java.awt.geom`, stroking, `javax.swing.undo`, SVG path parsing, polygon triangulation, a 2D graphics layer, a Web Worker, then the app. The DOM skeleton is static in the JSP (`home-3D-view` canvas, `home-plan`, `furniture-catalog-list`, toolbars, splitters) and the port attaches to it. `OBSERVED` (round-1 `raw/js_online.jsp.html` script list and markup)
- **Swing widgets are re-created as JS classes**: `JSComponent`, `JSDialog`, `JSViewFactory`, `JSComboBox`, `JSTreeTable`, `JSSpinner`, `JSPopupMenu`, `JSColorChooser`/`JSColorChooserDialog`, `JSImageResizingDialog`, `JSTextureDialog`, `JSModelMaterialsSelectorDialog`, `JSWizardDialog`. `OBSERVED` (round-1 bundle)
- **The app is server-driven for saves.** A `DirectHomeRecorder` talks to URLs (`listHomesURL`, `deleteHomeURL`); autosave/auto-recovery runs through `AutoRecoveryManager` + `recorderworker.min.js`; the page also loads `crypto-js` (integrity/local-storage crypto for the online manager) and registers a service-worker **resource cache** (`/resourceCache.js`) for offline asset reuse. Round 1 observed IndexedDB (models/cache) + Firebase heartbeat stores. `OBSERVED`
- **A community TypeScript re-port exists and confirms the diagnosis.** `luxvitae-eco/SweetHome3DJS` (6★, GPL-2.0 badge, default branch `dev`, pushed 2025-11-16) describes itself as a "work in progress effort to refactor and modernize the existing SweetHome3DJS implementation" whose goals are literally: *"Eliminating Java toolchains dependency"*, ESM, TypeScript, Vite/npm — and warns that **import, export, save and load are non-functional**. Its fork `FlySkyPie/SweetHome3DTS` (0★, 2025) continues the same attempt. `OBSERVED` (GitHub API + README; `raw/readme_sh3djs.md`)

**Interpretation (`INFERRED`).** The browser edition's architecture is its main liability: a Java desktop app faithfully transliterated into JS produces a large, hard-to-extend codebase with a Swing-like DOM-rendered UI (the round-1 a11y capture showed almost no semantic DOM — one `Canvas` node for the plan). A greenfield TypeScript/Three.js SPA like CasaPlazAI can beat it on bundle size, DOM semantics, accessibility, iteration speed and mobile performance without out-engineering its feature set.

### 2.2 Sweet Home 3D's data model, units and file format

**Evidence:** the maintained mirror of the official SVN tree, `keich/SweetHome3D` (`src/com/eteks/…`; 2,000 files under `src/com/eteks`, of which 242 are `.java` under `src/com/eteks/sweethome3d/`, the rest being resources/locales). Files downloaded by this job: `raw/src/Wall.java`, `Room.java`, `Home.java`, `HomePieceOfFurniture.java`, `HomeDoorOrWindow.java`, `Level.java`, `LengthUnit.java`, `PlanComponent.java`, `PlanController.java`, `HomeXMLExporter.java`, `HomeFileRecorder.java`, `HomeComponent3D.java`, `Component3DManager.java`. `OBSERVED`

- **Aggregate root.** `Home` (94 KB source) holds `List<Wall>`, `List<Room>`, `List<HomePieceOfFurniture>`, `List<Polyline>`, `List<DimensionLine>`, `List<Label>`, `List<Level>`, cameras, `BackgroundImage`, `HomeEnvironment`, `HomePrint`, `furnitureVisiblePropertyNames` and a free-form `Map<String,Object> visualProperties`. `CURRENT_VERSION = 7400`, with `KEEP_BACKWARD_COMPATIBLITY = true`. `OBSERVED` (Home.java:49–111)
- **Walls are segments, not polygons.** `Wall` fields: `xStart,yStart,xEnd,yEnd`, `arcExtent` (curved wall), `wallAtStart`/`wallAtEnd` (adjacency links), `thickness`, `height`, `heightAtEnd` (sloped wall), per-side colour/texture/shininess/baseboard (`leftSide*`, `rightSide*`), `symmetric`, `pattern`, `topColor`, `level`, plus transient geometry caches (`pointsCache`, `arcCircleCenterCache`). **This is how shared walls are modelled: two endpoint references, not a shared edge record.** `OBSERVED` (Wall.java:47–73)
- **Rooms are independent polygons.** `Room` stores `float[][] points` (polygon), `nameXOffset/nameYOffset/nameAngle`, `areaXOffset/…`, floor+ceiling colour/texture/shininess, `level`. A room is *not* derived from its bounding walls — so moving a wall need not update the room, which is a known class of user problem. `OBSERVED` (Room.java:52–69)
- **Doors/windows are furniture.** `HomeDoorOrWindow` extends `HomePieceOfFurniture`; an opening is a piece of furniture placed on a wall (the model even computes wall overlap area in `PlanController.addFurniture` when magnetism is on). There is no `Opening` entity with `segmentIndex`/`tCenter`/`sillHeight`. `OBSERVED` (model package; bundle `PlanController.addFurniture`)
- **Levels are a full entity.** `Level`: `name`, `elevation`, `floorThickness`, `height`, `backgroundImage`, `visible`, `viewable`, `elevationIndex`. Note both `visible` and `viewable` — one for 2D, one for 3D. Round 1 found users abuse levels as layers (50+). `OBSERVED` (Level.java:39–46)
- **Units are centimetres internally.** `LengthUnit` is an enum `{MILLIMETER, CENTIMETER, METER, INCH, INCH_FRACTION}` with `centimeterToUnit`/`unitToCentimeter` and `getMinimumLength() = 0.1`; METER multiplies by 100, MILLIMETER by 10. So CasaPlazAI's "everything in metres" is a cleaner contract, at the cost of one conversion at import. `OBSERVED` (LengthUnit.java)
- **The stored file is a ZIP containing `Home.xml`.** `HomeFileRecorder` documents "an additional `Home.xml` entry"; `HomeXMLExporter` writes a `<home version="…">` tree with the attributes `x, y, yStart, yEnd, xStart, xEnd, level, height, thickness, elevation, color, visible, shininess, angle, pitch, width, depth, diameter, model, icon, planIcon, image, catalogId, shelf, price`. That version tag is the format-compatibility marker the app keys on: round-1 forum ticket **#14439** ("Regression: Modify furniture does not open for existing furniture in ≥7.5 (works in 7.4)") reports a plan whose header is exactly `<home version="7400">` failing to open its furniture dialog after the 7.5 upgrade — the cautionary tale for a web schema. `OBSERVED` (HomeXMLExporter.java, HomeFileRecorder.java; `raw/threads/wish_14439.html` in the round-1 folder)
- **The whole home round-trips, including camera and print setup** (`topCamera`, `observerCamera`, `storedCameras`, `print`), whereas CasaPlazAI's 3D/walk state is deliberately out of schema. `OBSERVED`/`INFERRED`

### 2.3 Editing architecture: the 2D plan component, grid and "magnetism"

**Evidence:** `raw/src/PlanComponent.java` (317 KB), `raw/src/PlanController.java` (649 KB), round-1 `bundle/sweethome3d.min.js`.

- **Renderer:** `PlanComponent extends JComponent`; the web build paints the plan into a `<canvas>` 2D context (9 `getContext("2d")` call sites in the bundle) using the `graphics2d` shim. The JSP marks up `home-plan` as a `<div tabindex="1">` and `home-3D-view` as a real `<canvas tabindex="2">`, so the 3D canvas is static markup while the plan canvas is mounted by the port's graphics layer. React-free, retained-mode canvas. `OBSERVED`
- **Grid, explicit algorithm** (`PlanComponent.getGridSize`, lines 2883+): metric grid sizes are `{1, 2, 5, 10, 20, 50, 100, 200, 500, 1000, 2000, 5000, 10000}` cm and imperial is inches/feet (`2.54, 5.08, 7.62, 15.24, 1 ft, 3 ft, 6 ft, 12 ft, 24 ft, 48 ft, 96 ft, 192 ft, 384 ft`). The step is increased while `gridSize * gridScale < 10` px, and there is a second, coarser "main grid" for emphasis. So the visible grid **adapts to zoom** and is a reference, not a snap lattice. `OBSERVED`
- **Magnetism is a rounding + alignment system, not grid snap**:
  - `LengthUnit.getMagnetizedMeterLength(length, maxDelta)` picks a precision step from `maxDelta` (`0.1, 0.5, 1, 5, 10, 100` cm) and returns `Math.round(length/precision)*precision` — used when dragging/resizing furniture dimensions and elevations (`PlanController.adjustFurnitureSizeAndElevation`, `startDraggedItems`). `OBSERVED`
  - Walls and furniture align to existing walls via `adjustMagnetizedPieceOfFurniture` / `adjustPieceOfFurnitureOnWallAt`; wall endpoints are joined (`joinWalls`) so `wallAtStart/End` links form. `OBSERVED`
  - Magnetism is a **user preference defaulting to `false`**, toggled by a toolbar checkbox and *temporarily* inverted with Alt (Windows/Linux) / Cmd (macOS) while dragging — the state machine records `magnetismToggledLastMousePress`. `OBSERVED` (bundle `UserPreferences` ctor + `PlanController` + `HomePane` checkbox wiring)
  - **Correction to round 1:** round 1 concluded from the bundle that SH3D has "no snap-to-grid point logic". This deeper read shows it *does* have a length grid (in cm), but it is a separate rounding helper used mainly for furniture dimensions/elevation, not a cursor snap-to-grid-intersection lattice like CasaPlazAI's 0.5 m snap; and the plan grid is visual only. The complaint stands, but the precise architecture is "object alignment + length rounding", not "nothing". `OBSERVED`
- **Interaction is an explicit state machine.** `PlanController` holds state classes (`SelectionState`, wall/room/polyline/dimension/label creation and resizing states), each with `moveMouse`, `toggleMagnetism`, `escape`, `exit`. The `ActionType` enum (incl. `TOGGLE_MAGNETISM_ON/OFF` and alignment/duplication modifiers) lives on the view layer — `HomeComponent3D` for 3D and `HomeView.ActionType.ENABLE/DISABLE_MAGNETISM` in the bundle for the toolbar checkbox. Undo/redo is `javax.swing.undo` (`swingundo` shim). `OBSERVED` (`raw/src/HomeComponent3D.java:200`, bundle `HomePane.MagnetismChangeListener`)
- **Plan panning is bounded by `getPlanBounds()`** and margins in `paintGrid` (round 1: "the view is very boxed in"). `OBSERVED` (paintGrid uses `planBounds ± MARGIN`)

### 2.4 The 3D engine: Java 3D on the desktop, a WebGL clone in the browser

**Evidence:** `raw/src/HomeComponent3D.java` (181 KB), `raw/src/Component3DManager.java`, the `j3d/` package listing, and the round-1 bundle.

- **Desktop:** `HomeComponent3D extends JComponent implements View3D, Printable`, importing `javax.media.j3d.*` (Canvas3D, BranchGroup, TransformGroup, Shape3D, Appearance, Material, AmbientLight, DirectionalLight, BoundingBox, J3DGraphics2D…). `Component3DManager` instantiates Canvas3D, probes off-screen-image support (with a workaround for macOS+JOGL deadlocks) and uses off-screen rendering for photo output. The `j3d/` package holds `Wall3D`, `Room3D`, `HomePieceOfFurniture3D`, `Ground3D`, `Label3D`, `DimensionLine3D`, `Object3DBranch(Factory)`, `TextureManager`, OBJ/DAE/3DS loaders, `ShapeTools`, and external-JNI photo renderers (`PhotoRenderer`, `YafarayRenderer`). `OBSERVED`
- **Web:** the same vocabulary is re-implemented over WebGL in ~79 classes: `HTMLCanvas3D` (constructor calls `canvas.getContext("webgl")` with an `experimental-webgl` fallback, compiles a vertex+fragment shader pair inline — modelView/projection matrices, `textureCoordTransform`, `normalTransform`, `lightingEnabled`, `useTextures`, generated texture coordinates from `planeS`/`planeT`), plus `BranchGroup3D`, `TransformGroup3D`, `SharedGroup3D`, `Link3D`, `Node3D`, `Group3D`, `Shape3D`, `Appearance3D`, `Material` (337 refs), `Box3D`, `GeometryInfo3D`, `IndexedTriangleArray3D`, `IndexedLineArray3D`, `BoundingBox3D`, `Light3D`/`AmbientLight3D`/`DirectionalLight3D`, `Background3D`, `Ground3D`, `Wall3D`, `Room3D`, `HomePieceOfFurniture3D`, `Label3D`, `DimensionLine3D`, `HomeComponent3D`. Matrices come from `gl-matrix`. `OBSERVED`
- **Two 3D contexts exist in the plan too** — furniture icons/previews instantiate their own off-screen `HTMLCanvas3D` (`ModelPreviewComponent`, `PieceOfFurnitureModelIcon` with a parallel projection) — so a furnished plan creates many small GL contexts. That is a plausible explanation for the CPU/renderer complaints round 1 documented. `OBSERVED`/`INFERRED`
- **The 3D editor is real** (`EDITING_IN_3D_VIEW_ENABLED` preference, furniture groups updated on changes) — but it lives inside the ported Java logic, and round 1 could not render it headlessly. `OBSERVED`

**blueprint3d — the geometry textbook, and its live modern successor.** `OBSERVED` (`raw/src_bp3d/*.ts`, `raw/fork_modern_readme.md`)
- A plan is **walls glued by shared `Corner`s, and rooms are DERIVED**: each `Room` constructor runs `updateWalls()` then `updateInteriorCorners()`, building "a fancy doubly connected edge list (DCEL)". Each `Wall` has front/back `HalfEdge`s carrying `offset = thickness/2`, `height`, interior/exterior `Matrix4`s. `wall.ts`, `half_edge.ts`, `room.ts`
- **In-wall objects are a first-class base class** (`InWallItem extends WallItem`, `addToWall = true`, `getWallOffset()` with a "fudge factor so it saves to the right wall"), and `WallItem.boundMove()` clamps a window/door to the wall plane (`tolerance = 1`) so it cannot slide past the wall ends or through floor/ceiling.
- **Snapping is object/axis only**: `snapTolerance = 25` px to the previous corner/axis; `overlappedCorner/Wall` merge within 10/20 units. **No grid pitch exists in the 2D editor.**
- Serialisation is JSON with two source TODOs admitting it is unfinished (`// TODO: a much better serialization format.`), no version, defaults in inches.
- **Successor:** upstream master's last commit is **2016-07-10** (the 2021 `pushed_at` is a side branch); npm stopped at 0.0.1-1. Issue #120 (2025-11) points at **`charmlinn/blueprint3d-modern`** — MIT, 160★, complete ES-module rewrite on **Three.js r181 + TypeScript + Vite**, with a Next.js 15 demo persisting to **IndexedDB with no backend**, i18n (en/zh/tw), unit systems, room templates, texture selection, item lock and thumbnail previews. **But its README lists "Multi-room / multi-floor support" as an unchecked TODO**, and it has no walkthrough, no underlay, no collision and no schema version. This is the closest *live* open-source analogue to CasaPlazAI's positioning and should be watched. `OBSERVED` (`raw/fork_modern_readme.md`, `raw/fork_modern_pkg.json`)

**react-planner — the closest analogue to CasaPlazAI's UX, and the most complete opening/snap model.** `OBSERVED` (`raw/src_rp/*.js`; details in `raw/sub_bp3d_reactplanner.md`)
- Embeddable npm React component (`ReactPlanner` + `Catalog` + `reducer` + `Plugins`) wired into the host's Redux store. Domain classes: `Project`, `Layer`, `Group`, `Line`, `Hole`, `Vertex`, `Area`, `Item`, guides.
- **Walls are `Line`s with two `Vertex` ids; doors/windows are `Hole`s attached to a line by a normalised `offset` (0..1)** with catalog width/height/sill properties. Drawing calls `createAvoidingIntersections`, which **splits existing lines at intersections, removes colinear segments and re-scales the offsets of migrated holes**, then `detectAndUpdateAreas` finds rooms from graph inner cycles (normalised CCW) — **users close loops; they do not draw room polygons**. In 3D, `wall-factory-3d.js` builds the wall box and **subtracts each hole box with ThreeBSP CSG** — a real cut-out, not a decal.
- **Modes ≈ CasaPlazAI's Plan/3D/Walk**: `MODE_2D_*`, **`MODE_3D_VIEW`**, **`MODE_3D_FIRST_PERSON`** (pointer lock + WASD), `MODE_DRAWING_LINE/HOLE/ITEM`, `MODE_DRAGGING_*`, `MODE_ROTATING_ITEM`, `MODE_FITTING_IMAGE` (underlay), `MODE_VIEWING_CATALOG`.
- **Multi-floor is real**: `Layer{altitude, order, opacity, visible}`; the 3D scene sets `pivot.position.y = layer.altitude`. Changing altitude/opacity **tears down and rebuilds every object in the layer**.
- **Five-kind snapping with a mask, grid OFF by default**: `SNAP_MASK = {POINT:true, LINE:true, SEGMENT:true, GRID:false, GUIDE:true}`, resolved by (priority, distance); a real grid snap exists with `gridCellSize = 20` unit cells and per-type toggles in the footer; Alt temporarily disables snapping. `Hole.updateDrawingHole()` **forces `SNAP_SEGMENT` and clamps the offset so the hole width fits inside the line** — the same invariant as CasaPlazAI's `opening-too-wide`, enforced live.
- **Undo only, no redo**: history is `immutablediff` patches; `ESC` rolls back. **No furniture collision/fit** — item drag writes x/y unconditionally; **items are not snapped at all**, and the drawn grid is decorative and independent of the snap grid.
- **Autosave plugin** writes `JSON.stringify(state.scene.toJS())` to a caller-keyed localStorage entry on a 500 ms debounce and replays it on init — the closest existing analogue to CasaPlazAI's autosave, but unversioned and without restore points.
- **Verdict:** the richest editing model reviewed (CSG openings, layers+altitude as storeys, first-person 3D, maskable snapping, underlay fitting), but master has been frozen at 2.0.6 since **2019-11-03** (the 2024 `pushed_at` is a dependabot branch), it is pinned to React 16 / Three r94, and it lacks redo, furniture collision and non-demo export.

**Arcada — the most visible general-purpose competitor, and not actually backendless.** `OBSERVED` (`raw/arcada/` snapshot of `mehanix/arcada@master`, `raw/arcada_pkg.json`; details in `raw/sub_arcada_others.md`)
- React 18 + **pixi.js 6** + **zustand** + Mantine 4; one class per action (`AddWallAction`, `DeleteFurnitureAction`, `HistoryManager`, `MeasureToolManager`, `SaveAction`, `PrintAction`…); `Serializer`/`*Serializable`. Package is `arkada-react` v0.1.0; default branch is **`master`**.
- **It needs a server.** `src/api/api-client.tsx` fetches `http://localhost:4133/ categories`, `/category/:id`, `/wall/window`, `/wall/door`; the README advertises Express.js + MongoDB/Mongoose and points at a separate `arcada-backend` repo (which the subagent found frozen in 2023) plus a `docker-compose` setup. So Arcada's catalog and door/window *sprites* are server-supplied — a materially different architecture from a backend-free SPA. `three@0.140` is a declared dependency but **nothing in `src/` imports it**; there is no 3D view. `OBSERVED`
- **Multi-floor is real**: singleton `FloorPlan` with `floors: Floor[]`; a new floor **clones the previous floor's exterior walls** via a `nodeCloneMap`. Items record their host wall as `attachedToLeft`/`attachedToRight` node ids.
- **Undo *and* redo = whole-plan JSON snapshots**: `HistoryManager` (`LIMIT = 120`) listens to document `pointerup`, debounces 300 ms, re-serialises the plan, pushes to `undoStack` and clears `redoStack`; `redo()` restores from it. It refuses to snapshot mid-wall-draw.
- **Grid snap exists after all, and defaults ON.** `helpers/ViewportCoordinates.ts` applies `snap()` — hardcoded to a **fixed 10 px (0.1 m) pitch**, `Math.trunc`-ed — whenever `EditorStore.snap` is true, and `EditorStore` initialises `snap: true`; the toolbar has a "Snap to grid" toggle. There is **no user-settable pitch** and **no wall-endpoint snapping** (`AddWallManager.checkStep` only rejects nodes within 0.3×METER of each other). This corrects my earlier "none found". `OBSERVED` (`raw/arcada/src_helpers_ViewportCoordinates.ts`, `raw/arcada/src_stores_EditorStore.tsx:29`, `raw/arcada/src_ui_Layout_ToolNavbar.tsx:226`)
- Walls are `pixi.Graphics` subclasses — **the model IS the display object** — with `METER = 100` px, exterior 0.2 m / interior 0.16 m, mobile hit boxes doubled.
- **Autosave is manual, not automatic.** `Main.ts:120` writes `localStorage['autosave']` inside a `save` closure bound to **Ctrl+S**, and the `setInterval(autosave, 60000)` line below it is **commented out**; `WelcomeModal.tsx:79` offers to restore that key. `SaveAction` additionally exports `floor_plan.txt` via FileSaver, and `PrintAction` opens the browser print dialog.
- **No schema version, no furniture collision/fit** (no matches for `collision|overlap|fit|constraint`), no blueprint underlay, no PNG/JPEG render export, no 3D. `OBSERVED`

**wallgraph — architecturally the cleanest model found (but tiny and AGPL).** `OBSERVED` (`raw/wg_CLAUDE.md`, `raw/wg_package.json`)
- TypeScript, **zero runtime dependencies** (dev deps only: esbuild, tsx, typescript, web-ifc), builds to one self-contained `dist/index.html`; **AGPL-3.0-only** with a CLA. Only **3★**, one author.
- Its architecture reference states the model precisely: *"**The document is a planar graph of wall centerlines. Everything visible is derived.**"* Stored: nodes, walls (centerline edge + thickness + optional DXF `bulge` arc), openings parameterised along a wall (`t` = centre distance from node `a`, in **integer millimetres**), sized objects, authored **room names** (keyed to a point, reattached on change) and service `Route` graphs. **Not stored:** wall faces, mitered corners, room polygons, areas, dimension labels — all recomputed per `revision`.
- Invariants: integer mm in the document, y down, `bulge = tan(θ/4)`, **openings never enter the graph** (carved at resolve time; moving a wall moves its doors), and **all mutations go through `store.mutate()`**, which snapshots for undo and bumps `revision` to invalidate the derived cache.
- Public API `mountWallgraph(el) → {load, save}`; autosave key `floorplan-doc-v1`; JSON Schema emitted; IFC export via `web-ifc`; compliance/takeoff checks (energy, fire, materials). Its own known limits: single-thickness walls, approximate miters, **nothing checks cabinet/unit overlap**, 3D is indicative massing.
- **Verdict:** the best answer to "what is the document?" and the strongest *engineering* ideas (stored-vs-derived, integer units, single mutation point); its weakness is adoption, licence and scope, not design.

**easy-floorplan — the most polished 2026 editor.** `OBSERVED`/`DOCUMENTED` (README read directly: `raw/efp_readme.md`, `raw/efp_pkg.json`; more in `raw/sub_arcada_others.md` §4)
- MIT, 641★, `easy-floorplan-card` v0.7.2, pushed **the same day as this research**; Lit + `custom-card-helpers`, no heavyweight deps. It is a Home Assistant Lovelace card **and** a full visual editor: "draw walls, place furniture and connect your devices … in 2D or 3D".
- **Multiple floors** with a floor switcher and staircase navigation; **outdoor 3D stacking** of all levels at physical elevations with ground slabs and 3D roofs; **window `sill` height** semantics; PDF/image **tracing with scale calibration**; **SVG export**; room summaries. Persistence is HA dashboard YAML, so it is *not* a backend-free standalone SPA — but it is the best current example of a modern editor UX in this space (and the one to watch for feature parity). `OBSERVED`

**wy51ai/floorplan-3d — the star-count outlier.** `OBSERVED` (`raw/sub_arcada_others.md` §2)
- MIT, **3,276★** in 9 commits over four days (2026-09-29 → 10-02) — a trending artefact, not a maintained engine. It **is** a genuine planner (SVG 2D + Three.js 0.160 walkthrough, daylight, area/cost maths, localStorage `huxing-design-v1`, grid + wall-edge snapping, undo snapshots) — **but the building geometry is hardcoded in millimetres**: `WALLS`/`ROOMS`/`DOORS` are literal constants and there are no drawing tools. It is a decoration tool for one apartment.

**The camps** `INFERRED`: (1) *component/library* planners (react-planner is an embeddable npm component; Arcada is a React app with reusable-looking action classes but singletons) — flexible, but state and rendering are coupled; (2) *stand-alone Three.js* planners (blueprint3d, and its live `blueprint3d-modern` successor) — best 2D↔3D coherence; (3) *graph-first engines* (wallgraph, and the derived-room halves of blueprint3d/react-planner) — store the wall graph and derive rooms; (4) *SVG/canvas sketch* editors (homeRoughEditor, floorplanner2D, quickfloorplanner) — no 3D, no floors, cheap to build. A fifth, HA-bound cluster (easy-floorplan, floorplan-studio, home-studio) has the best 2026 UX but is not a standalone artifact.

**What they do better** `OBSERVED`/`INFERRED`:
- **Stored-vs-derived discipline with a revision counter** (wallgraph) — store the wall centreline graph; derive rooms, areas, miters and dimensions. Strictly cleaner than storing room polygons and deriving walls.
- **Exact, typed units in the document** — wallgraph mandates integer millimetres; react-planner types the scene as `unit:'cm'`; blueprint3d-modern supports in/ft/m/cm/mm. CasaPlazAI's metre floats with a 0.5 m snap are coarser.
- **Rooms auto-detected from the wall graph** (blueprint3d's DCEL room detection, react-planner's inner-cycle areas, wallgraph's `detectRooms()`) — the user draws walls and rooms fall out, instead of drawing rectangle/polygon rooms separately.
- **Openings as graph children with live clamping and a real 3D cut** (react-planner's `Hole.offset` + `clampOpening`-style fitting + ThreeBSP subtraction) — authoring model and validation loop to copy.
- **Snap *masks*** with per-type toggles and priority resolution (react-planner), rather than one master grid toggle.
- **Embodiment and test discipline**: react-planner is an npm package with a documented plugin contract; wallgraph publishes `mountWallgraph(el)→{load,save}`; easy-floorplan and wallgraph ship real test suites; home-studio exports JSON + GLB/OBJ and easy-floorplan exports SVG line-art.
- **Zero-backend storage that is richer than a single localStorage key** — blueprint3d-modern keeps a named "My Floor Plans" library in IndexedDB with generated `thumbnailBase64` previews; easy-floorplan persists several floors in HA dashboard YAML; Arcada writes one `localStorage['autosave']` snapshot on Ctrl+S and can also save `floor_plan.txt`.

**What they do worse / lack** `OBSERVED`/`INFERRED`:
- **No project has a versioned schema or migration.** All serialise whatever their JS objects are; blueprint3d says so in two TODOs; wallgraph and floorplan-3d bless a storage key string instead. Nothing to migrate *from* means old files rot silently (the mirror image of round 1's `home version="7400"` problem).
- **Grid snapping is off or missing nearly everywhere, with one exception.** blueprint3d has none; react-planner implements `GridSnap` but sets `SNAP_GRID:false`; SH3D's `gridVisible`/`magnetismEnabled` default `false`; wallgraph and homeRoughEditor snap keyboard-first to nodes/walls. **Arcada is the only one with grid snap on by default, but its pitch is a hardcoded 10 px (0.1 m) with no user control and no wall-endpoint snap.** CasaPlazAI's user-visible always-on 0.5 m grid snap is therefore a genuine differentiator — but it should not claim the category never snaps.
- **Furniture collision/fit is effectively absent.** blueprint3d's check is commented out; react-planner has none and does not snap items at all; Arcada has none; wallgraph documents that "nothing checks unit overlap"; SH3D users download the Fit-In plugin. CasaPlazAI's fit/collision palette is ahead of every open-source planner reviewed.
- **No single project combines an *adjustable* grid snap + multi-floor + openings + 3D walkthrough + versioned save + backend-free operation.** react-planner has openings/floors/first-person but defaults grid snap off and has no redo, collision or version; Arcada has floors, grid snap and polish but no 3D, needs an Express/MongoDB backend, and autosaves only on Ctrl+S; blueprint3d-modern has the modern stack and IndexedDB but no floors; wallgraph has the model but no furniture semantics or adoption; easy-floorplan has the best UX but stores its plan in Home Assistant YAML.
- **Maintenance is bimodal**: blueprint3d (2016), react-planner (2019), quickfloorplanner (2020), homeRoughEditor (2024) are frozen; Arcada, easy-floorplan and the `blueprint3d-modern` successor are active — but Arcada's *backend* (`arcada-backend`) is frozen since 2023, so the live repo alone cannot run.
- **Accessibility and testability**: most render into SVG/canvas DOM with little keyboard or screen-reader support, and Arcada's singletons + module globals make headless testing impossible — the same single-canvas weakness as SH3D.
- **Licence hazard for reuse**: wallgraph is AGPL-3.0-only with a CLA, so its ideas (not its code) are what is usable here.

### 2.6 What the architecture comparison says for a modern SPA

`INFERRED`, grounded above:

1. **The competitor's browser build is a legacy runtime, not a peer product.** CasaPlazAI should not try to match its class-for-class fidelity; it should match its *outcomes* (accurate 2D, believable 3D, print-quality export) with a fraction of the code, and treat "loads fast, works on a phone, semantic DOM" as product features.
2. **Openings are the sharpest modelling divergence.** SH3D models a door as furniture sitting on a wall; CasaPlazAI models an `Opening` with `segmentIndex` + normalised `tCenter` and validation (`opening-too-wide`). CasaPlazAI's model is closer to how builders think, and it makes wall thickness/head height exact — keep it, and market the exactness.
3. **Independent rooms are a latent bug class SH3D lives with.** Because its `Room` polygon is not reconciled with its `Wall` segments, resizing a wall can desynchronise the room. CasaPlazAI's per-room polygon plus explicit shared-wall handling should be presented as "walls and rooms stay in sync" — but it must actually re-derive rooms on wall edits, and say so.
4. **Snapping is a spectrum, not a toggle.** SH3D has three overlapping things (visible adaptive grid, length-rounding magnetism, object alignment) and no cursor grid snap, and defaults all of them off. CasaPlazAI's 0.5 m grid snap is genuinely different; add object-alignment and live dimension feedback alongside it and the comparison is decisive.
5. **Levels-as-layers was an accident of SH3D's design** (one `Level` entity with 2D+3D visibility, no grouping), and the open-source planners repeat variants of it (react-planner storeys as layer `altitude`; Arcada cloning the floor below). CasaPlazAI should keep floors as first-class structural data and layers/view state out of `FloorplanData` — which its "out-of-schema editor state" convention already anticipates.
6. **The whole category lacks schema versioning.** Not one surveyed planner — SH3D (which at least version-tags its XML and breaks old plans because of it), blueprint3d (two source TODOs admitting an unfinished format), react-planner, Arcada, wallgraph, blueprint3d-modern, easy-floorplan — offers a forward migration for saved plans. CasaPlazAI's `schemaVersion` + `migrate.ts` is therefore not table stakes; it is a category-unique claim worth stating in the UI.
7. **The strongest architecture found is wallgraph's**: store only the wall-centreline graph in integer millimetres, derive rooms/areas/miters/openings-cuts per revision, and funnel every mutation through one `mutate()` that snapshots undo and bumps the revision. CasaPlazAI stores room polygons rather than deriving them — an acceptable trade for its frozen interchange contract, but it should still adopt the **revision counter + derived cache** discipline so rooms, areas and cut-outs are provably recomputed on every edit.
8. **Openings are the feature to prove.** SH3D stores a door as furniture; react-planner stores a `Hole` offset on a line, clamps it during the drag and CSG-subtracts it from the 3D wall. CasaPlazAI's `Opening` schema (`segmentIndex`, `tCenter`, `width`, `sillHeight`, `headHeight`) is the strongest *declared* model in the category — the remaining work is to show the clamp live and confirm the 3D mesh is actually cut.
