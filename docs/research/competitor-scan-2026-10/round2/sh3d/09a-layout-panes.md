Job folder: `03-09a-ui-workflow-shortcuts-layout` · Round 2. Target: **Sweet Home 3D 7.5.2** (eTeks / Space Mushrooms, GPL) — desktop Java app (`https://www.sweethome3d.com/de/`), and the browser edition **Sweet Home 3D JS Online** (`https://www.sweethome3d.com/SweetHome3DJSOnline.jsp`) transpiled from the same Java core.

## 1. Summary (5 bullets)

- **The panes are interactive-splitter panes on both sides of the fence, but implemented twice.** Desktop uses three `JSplitPane`s (`setContinuousLayout(true)`, `setOneTouchExpandable(true)`, `setResizeWeight(0.3/0.5/0.5)`, divider size from the UI theme scaled by HiDPI); the web build re-implements the same three dividers as 4 px absolutely-positioned `div`s driven by one JavaScript routine, `HomePane.prototype.updateSplitter`. Both write the divider position into the *home document* under the same three keys (`…MainPaneDividerLocation`, `…CatalogPaneDividerLocation`, `…PlanPaneDividerLocation`). — OBSERVED (`raw/probe1.json`, `raw/probe4.json`, `raw/js/sweethome3d.min.js`) + DOCUMENTED (`raw/src/HomePane.java`).
- **Dragging is clamped only by zero and the far edge — there is no minimum pane size.** Dragging any splitter to the end collapses that pane to the width/height of the splitter itself (measured: catalog 1598 → 2 px; plan/3D: plan 2 px / 3D 1 px; catalog/list: catalog 0 px). On the desktop the splitter also carries **one-touch collapse/expand triangles**; the web build has none (no arrows in the DOM, and a synthetic double-click on a splitter changes nothing). Collapsing a pane in the browser is therefore a purely manual drag-to-the-edge gesture. The clamped value is written straight into the home document on mouseup (`Main/Plan/CatalogPaneDividerLocation`). — OBSERVED (`raw/probe1.json`, `raw/probe4.json`, `raw/probe5.json`), DOCUMENTED (`HomePane.configureSplitPane`).
- **Dividers are stored as absolute pixels online, not as a fraction — so the split drifts on resize.** The Swing `resizeWeightUpdater` pins `resizeWeight` to 0 or 1 while the divider is at an extreme and distributes extra space by weight in between; the web drag handler only ever clamps pixels. Measured: a 406 px catalog stayed 408 px at window widths 1200 / 800 / 1400 (plan absorbed every delta), and at 1600×700 the plan pane kept its dragged 561 px, leaving the 3D view 57 px. A *collapsed* pane does stay collapsed (clamp is one-directional), but there is no focus rescue online when a pane becomes invisible. — DOCUMENTED (`raw/src/HomePane.java`), OBSERVED (`raw/probe5.json`, `raw/probe6.json`).
- **Only two of the four panes are keyboard-reachable online, and the focus rectangle is missing.** `#home-plan` carries `tabindex="1"` and `#home-3D-view` `tabindex="2"`; `#furniture-catalog` and `#furniture-view` are `tabindex="-1"`. Tab from the plan moves to the 3D view and then **out into the surrounding sweethome3d.com page chrome**; both canvas panes have `#home-plan:focus, #home-3D-view:focus { outline: none }`, so the desktop's coloured focus rectangle (R1-F1) has **no web equivalent**. — OBSERVED (`raw/probe1.json`, `raw/probe2.json`, round-1 `evidence/studio_dom.html`).
- **The online build's responsive layout re-flows the same four regions and re-maps the splitters at runtime.** Under a coarse pointer, `@media (max-width:743px), (max-height:511px)` hides all `.pane-splitter`s, hides `#catalog-furniture-splitter`/`#furniture-view` and turns the catalog into a horizontal strip; two nested blocks then re-shape the plan/3D pair — stacked in portrait / ≤5:4 (with an ID-specific `#plan-3D-view-splitter{display:initial}`), side by side with a **vertical** 8 px divider in small-touch landscape ≥5:4. Crucial detail: the app re-derives which pane is each divider's "first" and "second" child **at runtime from their bounding rectangles** (`updateSplitters`), so the same three splitter objects keep working after the axis flip. — OBSERVED (`raw/probe5.json`, `raw/probe7.json`, `raw/probe8.json`), DOCUMENTED (inline CSS, round-1 `raw/sh3d-online.jsp.html` l. 726–903).

## 2. Findings

### 2.1 Splitter implementation: desktop (Swing) vs online (DOM)

- **F1 (DOCUMENTED).** Desktop builds exactly three split panes in `HomePane.java`:
  - `mainPane = new JSplitPane(HORIZONTAL_SPLIT, catalogFurniturePane, planView3DPane)`, default divider `360 × resolutionScale` px (mirrored for RTL locales), `defaultResizeWeight = 0.3`;
  - `catalogFurniturePane = new JSplitPane(VERTICAL_SPLIT, catalogView, furnitureView)`, weight `0.5`;
  - `planView3DSplitPane = new JSplitPane(VERTICAL_SPLIT, planView, view3D)`, weight `0.5`.
  All three go through one `configureSplitPane(...)` helper. — `raw/src/HomePane.java` (`createMainPane`, `createCatalogFurniturePane`, `createPlanView3DPane`, `configureSplitPane`), fetched from <https://sources.debian.org/data/main/s/sweethome3d/7.5+dfsg-1/src/com/eteks/sweethome3d/swing/HomePane.java>.
- **F2 (DOCUMENTED).** `configureSplitPane` sets `setContinuousLayout(true)` (panes repaint while the divider is dragged), `setOneTouchExpandable(true)` (collapse/expand triangles on the divider), `setResizeWeight(defaultResizeWeight)` (extra window space goes to the *second*/bottom component by default), and, for the two inner panes, `setBorder(null)`. Divider size is not set here; the theme supplies `SplitPane.dividerSize`, scaled for HiDPI by `SwingTools.updateComponentSize("SplitPane.dividerSize", getResolutionScale())`. History records a deliberate change: *"Increased the divider size of split panes under Windows."* — `raw/src/HomePane.java`, `raw/src/SwingTools.java`, round-1 `raw/history.txt`.
- **F3 (DOCUMENTED).** Divider location is persisted on every change and restored on open: `home.getNumericProperty(dividerLocationProperty)`; a `DIVIDER_LOCATION_PROPERTY` listener runs on the event queue and calls `controller.setHomeProperty(prop, String.valueOf(newValue))`. The same listener also re-homes the keyboard focus if the currently focused component has just been made invisible by the drag. — `raw/src/HomePane.java`.
- **F4 (DOCUMENTED).** A focus-traversal policy (`LayoutFocusTraversalPolicy` override + `isChildComponentInvisible`) **skips any component whose split-pane ancestor has width or height 0**, so Tab cannot land inside a collapsed pane. — `raw/src/HomePane.java` (`updateFocusTraversalPolicy`, `isChildComponentInvisible`).
- **F5 (OBSERVED).** The online build reproduces the three split panes as plain DOM: `#furniture-plan-splitter`, `#plan-3D-view-splitter`, `#catalog-furniture-splitter`, each `class="pane-splitter horizontal|vertical"` with a `display:block` inline style, 4 px thick (`width:4px; height:4px` in CSS), `background: linear-gradient(...)` for the thickness illusion, and `cursor: ew-resize` / `ns-resize`. Measured live: the catalog/plan splitter at `x=300,w=4,h=920`, the plan/3D splitter at `y=540,w=1296,h=4`, the catalog/furniture splitter at `y=726,w=300,h=4`. Hover lightens to `#BBB`, dragging adds `.moving` → `#CCC`. No one-touch arrows exist. — `raw/probe1.json` (`snapDesktop.ids`), round-1 `raw/js/sweethome3djs.css` (`.pane-splitter` block), round-1 `evidence/studio_dom.html`.
- **F6 (OBSERVED).** All three splitters are wired by one function, `HomePane.prototype.updateSplitter(c)`, over a descriptor `{element, homePropertyName, firstGroupElement, secondGroupElement, isDisplayed, resizeListener}`. It first **clears 11 inline styles** (display/top/left on the splitter; left/top/width/height on each pane), re-decides `display` from `isDisplayed()`, tears down any previous listener record, re-derives the orientation class from `clientWidth > clientHeight` (`horizontal` = splitter wider than tall = moves vertically), reads the persisted property, and — only if it is non-null and the splitter is displayed — re-applies it via `setSplitterPosition(h)`. It then installs `mousedown`+`touchstart` (both capturing) plus `window`-level `resize`. — `raw/js/sweethome3d.min.js` (`updateSplitter`, bundle offset ≈2 300 700).
- **F7 (OBSERVED).** `setSplitterPosition(o)` writes four things with the axis letters resolved from the orientation class: first pane `style[axis-size] = (o - l) + "px"` (**absolute**), splitter `style[axis-start] = o + "px"`, second pane `style[axis-start] = (o + splitterThickness) + "px"` and second pane `style[axis-size] = "calc(100% - " + (o + splitterThickness) + "px)"`. So the **first pane is pinned to a pixel size and the second is purely proportional** to what is left. `l` is the first pane's `offsetLeft`/`offsetTop` when its `offsetParent` is `<body>`, else 0. Measured after an 80 px drag: `#catalog-furniture-pane style="width: 422px"`, `#furniture-plan-splitter style="display:block; left:422px"`, `#plan-3D-view-pane style="left:426px; width:calc(100% - 426px)"`. — `raw/probe1.json` (`snapAfterDrag`), `raw/js/sweethome3d.min.js` (`setSplitterPosition`).

### 2.2 Limits of clamping: zero, the far edge — and nothing else

- **F8 (OBSERVED, live).** The **only** clamp is inside `setSplitterPosition`: `if (o < l) o = l; if (o > container[m] - splitter[m]) o = container[m] - splitter[m]`, where `container` is the pane's `offsetParent`, `m` is `clientWidth`/`clientHeight` and `splitter[m]` is the splitter's own thickness. So the divider may sit anywhere from the container's origin to `container axis size − 4 px`; the first pane's size is `o − l` and the second pane's is `calc(100% − (o + 4)px)` (a negative value the browser clamps to 0). **Every pane is collapsible to zero by dragging**, with no minimum visible area and no snap-back. Measured: dragging the catalog/plan splitter +5000 px stopped at catalog width `1598` px (viewport 1600 → plan pane 0 px); −5000 px stopped at catalog width `0` px. — `raw/probe1.json` (`dragFarRight`, `dragFarLeft`), `raw/js/sweethome3d.min.js` (`setSplitterPosition`).
- **F9 (OBSERVED, live).** The same applies on both inner dividers, and the residue is exactly the splitter itself. Dragging the plan/3D divider −6000 px gave plan height `2` px / 3D height `916` px; +6000 px gave plan `917` / 3D `1`, with `#home-3D-view style="top:919px; height:calc(100% - 919px)"`. Dragging the catalog/furniture divider −6000 px gave catalog height `0` px and furniture list `914` px (`#catalog-furniture-splitter top:0px`). No elastic band, no animation, no snap threshold. — `raw/probe4.json` (`collapse3DLimit`, `collapsePlanLimit`, `collapseFurnitureListLimit`).
- **F9b (OBSERVED, live).** The clamped value is **written into the home document immediately**: after a +100/+100/+50 px drag tour the home held `MainPaneDividerLocation="402"`, `PlanPaneDividerLocation="559"`, `CatalogPaneDividerLocation="695"` — exactly the *splitter* `left`/`top` pixels, not the pane sizes (pane widths measured 404/561/778 including the 2 px border and 4 px splitter). Before any drag all six layout visual properties read `null`. — `raw/probe5.json` (`A_propsInitially`, `A_propsAfterDrag`).
- **F10 (OBSERVED, live).** A double-click on any splitter is a no-op: `dblclick` is listened for only on the plan canvas and on tree tables, never on splitter elements. After a synthetic double-click on `#furniture-plan-splitter` and on `#plan-3D-view-splitter` the pane widths were unchanged (364 px before and after). — `raw/probe2.json` (`dblSplitter`), `raw/probe4.json` (`dblPlan3D`), bundle grep for `dblclick`.
- **F11 (DOCUMENTED).** Desktop's answer to the same problem is the two one-touch triangles of `setOneTouchExpandable(true)` plus the resize-weight pinning (F12). The web build ships neither. — `raw/src/HomePane.java`.
- **F12 (DOCUMENTED).** Desktop keeps a collapsed pane collapsed while the window is resized because a `DIVIDER_LOCATION_PROPERTY` listener rewrites `setResizeWeight(0)` when `getDividerLocation() <= 0` and `setResizeWeight(1)` when `divider + dividerSize >= width|height`, restoring `defaultResizeWeight` in between. This is explicitly commented *"keep invisible components hidden when the split pane is resized"*, and it is re-run once after restore from the document (`AncestorListener`). — `raw/src/HomePane.java`.
- **F13 (OBSERVED, live).** The web build's only resize hook is `windowResized`, which reads the splitter's computed `left`/`top` and re-clamps **only if** it now exceeds `container − splitter`; it never re-distributes space. Because the first pane is written in absolute px (F7) and the second in `calc(100% − x)`, all of a window's extra width goes to the **second** pane and the first keeps its pixel width. Measured on a coasting divider (catalog 406 px at a 1600 px viewport): the catalog stayed `408` px (incl. borders) at width 1200, at width 800 and again at 1400, while the plan pane took the whole delta (`1190 → 790 → 390 → 990` px); the vertical divider likewise kept plan height `561` at window heights 1000/700/1200 (3D pane `357 → 57 → 557` px). Desktop is different: `resizeWeight` 0.3 for the main split gives the first component 30 % of every future delta. — `raw/js/sweethome3d.min.js` (`windowResized`, `setSplitterPosition`), `raw/probe6.json` (`moderate_*`, `moderateH_*`), DOCUMENTED `raw/src/HomePane.java`.
- **F13b (OBSERVED, live).** A **collapsed** pane does stay collapsed across resizes (catalog left at 2/4 px at 1300 px and 1900 px width), because the clamp only ever fires in the "too big" direction. So the web port is safe for collapse but wrong for proportion. — `raw/probe5.json` (`A_collapseThenResize`).
- **F13c (OBSERVED, live).** A consequence worth calling out: **shrinking the window height can squeeze a pane almost to nothing without any user drag.** At 1600×700 the plan pane stayed at the height the user had dragged it to (`561` px, `top:559px`) and the 3D view was left with `57` px — the horizontal divider is never re-clamped for height, because `#plan-3D-view-pane`'s children use `calc(50% - 2px)` only until the first drag, after which the px value wins. There is no minimum for the *second* pane in the vertical axis. — `raw/probe6.json` (`moderateH_700`).

### 2.3 Collapsing, hiding and the responsive reflow

- **F14 (OBSERVED).** `isDisplayed()` is the per-splitter gate: `#furniture-plan-splitter` reports displayed iff `element.clientWidth > 0`; the catalog/furniture splitter additionally requires both child views to be non-null. `updateSplitter` clears every inline style first (`display`, `top`, `left`, pane `width`/`height`) and then sets `display:block` when displayed, `display:none` when not — i.e. **CSS decides the layout, JS only re-asserts the dragged value**. — `raw/js/sweethome3d.min.js`.
- **F15 (OBSERVED).** Collapse is therefore reachable three ways with no extra UI: (a) drag the divider to the edge (F8–F9), (b) let a CSS media query hide the splitter — coarse pointer + `max-width:743px` / `max-height:511px` hides *all* `.pane-splitter`s and re-shows only `#plan-3D-view-splitter` through nested orientation blocks (F19), or (c) shrink the window, which switches a splitter off through `isDisplayed()`/`clientWidth` as the CSS hides it (the clean 420×900 state in F19 is reached this way). Caveat on (c): my `raw/probe1.json viewportSweep` at 900×700 was taken *after* a drag, so its 2 px catalog is the drag (F8), not the viewport — I have no clean 900×700 measurement. — `raw/probe8.json` (`A_fresh420`, `B_plainResize420`), inline CSS l. 726–903.
- **F16 (OBSERVED, live).** Measured state in a 1600×1000 window, plain mouse, online build: `application-menu-toolbar` `display:none` (correct, it is the touch-only menu bar); `#level-selector` `display:none` because the home has fewer than two levels — the rule is *not* a media query but `HomePane`'s own `if (getLevels().length < 2) levelSelector.style.display = "none"` (bundle, `levelSelector`). The app's four regions are absolutely positioned against `<body>` starting at `y=82` (logo bar + 30 px toolbar), not inside `#home-pane`, which reports height 0; the site header is `position:fixed` and overlaid. — `raw/probe1.json` (`snapDesktop`, `paneVisibility`), `raw/js/sweethome3d.min.js` (`levelSelector`), round-1 `raw/sh3d-online.jsp.html` l. 1885.
- **F17 (OBSERVED, live).** Toolbar breakpoints on the online build: at 1600 and 1024 px the toolbar is `display:flex` with dotted group separators; at 700 and 420 px it becomes `display:block` and every `.toolbar-optional` button computes to `display:none` (the 800 px cutoff), while at 900/1024 they stay `inline-block`. — `raw/probe1.json` (`viewportSweep`), round-1 `raw/js/sweethome3djs.css`.
- **F18 (OBSERVED).** The panes themselves do **not** move at the 800 px/940 px breakpoints — only the toolbar reflows; the four regions keep the same pixel layout until the coarse-pointer rules apply. So the online build's "responsive" behaviour is (a) toolbar simplification for narrow windows and (b) a coarse-pointer-only re-flow — and the coarse re-flow is additionally gated on small-touch orientation blocks (F19d). With a mouse pointer at 900×700 nothing re-flows at all; the layout is the same absolute geometry as at 1600 px, minus width. — `raw/probe1.json` (`viewportSweep`), `raw/probe7.json` (`landscapeTouch1100x700`).
- **F19 (OBSERVED, live, coarse pointer).** The *intended* phone layout, measured twice from a clean state (fresh load at 420×900, and a plain 1100×820 → 420×900 resize with no prior drag): the catalog becomes a bottom strip (`#catalog-furniture-pane` at `y=775`, `410×80`; `#furniture-view` `display:none`), and of the three splitters **only `#plan-3D-view-splitter` is shown** — `display:block`, `x=5,y=386,w=410,h=8` — while `#furniture-plan-splitter` and `#catalog-furniture-splitter` are `display:none` with `clientWidth 0` (so `isDisplayed()` is false for exactly those two). Both clean paths produced byte-identical geometry. — `raw/probe8.json` (`A_fresh420`, `B_plainResize420`), `raw/probe7.json` (`shrunk420`).
- **F19c (OBSERVED, live, coarse pointer) — the phone transition is not idempotent.** If a divider was dragged first, the same shrink to 420×900 leaves the stale inline pixel geometry in place: `#furniture-plan-splitter` came back `display:block; left:412px` (so the catalog pane stays 412 px wide inside a 420 px viewport), the plan/3D pane is squeezed to **`clientWidth 0`**, `#catalog-furniture-splitter` reappears at `x=6,y=831,w=412,h=8` — i.e. two dividers that the CSS had just hidden are re-shown *outside* the phone strip layout. The numbers are self-consistent with the code rather than random: the divider had been persisted as `429`, and on the next `updateSplitter` the re-apply ran through `setSplitterPosition(429)`, whose upper clamp is `container − splitter = 420 − 8 = 412`, hence `left:412px`. In a second run of the same sequence the opposite happened: all three splitters ended `display:none` with every inline style cleared (`raw/probe7.json shrunk420`) instead of the one-splitter phone layout. Either way the result is order-dependent and differs from the clean case, so the transition depends on history rather than only on the viewport. — `raw/probe8.json` (`C_afterDrag1100`, `C_afterDrag420`, `C_phoneDrag`), `raw/probe7.json` (`afterDrag`, `shrunk420`).
- **F19d (OBSERVED, live, coarse pointer).** The plan/3D axis flip is gated on **both** conditions: it only becomes vertical in the small-touch layout *and* landscape ≥5:4. At 700×420 (small-touch, aspect 1.67) the splitter measured `x=421, w=8, h=370` with plan `268×370` left and 3D `267×370` right; at 1100×700 (aspect 1.57 but **not** small-touch) it stayed horizontal (`y=486, w=653, h=8`). — `raw/probe4.json` (`touch_700x420`), `raw/probe7.json` (`landscapeTouch1100x700`), inline CSS l. 862–899.
- **F19b (OBSERVED, live, coarse pointer).** Splitters are genuinely draggable with the page's own event path: it moved the catalog from 302 px to 82 px and set `left:80px`; at 1100×820 coarse the catalog/plan drag committed `MainPaneDividerLocation="429"` and the plan/3D drag committed `PlanPaneDividerLocation="481"`, with the 8 px splitter thickness preserved in `left:429px`. Touch layout logic is the same `updateSplitter` code path as the mouse, via its `touches[0]` branch. — `raw/probe4.json` (`touchDrag`), `raw/probe7.json` (`afterDrag`).
- **F20 (OBSERVED).** `updateSplitters()` re-derives the axis mapping at runtime: if the catalog view's bounding box top is more than 10 px below the 3D view's top, it swaps `plan3DViewSplitter.firstGroupElement`/`secondGroupElement`. This is exactly what keeps the *same* three splitter descriptors correct after the landscape/portrait flip of F19 — the plan/3D divider stops being "top = plan" and becomes "left = plan". — `raw/js/sweethome3d.min.js` (`updateSplitters`).
- **F21 (OBSERVED).** `addOrientationChangeListener` unconditionally installs a single `window` `resize` listener; its handler body first checks `window.matchMedia("(hover: none), (pointer: coarse)").matches` and, only then, removes the inline `style` attribute from `#plan-3D-view-splitter`, `#home-plan` and `#home-3D-view`, revalidates both views, and re-runs `updateSplitters()` on a 100 ms timeout. So the listener exists on a desktop pointer too, but is a no-op there; on a coarse pointer it is the mechanism that empties the styles and lets `updateSplitters` re-derive both the pane roles and the divider positions. Note the reset targets only the plan/3D trio by id, never the catalog side — which is consistent with the phone layout that keeps only `#plan-3D-view-splitter` (F19). — `raw/js/sweethome3d.min.js` (`addOrientationChangeListener`), `raw/probe8.json` (`B_plainResize420`).
- **F22 (OBSERVED).** There is **no menu action anywhere that hides or shows a pane**. The only pane-removal affordance is the desktop-only "Display in separate window / Display in main window" (`DETACH_3D_VIEW`/`ATTACH_3D_VIEW`), which replaces the 3D view inside the split pane by a dummy panel, sets `dividerSize = 0`, and stores the divider as a *fraction* (0.0 or 1.0) in `.detachedViewDividerLocation` so that re-attaching restores the old split. In the online build this is a no-op (`HomePane.prototype.detachView = function(){}`), so the web user cannot take a pane out at all. — `raw/src/HomePane.java` (`detachView`, `attachView`), `raw/js/sweethome3d.min.js` (stubs), round-1 F6/F45.
- **F23 (DOCUMENTED).** Desktop has `Swing Home 2D` mode (`-Dcom.eteks.sweethome3d.no3D=true`) which removes the 3D view (and the 3D menu, photos, videos, model import) entirely — the only supported way to run with **two** panes instead of four. The FAQ presents it as a fallback for machines without 3D. This is the real "collapse the 3D pane" feature the desktop product has and the web build does not. — round-1 `raw/faq.txt`; <https://www.sweethome3d.com/faq.jsp>.

### 2.4 Pane focus, Tab order and the focus rectangle

- **F24 (DOCUMENTED).** *"Each pane may have the focus (i.e. receive keyboard input) … recognizable by the coloured rectangle that surrounds it; for example, the home plan has focus in figure 2. To transfer focus to another pane, use Tab and Shift+Tab, or click in the pane that should gain focus."* — user guide §1 (round-1 `raw/userguide.txt` l. 175) and its German counterpart `raw/de-userguide.txt` l. 175 ("Jeder Bereich kann den Fokus haben … der durch das farbige Rechteck, das ihn umgibt, erkennbar ist").
- **F25 (DOCUMENTED).** On desktop the focus→controller link is `FocusOwnerChangeListener`: on `focusOwner` change it tests which of the four view components contains the new owner and calls `controller.focusedViewChanged(view)`, remembers `lastFocusedComponent` for the clipboard actions, and installs the `specialKeysListener` (Space = temporary pan mode, macOS Ctrl/Cmd specials). Leaving the plan view restores the previous plan mode. — `raw/src/HomePane.java`; round-1 `raw/js/sweethome3d.min.js` (`focusedViewChanged`, `addFocusListener`).
- **F26 (OBSERVED, live).** The online build registers a `focusin` listener on the whole pane which walks `event.target.parentElement` upward and calls `focusedViewChanged(view)` **only for `#home-plan` and `#home-3D-view`** — the catalog and furniture-list views are not part of the mapping. So `selectAll`, clipboard targeting and similar focus-dependent verbs have exactly two possible owners online, not four. — `raw/js/sweethome3d.min.js`; `raw/probe2.json` (`controllerProbe` was empty — no controller object is exposed on `window`).
- **F27 (OBSERVED, live).** The DOM declaration matches: `#home-plan` `tabindex="1"`, `#home-3D-view` `tabindex="2"`, `#furniture-catalog` `tabindex="-1"`, `#furniture-view` `tabindex="-1"` — identical in the shipped JSP template and in the live DOM. Every toolbar button is also `tabIndex = -1` (set in `createToolBarButton`), and open popup menus get `tabindex="1000"`, so the two canvas panes are the only app-level Tab stops. — round-1 `raw/sh3d-online.jsp.html` l. 1877–1887, round-1 `evidence/studio_dom.html`; `raw/probe1.json` (`focusProbe.tabIndex`), `raw/js/sweethome3d.min.js`. 
- **F28 (OBSERVED, live).** A real Tab tour starting from `#home-plan`: plan → 3D view → **the sweethome3d.com page chrome** (`#quick-wins-store-link`, `#close-button`, header items…) and never the catalog or the furniture list. Pressing Tab in a pane therefore leaves the application entirely once the two tabbable panes are exhausted — there is no focus trap and no cycle between the four panes. — `raw/probe2.json` (`tabTour`).
- **F29 (OBSERVED, live).** There is **no visible focus ring on either tabbable pane**: CSS sets `#home-plan:focus, #home-3D-view:focus { outline: none; }`, and the live `getComputedStyle` reports `outline-style: none` for both (and for the two non-tabbable panes too). The desktop's coloured focus rectangle (F24) has no online counterpart — the only way an online user knows which pane has focus is that arrow keys/Delete act on the plan. — `raw/probe1.json` (`focusProbe.outlines`), round-1 `raw/js/sweethome3djs.css`.
- **F30 (OBSERVED).** The web build does not implement `hasFocus()` anywhere (no occurrences in the bundle), consistent with the missing focus decoration; the plan canvas paints selection outlines from `getSelectionColor()` regardless of focus. — bundle grep; `raw/js/sweethome3d.min.js`.
- **F31 (INFERRED).** The combination F25–F29 explains a round-1 puzzle: online, focus-dependent state is only tracked for two views and is invisible, so a user who clicks the catalog and then presses a shortcut has no feedback that the app considers the plan (or nothing) focused. That is a UX regression of the web port rather than a design choice — desktop's four-view `focusableViews` array is literally narrowed to two in the browser build.

### 2.5 Persistence and defaults

- **F32 (OBSERVED, live).** All three divider positions are stored with the *home*, under the keys round 1 found (`HomePane.MAIN/CATALOG/PLAN_PANE_DIVIDER_LOCATION_VISUAL_PROPERTY`, all prefixed `com.eteks.sweethome3d.SweetHome3D.`) plus `.detachedViewDividerLocation` for the detached case. The web handler commits on `mouseup` (not on every mousemove) — `j.controller.setHomeProperty(c.homePropertyName, n.currentPosition == null ? null : n.currentPosition.toString())`. Live proof: `home.getProperty(...)` was `undefined` for all six layout keys before any drag, and `"402"` / `"559"` / `"695"` after dragging catalog/plan, plan/3D and catalog/furniture dividers — matching the splitter inline `left`/`top` exactly. The two pane-scroll keys (`PlanViewportX/Y`, `FurnitureViewportY`) are wired the same way (`planView.scrollPane.scrollLeft/Top` read on init, written on every `scroll`); see F33 for the live trigger. — `raw/js/sweethome3d.min.js`; `raw/probe5.json` (`A_propsInitially`, `A_propsAfterDrag`).
- **F33 (OBSERVED, live).** The scroll offsets of the two scrollable panes travel in the home too: `PLAN_VIEWPORT_X/Y` are restored into `planView.scrollPane.scrollLeft/Top` at init and written back on every `scroll`; `FURNITURE_VIEWPORT_Y` is the analogous key for the furniture table (round-1 F5). Live: the plan's inner scroll container is `div#home-plan.scrollPane` (and it is the element with `clientHeight < scrollHeight`, not `#home-plan` itself); setting its `scrollTop = 25` and firing `scroll` wrote `PlanViewportY="25"` onto the home (`PlanViewportX` went from `null` to `"0"` — the content was not wider than the viewport, so the X offset could not move). — `raw/js/sweethome3d.min.js`; `raw/probe6.json` (`scrollProbe`).
- **F33b (OBSERVED, bundle).** The furniture list has its own equivalent write path — a `scroll` handler on the list's scroll pane stores `FurnitureViewportY` and the same key is re-applied at init — so **all three** scrollable panes (plan X, plan Y, furniture list Y) persist per home. There is no `PlanViewportX`-for-3D analogue: the 3D camera lives in `Camera` objects inside the home model, not in a visual property. — `raw/js/sweethome3d.min.js`.
- **F34 (OBSERVED, live).** In the *unregistered* online build the home is not persisted at all (the page warns that registration is needed), and no home state reaches `localStorage`. After a drag + `page.reload()` the splitter was back at its CSS default; the only `localStorage` key present after a full session was `user_pseudo_id` (Firebase), plus cookies `JSESSIONID` and `__cflb`. The online editor's persistence channel is the server-side Online Manager recorder, not the browser. — `raw/probe1.json` (`afterDragStorage`), `raw/probe2.json` (`afterDragStorage`, `afterDragCookies`), `raw/probe4.json` (`afterReload`).
- **F35 (OBSERVED).** The demo `Studio.sh3x` that round 1 extracted contains *no* divider properties — it was authored before those were first saved, so a fresh open takes the CSS/Swing defaults (catalog 300 px, list bottom 30 %, plan/3D 50/50) and the first drag is what makes the document self-describing. Confirmed live: after loading the Studio demo the home's `visualProperties` object was empty (`{}`) and all six layout keys `undefined`. — round-1 `raw/studio/Home.xml`; `raw/probe5.json` (`A_homeHint`).
- **F36 (DOCUMENTED).** Defaults differ between desktop and online because they are *not* the same numbers: desktop main divider 360 px × HiDPI scale (≈22.5 % of a 1600 px window), and online catalog 300 px fixed by the inline stylesheet with the furniture list at `top: 70%`. History shows desktop divider restore bugs were fixed historically (*"Fixed a bug that didn't restore correctly the saved location of view splitters for maximized windows"*), which is the class of bug the web port's px-only model is exposed to (F13). — `raw/src/HomePane.java`, round-1 `raw/history.txt` l. 881.

### 2.6 Ordering of the panes and locale/RTL

- **F37 (DOCUMENTED).** The desktop honours component orientation: for right-to-left locales the catalog pane goes on the *right*, the divider default flips to 670 px, and `defaultResizeWeight` flips to 0.7; a `componentOrientation` property listener swaps the two components at runtime. There is no online equivalent — the CSS pins `#catalog-furniture-pane { left: 0 }` and `#plan-3D-view-pane { left: 304px }`, so an RTL locale keeps the left-to-right arrangement. — `raw/src/HomePane.java` (`createMainPane`), round-1 `raw/js/sweethome3djs.css`.
- **F38 (OBSERVED).** Online the splitter's "first/second" assignment is geometric (F20) rather than locale-driven, which is how the same code survives the landscape portrait flip; RTL is simply not modelled. — `raw/js/sweethome3d.min.js`.

### 2.7 What the online build drops

- **F39 (OBSERVED + DOCUMENTED).** Drop list for the four-pane workspace online, relative to desktop:
  | Desktop behaviour | Online status |

### 2.8 Cross-cutting inferences

- **F40 (INFERRED).** Writing the drag handler once per splitter descriptor (`updateSplitter`) and only re-deriving the child order when the layout flips is the cheap way to keep a *four-region* information architecture across mouse/touch portrait/landscape without a per-mode UI. It also explains why the web port inherited the desktop's persistence model unchanged (same keys, same commit-on-release) even though its rendering model is completely different.
- **F41 (INFERRED).** The `resizeWeight` pinning (F12) and the `isChildComponentInvisible` traversal policy (F4) are two halves of one desktop invariant: *a collapsed pane is still a pane* — it keeps its divider value, its focus cannot be entered, and a window resize will not silently re-open it. The web port reproduced neither half, which is why its collapse is a pixel accident rather than a mode.
- **F42 (INFERRED).** The missing focus rectangle (F29) is not an omission forced by the browser: `#home-plan` has a real `focus` state and the CSS deliberately turns the outline off (probably to avoid a box around the plan canvas). A one-line `:focus` outline or a 1 px inset border on the two panes would restore the desktop's most useful affordance at zero architectural cost.

- **F43 (INFERRED).** `updateSplitter` **deletes** and rebuilds a splitter's listener record (`delete c.mouseListener`) on every run, but it never invalidates the *persisted* divider value: on the coarse-pointer resize path, `addOrientationChangeListener` empties the three plan/3D inline styles and `updateSplitters`/`updateSplitter` immediately re-apply the value still held in the home (`updateSplitter` does `n.setSplitterPosition(h)` whenever the property is non-null and the splitter is displayed). That round trip — clear, then re-apply the stale number — is what produces the F19c `429 → 412` clamped `left:412px`: the layout is re-derived from *stale state*, not from the phone layout's own geometry. A layout engine that renders only from current viewport + intent would not have this failure mode.
- **F44 (INFERRED).** The asymmetry in F7 — first pane absolute px, second pane `calc(100% − x)` — is what makes the web port *look* correct on first use (the pane you drag follows the cursor exactly) while quietly producing the two worst artefacts: no proportional re-distribution on resize (F13) and no minimum for the second pane (F13c). A single `flex-basis`/percentage pair, or two `grid-template-columns` tracks with `minmax()`, would fix all three at once.

## 3. Ideas for CasaPlazAI (ranked by value / effort)

Ranking = value for a single-workspace web floorplanner, then effort. Each item names the finding it comes from. Where relevant it is tied to `src/shared/schema/types.ts` / `casaplazai-schema.md` (schema v1) and to CasaPlazAI's out-of-schema editor keys (`casaplaza.snap.settings.v1`, `casaplaza.underlay.v1`).

| # | Idea | Why (finding) | Value | Effort |
|---|------|----------------|-------|--------|
| 1 | **Give the splitter a real "collapse" state, not just a 0 px drag.** Persist `{collapsed: boolean, size: number}` per divider, snap shut below a small threshold (~24 px), and show a grab handle on the collapsed edge so the pane can be reopened. | F8–F10: the reference app lets you zero a pane but gives you no way back except a pixel-perfect drag; desktop solves it with one-touch arrows (F11), the web build doesn't. | High | Low–Med |
| 2 | **Remember divider sizes as proportions, and clamp `[min, max]` instead of `[0, container-4]`.** | F12/F13/F13c: desktop pins `resizeWeight` so a collapsed pane stays collapsed *and* extra space is distributed by weight; the web build's px-only model leaves the split at an arbitrary fraction of the window (catalog 408 px at both 1600 and 800 px, and the 3D pane squeezed to 57 px at 1600×700). | High | Low |
| 3 | **Draw a visible focus/active indicator on the pane that owns the keyboard**, and make Tab a closed cycle over Plan → 3D → inspector → tool card. | F24, F28, F29: this is a documented desktop affordance (coloured rectangle) that the online build lost; CasaPlazAI's Plan/3D/Walk modes make "which pane has keys" ambiguous. | High | Low |
| 4 | **Do not route Tab out of the app.** Trap focus in the workspace and use Tab only between panes once the canvas has focus; provide an explicit Escape/explicit close for the tool card. | F28: measured online, two Tabs put focus into the marketing page around the app. | High | Low |
| 5 | **Persist per-pane viewport state with the plan** (plan zoom/pan centre, inspector scroll + sort + visible columns), alongside the existing localStorage autosave. | F32, F33 and round-1 F5/F40; CasaPlazAI already persists out-of-schema editor state under `casaplaza.*` keys, so pane state belongs there or in a `casaplaza.workspace.v1` key — *not* in `FloorplanData` (the schema doc explicitly keeps editor state out of the interchange contract). | High | Low |
| 6 | **Make the responsive breakpoints a documented contract, not ad-hoc `@media`s.** Three named widths — desktop (3 panes + inspector), tablet (splitter widths ×2, plan/3D side by side), phone (tools bottom strip, inspector as a sheet) — and one place that decides which of them is active. | F17–F21 / F19c: the reference flips the plan/3D divider's axis and doubles splitter thickness for touch, but it also *loses* the user's pane sizes when it enters and leaves the phone strip layout; a named tier table makes that transition explicit and testable. | Med–High | Med |
| 7 | **Re-derive pane roles from geometry, not from hard-coded left/top.** Keep a descriptor per divider (`first`, `second`, axis) and recompute the mapping after an orientation/layout change. | F20: this single trick is what lets Sweet Home 3D reuse three splitters across portrait/landscape. It is also what makes a future "3D on the left" preference cheap. | Med | Low |
| 8 | **Snapshot the workspace layout into the plan file *and* restore it on share-link load**, defaulting gracefully when the key is absent. | F34/F35: the reference demo home carries no divider properties and simply falls back to defaults — a robust pattern for a schema that must stay backwards-compatible (`migrate.ts` hook, never break shipped types). | Med | Low |
| 9 | **Add an explicit "only 2D" / "only 3D" workspace mode** rather than relying on the user collapsing a pane by dragging. | F23: desktop ships `Sweet Home 2D` for machines without 3D; a single-workspace web app benefits from a deliberate two-pane mode, and it is also the zero-WebGL fallback. | Med | Med |
| 10 | **If/when a "detach 3D" style affordance is ever wanted, store it as a fraction of the pane axis (0.0/1.0) plus the pane's own window rect, exactly as desktop does.** | F22: the desktop detach stores `detachedViewDividerLocation` as a ratio, so re-attaching restores the old split without a pixel-drift bug. Low priority for a single-window web app. | Low | Med |
| 11 | **Make layout re-derivation idempotent and cheap enough to run on every resize**, and rebuild any drag listeners in the same pass — never leave a stale listener attached to stale geometry. | F43/F19c: the reference tears down and reinstalls its splitter listeners in `updateSplitter`, and exactly that mixture of cleared styles and surviving inline pixels is why its phone layout differs depending on drag history. A layout engine that only ever *renders from state* avoids the whole class of bug. | Med | Med |
| 12 | **Persist the inspector column widths/sort and the plan scroll offset as one `casaplaza.workspace.v1` object**, applied on load with a "if absent, use defaults" path — never folded into `FloorplanData`. | F32/F33b/F35: the reference keeps all of these in per-home visual properties, and its demo home simply has none — proof that a missing key must be a valid, defaulting state in a schema that guarantees backwards compatibility. | Med | Low |

## 4. Unknowns

- **Cross-session persistence in the registered Online build.** I could not register (rules forbid account creation), so I could not confirm that the Online Manager actually round-trips the three divider properties through a saved home. I confirmed the write path in code (F32) and the absence of any browser-side persistence (F34).
- **Desktop one-touch arrows visually.** I never ran the Java app (no desktop installer allowed), so the one-touch triangles, the coloured focus rectangle and the Windows divider-size change are DOCUMENTED from source/history, not OBSERVED. The shortcut sheet has no documented *keyboard* binding for splitter resize either — round 1's Unknown stands, and the source I read has no `VK_` handler for it, so "no keyboard resize" is now INFERRED at high confidence rather than unknown.
- **iOS/Android real-device behaviour.** F19/F19b–F19d are Chromium `isMobile/hasTouch` emulation at `deviceScaleFactor: 2`; the real Safari/Chrome viewport behaviour (visual viewport, scrollbars, `touch-action`, and whether `(hover:none)`/`(pointer:coarse)` resolve identically) may differ. In particular the phone layout may be cleaner on a real device than the F19c order-dependent state, because a real phone resizes once at load rather than mid-session.
- **Which of the two F19c outcomes is canonical.** I saw the stale-inline state once and the fully-hidden state once, from nominally the same drag-then-shrink sequence. I could not pin the discriminator (timing of the resize vs. the coalesced redraw, or which splitter had last been dragged), so the *class* of problem is established and the exact trigger is not.
- **Performance during continuous drag.** The web handler sets `continuousLayout`-equivalent inline styles on every mousemove and calls `revalidate()` on both views only after release; I measured geometry, not frame timings, so I cannot say whether the plan/3D re-render is throttled when the divider crosses a 3D canvas.
- **Exact desktop divider width.** `SplitPane.dividerSize` comes from the UI theme and is then multiplied by `getResolutionScale()`; I did not run the app, so I have no pixel value (the history note says it was *increased* for Windows).
- **Whether the online build's `outline: none` is deliberate or an artefact** of the page's own stylesheet (the rule lives in `sweethome3djs.css`, i.e. the app itself, not the site customisation) — the rule is app-shipped, but the intent is not documented.
- **Terminal/`detachedView` stubs under a real 7.5 desktop build** may differ from the 7.5+dfsg-1 Debian source if 7.5.2 changed `HomePane`; the bundled JS self-reports 7.5.2 while the Debian source is 7.5. I did not diff them.

### Reproduction

All live measurements come from eight headless-Chromium scripts in `scripts/` driving the real `SweetHome3DJSOnline.jsp` with `chromium.launchPersistentContext` (Playwright-core shipped inside `rea-agents`), software WebGL via `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`. Splitters were exercised by dispatching `mousedown`/`mousemove`/`mouseup` (and `touchstart`/`touchmove`/`touchend`) directly on the splitter element, because `page.mouse.down/move/up` did not reliably reach the capture-phase listeners. Each run loads the page, clicks the third demo ("Studio") and waits ~26 s for the home to finish loading. Runtime ~90 s per desktop probe, ~150 s per probe that also launches the coarse-pointer context.
