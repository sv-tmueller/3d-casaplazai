## 1. Summary (5 bullets)

- **The browser edition's first screen is a blocking demo chooser, not an editor (OBSERVED).** On load, `#demo-choice` covers the whole app area with a 70 %-grey overlay and a centred table titled *"Select a demo"* — a 3×3 grid of thumbnails + links (`Empty home`, `Studio`, `1-Bedroom apartment`, `2-Bedroom apartment`, `3-Bedroom apartment`, `Apartment with bow window`, `2-Bedroom house with basement`, `3-Bedroom house with attic`, `3-Bedroom house with mezzanine`). There is **no close button, no Escape, no "skip"** — the only way forward is to pick one. Behind it the app chrome does not exist yet (0 toolbar buttons, 0 catalog icons in the DOM; after loading: 29 and 805).
- **The desktop app's first screen is the opposite: an empty default home (DOCUMENTED).** "To create a home, simply use the default home created at Sweet Home 3D launch or click on the New home button in the tool bar" (<https://www.sweethome3d.com/users-guide/>). The 9-demo chooser is hidden behind **File ▸ New from demo…**, a dialog titled *"New home from demo"* with buttons *"Use selected demo" / "Find more demos" / "Cancel"* (vendor resource bundle); the user guide **never mentions it**.
- **Tips are a per-tool, one-shot dialog — the desktop's only in-app coaching (DOCUMENTED + OBSERVED).** Five creation tools (walls, rooms, polylines, dimensions, texts) each show an HTML tip **the first time that tool is used**, with a *"Do not display this tip again"* checkbox; **Preferences ▸ "Reset the display of tips"** restores them all. The trigger is `HomeController.setMode` → `showActionTipMessage(tool)` → mark ignored (vendor JS bundle). Added in **v1.5, Dec 2008**, unchanged since.
- **The browser edition ships with the learning aids switched off (OBSERVED).** The online JS bundle contains **zero** occurrences of `HelpController`/`HelpPane`/"Sweet Home 3D Help", `HelpController.help = function(){}` (R1-F45), and `showActionTipMessage` returns `false` — so no help window and no tips online, even though `raw/localization.json` carries the full help string set. The online toolbar has 29 buttons including **About** but **no Help button** (`#toolbar-button-HELP` count = 0).
- **"First 5 minutes" ends with almost no guidance and no persistence (OBSERVED).** After picking *Empty home* an `alert()` warns *"your design won't be saved … register for free"*, then you land in a fully-enabled empty workspace. `localStorage` contains only Firebase analytics keys and cookies; **no home, no preferences, no tip state**. I found **no quick-start page, no first-run tour, and no welcome screen** in vendor documentation.

## 2. Findings

### 2.1 What the browser edition shows in the first seconds (OBSERVED, live)

- **F1 (OBSERVED).** `evidence/A_settle_a11y.txt` (12 s after navigation to `SweetHome3DJSOnline.jsp`, before any click) contains, after the site header, a table whose first row is `row "Select a demo"` followed by three image rows and three label rows: `Empty home | Studio | 1-Bedroom apartment`, `2-Bedroom apartment | 3-Bedroom apartment | Apartment with bow window`, `2-Bedroom house with basement | 3-Bedroom house with attic | 3-Bedroom house with mezzanine`. It is the **first and only app content** in the accessibility tree.
- **F2 (OBSERVED).** `evidence/A_settle_html.html`: the overlay is `<div id="demo-choice">` — **no inline `display:none`** and **no `style` attribute at all**, so it is visible by default; the page's own `viewHome()` sets `style.display = "none"` when a demo is chosen (same inline script quoted in R1-F42). CSS from `raw/sh3d-online.jsp.html`: `position:absolute; top:50px; left:0; right:0; bottom:0; z-index:1000; background-color:rgba(128,128,128,.7)`; the inner `<table>` is `rgba(208,208,208,.9)`, centred, font-size 90 %.
- **F3 (OBSERVED).** The chooser is **not dismissible**: `evidence/A_settle_html.html` has no close/×/skip control inside `#demo-choice`, and the page defines no Escape handler for it. Every path forward is one of the 9 tiles.
- **F4 (OBSERVED).** Tiles are plain `<img class="demo-image" onclick="viewHome('…')">` plus `<a onclick="viewHome('…')">` — **no `href`** (0 of 7 checked anchors had one) and no `tabindex`, so the chooser is pointer-only and each click also fires a Firebase event `wce_onlinetool_select demo`. Accessibility gap worth noting for CasaPlazAI in reverse: this is the pattern to avoid.
- **F5 (OBSERVED).** Each demo is a compressed `.sh3x` under `/examples/`, with a matching `.png` thumbnail: `/examples/EmptyHome.sh3x`, `Studio.sh3x`, `1BedroomApartmentWithRoundWall.sh3x`, `2BedroomApartment.sh3x`, `3BedroomApartment.sh3x`, `2BedroomApartmentWithBowWindow.sh3x`, `2BedroomHouseWithBasement.sh3x`, `3BedroomHouseWithAttic.sh3x`, `3BedroomHouseWithMezzanine.sh3x` (9 files = 8 furnished homes + Empty home). `viewHome()` calls `application.getHomeRecorder().readHome(homeUrl, recorderObserver)`.
- **F6 (OBSERVED).** At first load the app is **not** merely hidden behind the overlay — it is unbuilt. `evidence/A_settle_html.html`: `id="toolbar-button-…"` matches = **0**, `class="furniture-icon"` = **0**, while `id="home-pane-toolbar"`/`catalog-furniture-pane` shell exists; `evidence/B_after_alert_html.html` (after picking Empty home) has **29** toolbar buttons and **805** catalog icons. The chooser therefore gates the whole workspace render, not just its visibility.
- **F7 (OBSERVED).** Two monetisation/dialog overlays compete with the chooser in a fresh profile: a top "Full version available / Get access to over 1,600 3D models… / Download" banner, a dismissible bottom-right "Full version available" banner, and an **iubenda cookie `alertdialog` "We use cookies"** with `Learn more and customize / Reject / Accept` (present in every `A_*`/`B_*` a11y snapshot). R1-F48 observed the banners; I confirm the cookie dialog sits **on top of the demo chooser** in the pre-consent state, so a first-time visitor meets two overlapping modal surfaces.
- **F8 (OBSERVED).** `evidence/scenarioA.json` storage artifact: `localStorage` = `[{name: user_pseudo_id}]` (hashed), `sessionStorage` = `first_visit_logged`, `ip_address` (hashed), cookies `JSESSIONID`, `__cflb`. **No home data, no preferences, no tip flags.** So the chooser reappears on every page load, and nothing the user does in the first 5 minutes survives a reload until they register (R1-F42/F44).

### 2.2 Empty home → the empty workspace (OBSERVED, live)

- **F9 (OBSERVED).** `evidence/B_pick_empty_a11y.txt` (immediately after clicking the *Empty home* link) still shows the surrounding site and the cookie dialog; `evidence/B_after_alert_html.html` contains the alert text `Keep in mind that your design won't be saved! If you want to save it, go first to Online page and register for free.` — matching R1-F42's quote of the page's own `setTimeout(..., 500)` in the inline script, i.e. the warning fires **0.5 s after** the pick and is the user's first feedback.
- **F10 (OBSERVED).** `evidence/B_after_alert_a11y.txt` is the full empty-workspace toolbar: View-from-top · View-from-observer · Can't Undo · Can't Redo · Delete · Cut · Copy · Paste · Add catalog furniture · Select · Pan · Create walls · Create rooms · Create polylines · Create dimensions · Add texts · Disable magnetism · Lock base plan · Flip H/V · text-size · bold · italic · Zoom in · Zoom out · **About** · **Preferences** — **no Help button** (consistent in `A_settle_html.html` and `B_after_alert_html.html`: `#toolbar-button-HELP` = 0). Catalog dropdown lists the 13 categories, search box present, 805 pieces loaded.
- **F11 (OBSERVED).** The empty workspace after Empty-home is genuinely empty: furniture list has **0** body rows (`div row="true"` = 0 in `evidence/B_after_alert_html.html`) and `#level-selector` is `display:none`. Round-1's Studio load (R1-F2/F39) is the furnished counter-example.
- **F12 (OBSERVED).** No tour, tip, coach-mark, dialog or welcome panel appears at any point in `evidence/B_after_alert_a11y.txt` after the alert. The first 5 minutes online = cookie dialog → demo chooser → alert → empty plan grid + full toolbar + catalog. Nothing else.

#### 2.2.1 The online first-run state machine, in the page's own words (OBSERVED, `raw/sh3d-online.jsp.html`)

- **F12a (OBSERVED).** The page's inline script defines the whole first-run flow in ~15 lines, and it is instructive how little there is. `viewHome(homeUrl)` does exactly three things: hide `#demo-choice`; after **100 ms** show `#progressDiv` **unless** the URL is `EmptyHome.sh3x`; and after another **500 ms**, for `EmptyHome.sh3x` only, fire the `alert(...)`. The furnished demos therefore do get a `#progress`/`#progressLabel` bar, the blank path does not — the empty path is deliberately the *unceremonious* one.
- **F12b (OBSERVED).** Failure states are first-run-relevant because they are the only message a new user may see: `recorderObserver.homeError(err)` writes into `#progressLabel` — `No WebGL` → *"Sorry, your browser doesn't support WebGL."*; HTTP 403 → *"User not logged in. Please log in to continue your design."*; HTTP 404 → *"This home doesn't exist."*; anything else → `Error: <constructor> <message>` plus `console.error`. None of these has a retry or a "pick another demo" action, so a failed load strands the user on the chooser with a message.
- **F12c (OBSERVED).** Two more behaviours fire only after a successful demo load: the app installs a `beforeunload` guard — *"Some modifications have not been saved to the server yet. Do you want to leave the page now and lose them?"* — and, on `unload`, `application.deleteHome(home)`. So the online session's home is **ephemeral by design**, which is the technical counterpart to the `Empty home` alert in F9.
- **F12d (OBSERVED).** The online onboarding also seeds **one editor preference** on load: `preferences.setNewRoomFloorColor(0xFF9999A0)` — a pink fill for new rooms, applied by the host page, not by the core. It is a small but real precedent for "the embedding page customises a sensible default for its users", independent of tips or demos.

### 2.3 The desktop first 5 minutes (DOCUMENTED, vendor sources)

- **F13 (DOCUMENTED, verified directly this round).** Launch behaviour. Vendor guide: "To create a home, simply use the **default home created at Sweet Home 3D launch** or click on the New home button in the tool bar" — <https://www.sweethome3d.com/users-guide/>. The vendor's own in-app help source says it precisely: *"To create a home, simply use the **default empty document created at Sweet Home 3D launch**, choose File ▸ New or select one of the demos available in the dialog box displayed by **File ▸ New from demo**."* (`creatingHome.html`, revision r9047 — fetched and read directly at <https://sourceforge.net/p/sweethome3d/code/HEAD/tree/trunk/SweetHome3D/src/com/eteks/sweethome3d/viewcontroller/resources/help/en/creatingHome.html?format=raw>). The same page documents the new-home defaults: floor **10 × 10 m** and new-wall height from the *New walls height* preference.
- **F14 (DOCUMENTED).** A splash screen exists but is transient and is documented mainly through its failure mode: FAQ *"When I run Sweet Home 3D, only a splash screen appears during a few seconds. What happened?"* → answer attributing it to graphics-card configuration (<https://www.sweethome3d.com/faq/>; the answer points at the 3D-driver error). History v1.1 records "Modified splash screen" (`raw/history.txt`).
- **F15 (DOCUMENTED).** Relaunch behaviour changed early and never reverted: history v0.17 records "**No new empty home is created at application relaunch**" and "The first untitled and unmodified home is automatically closed when an other one is opened" (`raw/history.txt`). So the desktop app does **not** re-greet a returning user with a fresh document.
- **F16 (DOCUMENTED).** The user guide's *Starting a new home* section begins with an action the user would not guess: "**Before proceeding further, display the preferences dialog box** … Check the default unit used in the program, the default thickness and height of walls, and other preferences", and then lists the 8 suggested steps (import blueprint → draw walls → edit walls → add doors/windows → add furniture → draw rooms → add levels → dimensions/texts) (<https://www.sweethome3d.com/users-guide/>). That preference check is the guide's *step 0*; there is no "quick start" or "first 5 minutes" page anywhere on the site.
- **F17 (DOCUMENTED).** The guide names exactly two onboarding entry points inside the app: the **Help button found in the tool bar** and **Help ▸ Sweet Home 3D Help**, plus "view Sweet Home 3D video tutorials … and learn more advanced tips" (<https://www.sweethome3d.com/users-guide/>, <https://www.sweethome3d.com/documentation/>). It names **no** welcome screen, **no** demo chooser on startup, and **no** first-use tip. Third-party beginner guides and vendor blog posts describe the same empty split-screen launch (see §2.7).
- **F18 (DOCUMENTED).** "Check updates at program launch" is a Preferences checkbox and there is a modal *"Available updates"* message with its own **"Do not display these updates again"** checkbox (vendor `localization.json` keys `UserPreferencesPanel.checkUpdatesCheckBox.text`, `HomePane.showUpdatesMessage.title`, `HomePane.doNotDisplayShownUpdatesCheckBox.text`; update feed `HomeController.updatesUrl = http://www.sweethome3d.com/SweetHome3DUpdates.xml`). So a returning desktop user can also be met by an update notice — a second, separate "opt out forever" surface.
- **F19 (OBSERVED).** In the browser build `UserPreferences.prototype.isCheckUpdatesEnabled`, `setCheckUpdatesEnabled`, `setAutoSaveForRecoveryEnabled` etc. are empty bodies and `showUpdatesMessage` is stubbed among the no-ops R1-F45 lists — update checks and tips/help are desktop-only chrome. (Source: `raw/js/sweethome3d.min.js`; R1-F45.)

### 2.4 The demo chooser: two different products, two different placements

- **F20 (DOCUMENTED).** Desktop: **File ▸ New from demo…** (action label `"New from demo..."`, mnemonic D) opens a dialog whose resource strings are `New home from demo` (title), `Select a demo and confirm your choice.` (message), `Use selected demo`, `Find more demos`, `Cancel` (vendor `localization.json`: `HomePane.NEW_HOME_FROM_EXAMPLE.*`, `HomePane.newHomeFromExample.*`). "*Find more demos*" shows the message "Visit http://www.sweethome3d.com/gallery.html to find more demos." (`HomePane.findMoreExamplesMessage.text`; the URL is also `HomePane.findMoreExamples.url`).
- **F21 (DOCUMENTED).** The feature landed in **v5.5, September 6, 2017** with "**File ▸ New from demo** menu item with **9 demos (5 apartments and 4 houses)** distributed under GNU GPL and CC-BY license" (`raw/history.txt`). The vendor blog for 5.5 adds that the demos were designed by a contributor and released CC-BY so they can be reused.
- **F22 (OBSERVED).** The **online** chooser is not that dialog: it is a server-rendered HTML overlay with 9 tiles (F1/F5) that the page's own `viewHome()` drives, and the compiled core's `newHomeFromExample` / `showNewHomeFromExampleDialog` are **empty stubs** (`raw/js/sweethome3d.min.js`; R1-F45). The core still models demos as data — `UserPreferences.getHomeExamples()/setHomeExamples()` + a `HOME_EXAMPLES` property-change event — so **the host page owns the chooser UI and the core owns the list**. That is exactly the seam an embedder plugs into.
- **F23 (OBSERVED).** Desktop has 9 demos = 5 apartments + 4 houses (F21). The online chooser offers 8 furnished homes + `Empty home`; the furnished set is 5 apartments + **3** houses, and `Empty home` is a special case (no progress bar, immediate alert — F9, R1-F42). So "9 demos" means something slightly different in each product.
- **F24 (INFERRED).** The online chooser is a **blocking, first-paint** decision while the desktop one is an **opt-in menu item**. Same content, opposite onboarding weight: online the chooser *is* the welcome screen; desktop the chooser is a hidden power feature. Neither product, however, offers a "blank" path without consequences: online's blank path is `Empty home` + an alert, desktop's is the default empty home + nothing.
- **F25 (INFERRED).** Neither placement is persisted: the desktop remembers the *last opened* files and re-opens no new home (F15); the online chooser has no "don't show again" (F2/F8). So the reference app chose "ask every time" over "remember the answer".

### 2.5 The tips system (DOCUMENTED + OBSERVED) — the only in-app coaching

- **F26 (DOCUMENTED).** Tips exist for **exactly five** tools, and they are the first-use instructions for those tools: `HomePane.CREATE_WALLS`, `CREATE_ROOMS`, `CREATE_POLYLINES`, `CREATE_DIMENSION_LINES`, `CREATE_LABELS` each carry a `tipTitle` and a `tipMessage` in the vendor resource bundle (titles: *"Create walls tip"*, *"Create rooms tip"*, *"Create polylines tip"*, *"Create dimensions tip"*, *"Add texts tip"*) — `raw/localization.json`. There is no tip for Select, Pan, furniture placement, doors/windows, background-image import, or 3D.
- **F27 (OBSERVED).** The tip bodies are long HTML walkthroughs, not one-liners. Verbatim substance of each (paraphrased): **walls** — *click the start point, then click/double-click the end; until you double-click or press Escape each click alternates the opposite point and the start of the next wall; press Enter for keyboard entry; hold Ctrl (alt/option on macOS) at the end point for a round wall; double-click inside an existing room to build its walls*; **rooms** — *click each corner then double-click the last point or press Escape; Enter for keyboard entry; or double-click inside an existing closed surface*; **polylines** — *click each point, double-click the end or press Escape; double-click the start point to close a polygon; hold Ctrl (alt/option) while drawing the first segment for a curve*; **dimensions** — *three clicks (start, end, placement); or double-click a furniture border / wall side / room side then click placement; Ctrl (alt/option) + click the start point for an elevation dimension*; **texts** — *click the location, then type the text in the dialog that appears*. (`raw/localization.json`; matches the interaction contract in R1-F25/F28.)
- **F28 (OBSERVED).** Trigger logic, verbatim from `raw/js/sweethome3d.min.js` (`HomeController.setMode`): when the new plan mode maps to `CREATE_WALLS|CREATE_ROOMS|CREATE_POLYLINES|CREATE_DIMENSION_LINES|CREATE_LABELS`, and `!preferences.isActionTipIgnored(action)`, the controller calls `getView().showActionTipMessage(action)` on the UI thread and, **if it returns true, calls `preferences.setActionTipIgnored(action)`**. Consequences: the tip is keyed by **action**, shown **once per action**, and the ignore flag is set whenever the dialog was displayed — the *"Do not display this tip again"* checkbox is therefore corroborating UI rather than the sole mechanism.
- **F29 (DOCUMENTED, verified directly this round).** The ignore-list is user-visible and resettable. Verbatim from the vendor's in-app help page `editingPreferences.html` (revision r9047, fetched and read directly at <https://sourceforge.net/p/sweethome3d/code/HEAD/tree/trunk/SweetHome3D/src/com/eteks/sweethome3d/viewcontroller/resources/help/en/editingPreferences.html?format=raw>): *"Finally, the **Reset the display of tips** button resets the answers you gave to the check box **Do not display this tip again** shown in the tips dialog boxes displayed when you click on some tools. This means that all the dialog boxes where you selected this check box will appear again."* The same page documents the neighbouring Preferences items (`Language` dropdown incl. importing SH3L libraries, `Check updates at program launch`, `Save home data for recovery`). The corresponding resource strings are `UserPreferencesPanel.RESET_DISPLAYED_ACTION_TIPS.Name = "Reset the display of tips"`, `HomePane.doNotDisplayTipCheckBox.text = "Do not display this tip again"` (`raw/localization.json`).
- **F30 (OBSERVED).** Persistence shape: `UserPreferences` keeps `ignoredActionTips = {}`; the recorded (web/server) subclass keeps a map `ignoredActionTips[action] = true` and `resetIgnoredActionTips()` writes `false` for every key; the base JS class's `isActionTipIgnored` returns a constant `true` (GWT default for the unimplemented base), so **only the recorded/default-preferences subclass can show tips at all**. The list is therefore a growing per-user key set, not a boolean.
- **F31 (DOCUMENTED).** The tips feature is old and stable: history **v1.5, December 8, 2008** — "*Displayed tips at first uses of a creation tool*" (`raw/history.txt`). It has survived 18 years of releases alongside much newer UI, i.e. the vendor considers first-use tips worth keeping on desktop.
- **F32 (OBSERVED).** **The browser edition shows none of this.** `HomePane.prototype.showActionTipMessage = function(a){return false};` in `raw/js/sweethome3d.min.js` (R1-F45/F13), and `doNotDisplayTipCheckBox` / `showActionTipDialog` have **zero** occurrences anywhere in the online bundles. Because F28 marks a tip ignored only when the dialog *returns true*, the online stub also means the recorded ignore-map is never written — the whole tip subsystem is dead code online.
- **F33 (OBSERVED).** Three other in-app "tip" surfaces exist but are unrelated to first-use coaching: `VideoPanel.tipLabel.text` ("Move in the 3D view and click on the red button at the main locations…") and `PhotosPanel.tipLabel.text` ("Select the points of view where you want to compute a photo…") are static instructional labels inside the desktop photo/video panes, and catalog item tooltips (`CatalogItemToolTip.*`). None of these reach the online build either (photo/video creation is desktop-only, R1-F44).

### 2.6 Help integration (DOCUMENTED + OBSERVED)

- **F34 (DOCUMENTED).** Desktop has a full built-in **Help window**. Two entry points: the **Help button in the tool bar** and **Help ▸ Sweet Home 3D Help**; accelerator **F1** (Windows/Linux) / **cmd-?** (macOS) per the vendor shortcut sheet <https://www.sweethome3d.com/storage/SweetHome3DShortcuts.pdf> (R1-F27 already recorded F1/cmd-? from the same sheet).
- **F35 (DOCUMENTED).** The window's own vocabulary, confirmed in the vendor resource bundle (`raw/localization.json`): frame title **"Sweet Home 3D Help"** (`HelpPane.helpFrame.title`), a `Search:` label with mnemonic S, `SHOW_PREVIOUS` ("Show previous page"), `SHOW_NEXT` ("Show next page"), `SEARCH` ("Search"); controller strings `HelpController.helpTitle`, `searchFound` ("Your search **%s** was found in the following documents."), `searchNotFound` ("Your search **%s** did not match any documents."). Vendor source adds the accelerators Ctrl+F / Ctrl+P / Ctrl+N (cmd variants on macOS).
- **F36 (DOCUMENTED/OBSERVED).** Help content is the user guide, shipped **inside** the app as localised HTML, one directory per language: `HelpController.helpIndex = '/com/eteks/sweethome3d/viewcontroller/resources/help/en/index.html'` (`raw/localization.json`) — a **classpath** resource, so there is no public URL (the marketing site 404s `/help/*`). The guide says help is available in 29 languages, and history records a **search engine added in v1.2 (Nov 2007)** and **highlighted searched text in v3.3** (`raw/history.txt`).
- **F37 (OBSERVED).** The online build has **no help at all**, by construction: `HelpController`/`HelpPane`/"Sweet Home 3D Help" occur **0** times in `raw/js/sweethome3d.min.js` and in every other online bundle; `HomeController.help = function(){}` (R1-F45); `#toolbar-button-HELP` count is 0 in `evidence/A_settle_html.html` and `evidence/B_after_alert_html.html`; the online toolbar ends with **About** then **Preferences** (F10). The only online remnant is `HomeAppletController.helpIndex = 'http://www.sweethome3d.com/userGuide.html'` pointing at the website, and even that is not wired to a visible control.
- **F38 (OBSERVED).** What the online build *does* offer is **About**, and its content doubles as the licence/provenance panel: `HomePane.about.title = "About Sweet Home 3D"`; `HomePane.about.message` = "Sweet Home 3D ® / Version %1$s" + a third-party credit list (JSZip, glMatrix, big.js, jsXmlSaxParser, Batik, OpenJDK-derived 2D geometry and undo/redo libraries) + "Please, visit http://www.sweethome3d.com/ for support and bug report." + "© Copyright 2024 Space Mushrooms… Distributed under GNU General Public License". Desktop additionally has a `Libraries...` button (`HomePane.about.showLibraries = "Libraries..."`). My live attempt to open it (`raw/scenario_E_about.json`) failed with a provider cleanup timeout and retained **0** steps, so the About *rendering* is asserted from the resource bundle, not from a fresh click (see Unknowns).
- **F39 (DOCUMENTED).** Off-site onboarding material a new user can reach: the **User's Guide** (<https://www.sweethome3d.com/users-guide/>), a **Tips and Tricks** index of **17 dated blog tips** plus a "Tips on YouTube" block of 11 titles (`raw/tips.txt`), **video tutorials embedded under `/documentation/#video-tutorials`** (no standalone video page; `/videoTutorial.html` 404s), a **Gallery** of downloadable `.sh3d` examples (<https://www.sweethome3d.com/gallery/>), and a downloadable **tutorial example home `userGuideExample.sh3d`** (~3.2 MB) plus its blueprint image, linked from the guide. Docs list features and FAQs but **no "quick start" or "first 5 minutes" page**.
- **F40 (INFERRED).** Help is *well integrated* on desktop (F1 accelerator, toolbar button, menu item, searchable localised HTML, and the guide itself begins by pointing at it) and *completely absent* on the web (F37). Any CasaPlazAI plan should note the asymmetry: the reference app's help is a desktop privilege, and its web edition substitutes nothing — matching R1-F56's conclusion that Online competes on "the same editor, simpler".

### 2.7 Locale, German edition, and the `/de/` URL named in the task

- **F41 (OBSERVED).** `https://www.sweethome3d.com/de/SweetHome3DJSOnline.jsp` does **not** exist: `evidence/scenarioD.json` loaded a page whose `<title>` is *"Sweet Home 3D - Page Not Found"* with heading *"This Page Doesn't Exist"* (`evidence/D_settle_html.html`); there is no `#demo-choice`, no `viewHome`, no app bundle. The German site's Online page instead links **directly to the English app path** `/SweetHome3DJSOnline.jsp` (checked in the round-1 `raw/de-online.html`).
- **F42 (OBSERVED, confirmed end-to-end).** The online app **does not localise itself from the browser**. The served page hard-codes `applicationParams.userLanguage = "en"` (with a single special case mapping `pt`→`pt_BR`; `raw/sh3d-online.jsp.html`), and the live rendered DOM confirms the literal value `en` (`evidence/scenario3.json` DOM). I then ran the same page with the browser context set to `locale: de-DE`, `timezone: Europe/Berlin` (`raw/scenario_F_de_locale.json`): `evidence/F_settle_a11y.txt` still shows `row "Select a demo"` → `Empty home | Studio | 1-Bedroom apartment` in English (the rendered DOM again contains `userLanguage = "en"` and `count("Wählen") == 0`). The demo tile labels and the alert are page markup in English (F1, F9). **Net: the German product URL in my brief leads a German-speaking newcomer to an English browser app.**
- **F43 (DOCUMENTED).** The German *desktop* product is fully localised: `raw/de-userguide.txt` is a complete German user guide for 7.5, including the same sentences about the `Hilfe` button in the toolbar ("die Sweet Home 3D-Hilfe nutzen, die Sie über die Schaltfläche **Hilfe** in der Symbolleiste … aufrufen können") and the same 8 suggested steps; `UserPreferences.DEFAULT_SUPPORTED_LANGUAGES` lists 19 UI locales including `de`, and the site advertises 29 languages of help. The German **online** marketing page (`raw/de-online.html`) is German, but it hands off to the English app (F41).
- **F44 (INFERRED).** Localisation is a property of the *installed product*, not of the *hosted product*: locale lives in user preferences (per-installation/per-server-profile), and the hosted page simply doesn't ask. For CasaPlazAI — a single-workspace web app — that is a cheap lesson in reverse: the browser's `Accept-Language`/`navigator.language` is free, and the reference app's hosted edition leaves that value on the table.

### 2.8 Cross-cutting: what the first 5 minutes are made of (INFERRED)

- **F45 (INFERRED).** The three editions encode three different first-run philosophies, and they contradict each other: **desktop** = empty default home, demo chooser hidden in a menu, opt-out first-use tips, full searchable help, update notice; **web** = blocking demo chooser, no tips, no help, no persistence, alert-based warnings; **mobile** (R1-F49) = gesture-only, no printing/photos/plug-ins, auto-saved. The invariant is the four-pane editor; the onboarding is entirely edition-specific.
- **F46 (INFERRED).** "First run" in this product is deliberately *unmemorised*: nothing (F8), no recent-home reopen of an untouched document (F15), and tips that are one-shot per tool rather than per session (F28). The product optimises for "no state, no surprise" and pays for it with a first 5 minutes that is either empty (desktop) or a hard gate (web).
- **F47 (INFERRED).** The tips are the highest-value thing to copy and the help window is the lowest, for a browser floorplanner: the tip content is *directly* a description of CasaPlazAI's own interaction contract (click start → click end → Escape/double-click to finish → Enter for typed entry), it is five strings of data, and it needs no content pipeline. The help window, by contrast, needs localised HTML, a search index, and a container (window vs dialog) — which is exactly the surface the reference app chose to drop from its own web build.

## 3. Ideas for CasaPlazAI (ranked by value/effort)

Ranking = value for a single-workspace web 2D/3D floorplanner, then effort. Each row names the finding(s) it comes from and, where relevant, the CasaPlazAI schema field it touches.

| # | Idea | Why (finding) | Value | Effort |
|---|------|----------------|-------|--------|
| 1 | **First-use tips for each creation tool, one per tool, dismissible, with a global "Reset tips" in settings.** CasaPlazAI's contract is already close to SH3D's (click start → click/double-click end → Escape; Enter = typed dimensions). Ship five tip bodies mirroring the tools (rectangle room, polygon room, door/window, measure, underlay trace) and store the ignore set as a small `string[]` next to `casaplaza.snap.settings.v1` (out-of-schema editor state, like the underlay key). | F26–F31, R1-F33/F56 — the reference app's *only* in-app coaching, 5 strings of data, and the Online build stubs it out, so it is an unclaimed differentiator. | High | Low |
| 2 | **Pre-fill the first run with a real plan instead of a blank grid — but make it one tile and local.** Extend the existing demo idea into a "starter flat" that is generated locally (a 6×8 m two-room flat with one door and two windows, i.e. `rooms` + `openings` + a couple of `FurnitureItem`s) so the 3D/Walk modes have something to show in the first minute, with a clear "this lives in your browser" notice. | F20–F24, F13 — desktop's "default home" and online's chooser both exist precisely because the blank canvas is the drop-off; a local starter is cheaper than shipping `.sh3x`-style assets. | High | Med |
| 3 | **Make the first-run choice dismissible and remembered.** If a chooser-style surface is used, add a visible *Skip / Start empty* and persist the answer (e.g. `casaplaza.onboarding.v1`), because the reference chooser has **no close button and no memory** and blocks the whole workspace render until an option is clicked. | F1–F3, F8, F25 — a hard gate with no exit and no memory is the single worst first-run pattern observed live. | High | Low |
| 4 | **Contextual help as a *pointer to the docs site*, not a help window.** A single "?" affordance that deep-links to the exported markdown/HTML guide anchors for the current mode (Plan/3D/Walk) matches what the reference web build does (it drops `HelpPane` entirely) while still answering "how do I…"; add `title` tooltips with the shortcut on every toolbar button (the SH3D toolbar is 29 icon-only buttons with `title` text only). | F34–F38, R1-F45 — the reference ships a full help window on desktop and **nothing** on the web; a deep link is the 10 % that buys 80 %. | Med–High | Low |
| 5 | **Type the undo/redo label into the tip chain** ("Undo Move wall", "Undo Delete door") so the first edit a new user makes is self-explaining; combine with tip #1 by showing the tip *after* the first completed use of a tool rather than before. | R1-F19/F20 + F28 — the reference types undo labels and gates tips by action; a post-use tip is better-timed coaching with the same data model. | Med–High | Low |
| 6 | **A `blueprint underlay` first-run path, guided by a 3-step wizard, offered as step 1 of an onboarding checklist.** CasaPlazAI already has the underlay (`casaplaza.underlay.v1`, per-floor, deliberately outside `FloorplanData`); make it the *recommended* first action for "I'm copying my existing flat" and keep "start from scratch" equally prominent. | F16, R1-F34/F35 — the reference guide's own step 1 is blueprint import, and its wizard scale step ("the real length, not the screen length") is the proven friction point to design around. | Med–High | Med |
| 7 | **Do not localise by URL; localise by preference + browser hint.** Serve one app path and read `navigator.language`, with an explicit language picker; never create per-language app URLs (the reference's `/de/<app>.jsp` is a 404 and the hosted app hard-codes English). | F41–F44 — cheap correctness, and it keeps share links single-form. | Med | Low |
| 8 | **Bundle a "what's new" surface with its own opt-out**, mirroring "Do not display these updates again"; a first-run notice board is a legitimate second onboarding surface and is independent of tips. | F18, R1-F33 — the reference has a separate ignored-list for update notices; worth copying once CasaPlazAI has releases. | Med (later) | Low |
| 9 | **Export the in-app tip texts as the "help" content.** Since CasaPlazAI has no backend, authoring five tips as data and rendering them both as first-use dialogs and as a searchable panel gives one content source for in-app help and the docs page. | F26/F27 + F47 — avoids the reference app's split where the guide and the tips never reference each other. | Med | Med |
| 10 | **Play the reference's restraint on onboarding *volume*:** no splash screen, no auto-opened welcome tour, no second modal at first paint. The measured first 5 minutes online currently contain cookie dialog + 2 download banners + demo gate + `alert()` — four interruptions before the first edit. | F7, F9, F14 — the reference's own splash is transient/error-prone and its banners compete with the chooser; CasaPlazAI can win by having exactly one first-run interruption. | Med | Low |
| 11 | **Keep tips inside the editor state, never inside `FloorplanData`.** Tips, tip-ignore list, onboarding-seen flag, language, and the starter-plan flag must not cross the editor→viewer contract or leak into share links. | CasaPlazAI schema "Out-of-schema editor state" section + F8 (the reference stores tip state in user preferences, home state in the home file, and the two never mix) — this is the reference's actual separation and it matches the schema. | Med (hygiene) | Low |
| 12 | **Make the demo/starter choice keyboard- and screen-reader-reachable.** The reference chooser is `onclick`-only `<img>`/`<a>` with no `href`, no close, no role; a CasaPlazAI dialog should be a real `role="dialog"` with focus management, Escape-to-skip, and `aria-describedby` on the "not saved" warning. | F3, F4 — the exact defect observed live, and cheap to avoid. | Med | Low |
| 13 | **Seed one sensible editor default on first use instead of a tip.** The online host page calls a single preference setter (`setNewRoomFloorColor`, F12d) to make its audience's first room look intentional; CasaPlazAI can do the analogous thing by seeding `floorTexture`/grid + default `wallThickness`/`wallHeight` for a first-run plan so the first room already looks finished. | F12d — a one-line, zero-UI onboarding lever that the reference uses and that maps onto the schema's global `wallHeight`/`wallThickness` and `Room.floorTexture`. | Med | Low |
