# 3D House Planner — Levels: adding, switching, duplicate-level semantics, visible floors

Competitor research for **CasaPlazAI**. Subject: **3D House Planner**, <https://www.3dhouseplanner.com/> (browser editor, Babylon.js; 2D planner iframe at `/2D-Planner/index.php`).

**Round 2 scope.** The *levels* subsystem only — how levels are added and switched, the semantics of the Duplicate-level dialog, what "Visible floors" actually hides, and what happens when you edit on a hidden level. This builds on the Round-1 report at `~/dsh-workspaces/rea-3dhouseplanner-2026-10/09-09-measurements-levels/report.md` (read-only) and reuses its shipped-JS evidence; it does **not** repeat its measurement/units findings. Round-1 unknowns #5 (snap slider labels) and #6 (whether "Visible floors" hides the *current* level, and editing hidden levels) are addressed directly here.

**Evidence tags.** `OBSERVED` = seen in a live captured page/DOM/JS state, or read out of JavaScript the site served my browser (file cited). `DOCUMENTED` = stated by the vendor on a page I fetched. `INFERRED` = my reasoning beyond what was directly observed.
**Note on code.** 3D House Planner is proprietary (footer: *"© 2022-2026. All rights reserved."*). Everything below describes behaviour, identifiers and UX in my own words; decoded source stays local as evidence and is not reproduced.

**Method.** Round-1's `rea capture-browser-scenario` action schema has no JS-evaluate step, so I launched the site's own Playwright Chromium (`chromium-1243`) directly with software-GL flags (`--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`). WebGL came up, the editor booted to `app.php`, and I drove it through the page's **own** exposed APIs (`window.HP3D`, `window.HPBIM`, the DOM controls) and read the resulting scene/DOM state. Scripts: `notes/probe*.mjs`; raw results: `evidence/live-probe*.json`.

Local evidence: `evidence/` (live-probe*.json), `notes/` (scripts + deob helpers), `sources.json`.

## 1. Summary

- **A level is an integer index, not an entity.** There is no floor table: `HP3D.setLevel(n)` clamps `n` to `0..50` with `Math.round`, `currentLevel()` returns the slider's integer, and `levelBase(n) = floorHeight × n` with one global floor-to-floor height (default 2.65 m, hidden input `#floorheight`, `min 2 / max 5`). No per-level name is stored in the geometry layer (`OBSERVED`, live-probe3/6; `hp-editor`).
- **Adding and switching are the same "+"/"−" control, and adding is purely a change of the current index.** The top toolbar `div.hp-level` (`− / Level n / +`) and the 2D planner's own `div.fp-level` both call the same `setLevel`, clamped to `[0, 50]`, instantly and with no dialog; going to an empty level creates nothing. The 2D planner's bridge exposes `requestLevel(n)` which the 3D side awaits (`OBSERVED`, live-probe2/3/8).
- **"Duplicate level" is a real, well-built copy dialog** reachable from a button injected into the *Floors & grid* dock card. It has From/To selects, a "New level above (Level N)" target that is always `max(existing)+1`, seven category checkboxes with live per-category counts (Walls, Doors and windows, Floors, Skirting and cornices, Furniture and objects, Stairs, Roofs) that are *disabled* when the source level has none, and — only when the target already holds elements of the ticked kinds — a warning plus **Add to them / Replace them** radios. On success it switches you to the target level and toasts `"N elements copied to <name>"` (`OBSERVED`, live-probe5/6/7/9).
- **"Visible floors" is a global Y-threshold, not per-level checkboxes.** A slider `1..50` (default 50) hides every root mesh whose `getAbsolutePosition().y` exceeds `floorHeight × value + 0.001`, recursively hiding children; it never consults the current level. Because `levelBase(n) = floorHeight × n`, sliding to *k* shows levels `0..k-1` (`OBSERVED` live-probe4/7; `hp-editor`).
- **Editing on a hidden level works, but blindly.** Geometry can still be created on a hidden level, but the app enforces visibility *lazily*: a freshly built mesh stays `isVisible = true` until something calls `refreshVisibility()`, so a new object on a hidden level is briefly visible, then hidden; the new mesh is never highlighted, the camera never moves to it, and the visible grid stays on the ground. Hidden meshes keep `isPickable`/`isEnabled` and only lose `isVisible`, so pick predicates that test only `isEnabled()` hit geometry the user cannot see; creation and deletion on a hidden level are both ungated (`OBSERVED` live-probe4/7/9/11).

## 2. Findings

### 2.1 The level model

- **Index arithmetic, verified live.** With the default `floorHeight = 2.65`: `levelBase(0)=0`, `levelBase(1)=2.65`, `levelBase(2)=5.3`, `levelBase(50)=132.5`. A wall built on level *n* sits at `y = levelBase(n) + wallHeight/2` (walls on level 1 measured `y = 3.975` = 2.65 + 2.65/2) (`OBSERVED`, live-probe3). This matches Round-1 finding 2.5; I re-verified it rather than re-deriving it.
- **No level entity, names live elsewhere.** `levelOf(mesh)` mostly reads `mesh.metadata.hp.level` for slabs/roofs/frames/finishes, but for `wall`, `object`, `door` and `window` it *derives* the level from the mesh's Y position via `levelOfY(y) = max(0, floor(Math.floor((y+0.05)/floorHeight)))`. So level membership is recomputable geometry, not a stored key, for the element kinds a user moves around (`OBSERVED`, `hp-editor` `_0xc6fc75` / `_0x38aefb`).
- **Names are a BIM-only map.** `HPBIM.levelName(n)` returns `Level n` unless `HPBIM.setLevelName(n, name)` was called (I set level 1 to "First floor" and read it back); `setLevelName(k,v)` writes into the BIM state object that is serialized with the project. It is not part of the geometry model and has no editor UI in the 3D dock I inspected (`OBSERVED`, live-probe6; `hp-bim` `setLevelName`, i18n `bim.levelName`).
- **`levelBase` is read nearly everywhere** (paste offset, stairs, dims, support heights). `HPStairs` auto-cuts a hole in the slab at `levelBase(n+1)+0.06` — i.e. it assumes **uniform storey height**; a per-level height would silently break it (`OBSERVED`, `hp-stairs`; `INFERRED` for the consequence).

### 2.2 Adding and switching

- **Toolbar.** `div.hp-level` = `[−] "Level" <span.hp-level-value>n</span> [+]`, `title="Current level: new walls, floors and objects go here"`. The `+`/`−` buttons are `aria-label="+"/"−"`, and clicking them simply runs `setLevel(current ± 1)`. Live: from level 1, `+` → 2, two `−` → 0; the DOM counter and `HP3D.currentLevel()` always agreed (`OBSERVED`, live-probe2/3).
- **Clamping is silent.** `setLevel(99) → 50`, `setLevel(-5) → 0`, `setLevel(1.6) → 2`, `setLevel('abc') → 0`. The 2D planner mirrors this by disabling its below/above buttons at `<=0` / `>=50` (`OBSERVED` live-probe3; `planner-bridge3d` `_0x433a88`).
- **"Adding a level" creates no geometry.** After `+` from 0, `listElements({level:4})` was empty and the total element count was unchanged — the `+` is just a target index (`OBSERVED`, live-probe9). The meaningful "add a storey" gesture is Duplicate level (2.3) or drawing on the new index.
- **Two level switchers.** The 2D planner iframe has its own `div.fp-level` with `aria-label="Level below"/"Level above"` and `span.fp-level-value` reading `Level n`. Clicking its `+` drove the 3D side to level 1 and the iframe label to `Level 1`; the bridge's status line reads `Synced with 3D · Level n` (`OBSERVED`, live-probe8). This means the level is a *shared* piece of state between the two panes.
- **No level keyboard shortcut found.** I found no `PageUp/PageDown/Digit` level binding in `hp-editor`/`hp-ui`; the only level controls are the two toolbars and the API (`OBSERVED` negative; `INFERRED` that none exists in the bundles I searched).

### 2.3 The "Duplicate level" dialog

- **Entry point.** A button `button.hp-btn.hp-level-copy` (icon `library_add`, label *Duplicate level…*) is injected into `#hpLevelPanel .hp-fcard-body` (the *Floors & grid* dock card) on startup. One dialog element `#hpLevelCopyDialog` is built lazily and reused (`OBSERVED`, live-probe5/9; `hp-copy` `_0x30c761`, `_0x20c506`).
- **Anatomy (from the live DOM).** `role="dialog" aria-modal="true"`, title *Duplicate level*, subtitle *"Copy walls, openings and floors of a level to another one, for example to start the upper floor."* Body: `From` select, `To` select, a "What to copy" section of seven `<label class="hp-lc-group">` rows each with a checkbox, a Material icon, a name and a count, then a `.hp-lc-target` live region that appears only when relevant. Footer: *Cancel* and the primary *Duplicate* button (`disabled` until at least one source category has elements) (`OBSERVED`, live-probe5/9).
- **From list.** One option per level that currently holds at least one non-terrain element, **plus the current level**, sorted ascending and defaulting to the current level. With geometry only on 0 and 1 and current = 1, From was exactly `[Level 0, Level 1]` (`OBSERVED`, live-probe6).
- **Level gaps survive.** With walls/slabs on levels 0, 1 and 3 and nothing on 2, From was `[Level 0, Level 1, Level 3]` (selected 3) and To was `[New level above (Level 4), Level 0, Level 1, Level 2]` — i.e. **gaps are first-class**: level 2 is a legal target that was never used, and the "new" target is `max(existing)+1 = 4`, not `distinct-count` (`OBSERVED`, live-probe8). This contradicts a naive "levels are contiguous" assumption and is worth copying deliberately.
- **To list.** `"New level above (<name of max+1>)"` first, then every level `0..max` **except the From level**, in ascending order. Every level — including empty ones — is offered as a target (`OBSERVED`, live-probe6/8; `hp-copy` `_0x3ac0ad`).
- **Category model.** Seven fixed groups, each `{id, icon, default-on, test}`: Walls (default on; kind `wall` or `frame`), Doors and windows (on; `door`/`window`), Floors (on; `slab`), Skirting and cornices (on; `skirting`/`ceiling_trim`), Furniture and objects (**off**; `object` that is not a stair), Stairs (**off**; `object` that `HPStairs.isStair` recognises), Roofs (**off**; `roof` except the auto-roof). A group whose `test` matches zero elements on the From level is rendered `disabled` with count `0`; enabled groups show their live count and remember their tick state across recomputes (`OBSERVED`, `hp-copy` `_0x4fcd53` / `_0x1a0557`; live-probe5/6).
- **Add vs Replace appears only on conflict.** When the To level already holds elements of the ticked kinds, a `.hp-lc-warn` line appears (`"Level 0 already has 5 elements of these kinds."`) plus radios `Add to them` (default) / `Replace them`. With no conflict the region is empty and Add is implicit (`OBSERVED`, live-probe7/9; `hp-copy` dialog builder).
- **What Replace means, precisely.** Replace removes **only the elements of the ticked categories** on the target, then copies. Measured: target level 0 with 5 elements, duplicating 5 elements from level 1 with Add → 10; re-running with Replace → 5. The toast text is procedurally generated from the count made, `"N elements copied to <name>"`, with an `ok`/`error` tone (`OBSERVED`, live-probe7; `hp-copy` `_0x1a0867`).
- **The copy is a re-instantiation, not a clone.** The target is built by re-creating each source element at `dy = levelBase(to) − levelBase(from)` and `level = to`, walking a serialised recipe per element; elements that fail to rebuild are counted as `failed`. Walls are created first, then the rest, then trims/skirtings, then `cutwalls()` so openings re-cut the new walls. On success the dialog closes and `setLevel(to)` runs (`OBSERVED` in code, `hp-copy` `_0x1a0867` + `hp-bim.copyElements`; the switch-on-success is also visible live, live-probe6).
- **Roofs are deliberately excluded in one case.** `copyElements` skips a mesh whose id is `autoRoof` (the derived roof), so the auto-roof is regenerated rather than duplicated (`OBSERVED`, `hp-bim` copyElements).

### 2.4 "Visible floors": what it hides

- **It is a Y-threshold, not a set of levels.** `refreshVisibility()` iterates root scene meshes and sets `isVisible = false` (recursing into `getChildMeshes()`) for any mesh whose `getAbsolutePosition().y > floorHeight × sliderValue + 0.001`; the grid clone, base grid, terrain and skybox are exempted by identity. Dimension-line meshes and imported merged walls get a second pass using their bounding-box **centre** against the same threshold (`OBSERVED`, `hp-editor` `_0x4cb0bd`, live-probe4).
- **Verified effect.** With one room per level on 0/1/2 and the slider set to 1: level 0 kept 5/5 visible, levels 1 and 2 dropped to 0/5. Slider 2 → levels 0,1 visible; slider 3 → all three; slider 50 (default) → all (`OBSERVED`, live-probe4/7).
- **It ignores the current level.** With the slider at 1 and the user on level 2, level 2's geometry stayed hidden — the predicate never consults `currentLevel()`. So the editor cheerfully lets you stand on a level whose contents are invisible (`OBSERVED`, live-probe4/7). *This directly answers Round-1 unknown #6: yes, "Visible floors" hides the current level's own contents when the threshold is below it.*
- **The label and the cut plane do not line up.** The predicate cuts strictly at `h·value`, so the *label* "up to k" describes a plane at the *ceiling* of level `k−1`, not at its floor. Value 1 shows level 0 only; value 2 shows levels 0 and 1, i.e. everything below `2.65×2 = 5.30 m` — the top of level 1; value 3 and above include everything up to the top. So the slider behaves like "floors fully below height `h·k`", which is a reasonable mental model but is off by one against a naive "show k floors" reading (`OBSERVED` from the predicate + live measurements; `INFERRED` for the naming implication).
- **Level 50 is a boundary hole.** `setLevel(50)` is accepted and `levelBase(50) = 132.5`, so a wall there has centre `133.825` — strictly above the maximum threshold `2.65×50 + 0.001 = 132.501` even at slider 50. A wall built on level 50 is therefore invisible at every slider setting (verified: `elementsAt50Visible: [false]`; level 49 at `y = 131.175` was visible). `INFERRED`: the top level is effectively unusable, matching the displayed cap "50 floors" meaning indices 0..49.
- **Lazy refresh is a real bug source.** A mesh built while the threshold already excludes its height is **not** hidden immediately: the `silent` build path never calls `refreshVisibility()`. Building a wall on level 2 with the slider at 1 gave `isVisible: true` straight away; only after an explicit `cutwalls()`/refresh did it become `false`. Any code path that creates geometry on a hidden level without a subsequent refresh leaves it visible (`OBSERVED`, live-probe9).
- **`refreshVisibility()` is exported and called at natural sync points** (after 2D→3D apply, after a project load, after the BIM visibility panel's "show all"/"show only this" actions, and after a stair rewrite), not on every frame (`OBSERVED`, `hp-sync`, `hp-bim`, `hp-editor`).

### 2.5 Editing on a hidden / other level

- **Creation is not gated.** `setLevel(2)` + `buildWall(...)` with the slider at 1 built the wall at `y = 6.625` and the element count on level 2 rose 5 → 6; the wall's base was exactly `levelBase(2)`. Nothing warned, and the "Level n" badge kept showing 2 (`OBSERVED`, live-probe4/9).
- **Hidden geometry is still enabled and pickable.** On a hidden level, meshes keep `isPickable = true` and `isEnabled() = true`, with only `isVisible = false`. A downward `scene.pickWithRay(ray, m => m.isPickable && m.isEnabled())` from above the hidden slab hit the hidden slab; with a default predicate that also checks `isVisible`, the same ray hit the *visible* level-0 slab instead. So picking correctness depends entirely on each call-site's predicate, and the editor's own pick predicates are inconsistent about `isVisible` (`OBSERVED`, live-probe7/11; `hp-editor` uses both `isEnabled()`-only and `isPickable && isEnabled()` forms).
- **Deletion is not gated either.** `disposeElement` on a hidden level's wall worked and the level's element count fell, with no visibility check (`OBSERVED`, live-probe11).
- **No visual or camera feedback for the level you are on.** Only the invisible "grid clone" pick plane tracks the level: at level 0 it sits at `y = -0.05`, at level 2 at `y = 5.3` (= `levelBase(2)`), while the *visible* grid stays at `y = -0.05` and the terrain at `y = -0.06`. The orbit camera's `target.y`, `radius` and `position.y` were byte-identical before and after the switch. So changing level moves the *working plane* under the cursor, not the *view*; on a tall building you can end up looking at empty space (`OBSERVED`, live-probe11).
- **Hidden levels keep their data.** Visibility is display-only: `listElements()` still returns every level's elements, and the 2D planner syncs only the current level's projection. Switching back restores the meshes' visibility on the next refresh (`OBSERVED`, live-probe4/8/11).
- **The 2D planner follows the level, one level at a time.** With walls+slab on 0 and 1, switching the 3D level to 1 made the iframe's `FloorplanBridge.getModel()` report exactly that level's 4 walls + 1 room; back to 0 it reported level 0's. The per-level plan is projected on demand from 3D meshes (`hp-sync` `_0x136b0c`, which builds a fresh plan and reuses cached walls by uid) and cached in a per-level `plans` map (`OBSERVED`, live-probe8; `hp-sync` `_0x9c02`).

### 2.6 Transitions and metadata

- **Duplicate level is the only "add a storey" operation.** It is a copy-of-categories, not a "create empty storey" command; a new index is materialised by the Duplicate dialog's "New level above" target or by simply navigating to an unused index and drawing (`OBSERVED`, live-probe2/3/9).
- **No level deletion anywhere.** I found no delete-level command in the dock, the dialog or the exported API — only element deletion. A level "exists" iff some element reports that index (`OBSERVED` negative; live-probe2 dialog + `HP3D` key dump).
- **Dock card title is "Floors & grid"** (`#hpLevelPanel .hp-fcard-title`) and holds, in order: **Visible floors** (`1..50`, default 50), the hidden current-level slider (`0..50`, default reflects the level), the **snap-to-grid** slider (`min 2 / max 16 / step 2`, label `1/value`), and hidden wall-height/thickness/terrain sliders. This confirms Round-1 unknown #5's arithmetic: reachable labels are 0.5, 0.25, 0.1667, 0.125, 0.1, 0.0833, 0.0714, 0.0625 m (`OBSERVED`, live-probe4 slider dump; `hp-panels`).
- **Persistence is not level-specific in localStorage.** After a session's work the only `hp-*` key was `hp-donate` (plus `hp-sync-prefs` for the sync toggle, read from code); the project itself is held in the BIM/serialization layer with an explicit `levelInfo` map and `levels` name map, and the 2D bridge keys observed were third-party extension keys (`extension-floorplanner-*`) (`OBSERVED`, live-probe8/9; `hp-bim` `'levels'`, `'levelInfo'`, `setLevelName`).

## 3. Ideas for CasaPlazAI

CasaPlazAI's shipped `FloorplanData` v1 has **no floor/level concept at all** — `rooms`, `openings`, `furniture`, one `wallHeight`, one `wallThickness`. The Round-1 anti-patterns ("do not make storey height global and immutable"; "do not hide floors purely by height") and the per-floor underlay key (`casaplaza.underlay.v1`) already presuppose a floor dimension. So the highest-value ideas here are about *modelling* floors before building UI on them. Ranked by value/effort.

1. **Model a floor as a first-class entity, not an index** *(findings 2.1, 2.6; schema)*. Add `Floor { id, name, elevation, height }` and a `floors: Floor[]` + `floorId` on `Room` (and infer openings/furniture through their room) as the schema's next migration — `registerTransform(1, …)` bumping to `SCHEMA_VERSION 2`. This is the one change that makes every later idea cheap and is exactly what the competitor lacks (`levelBase = global × n` cannot express a garage, a basement or a split level, and `HPStairs` will silently mis-cut a hole if heights differ). Effort: schema + validator + migrate, no UI required for the first step. Value: highest — unblocks the rest.

2. **"Duplicate level" dialog with live category counts and Add/Replace only on conflict** *(finding 2.3)*. Copy their shape almost literally, adapted to CasaPlazAI's enums: categories ⇒ Walls (`Room.polygon` segments), Openings (`Opening.kind`), Floors (`floorTexture`), Furniture (`FurnitureItem.type`); count per category from the source floor; disable empty ones; offer "New floor above (Floor N)" = `max(elevation)`+1 **and** keep index gaps legal. The "Add to them (default) / Replace them" radios appearing *only* when the target already holds elements of the ticked kinds is a small touch that avoids both a scary always-on warning and a silent destructive default. The "Replace removes only the ticked categories" semantics is important and easy to get wrong. Effort: medium (one dialog + a pure copy function over `FloorplanData`). Value: very high — it is the whole multi-floor authoring workflow.

3. **Cut-plane slider + per-floor visibility flags, not one or the other** *(findings 2.4, 2.5)*. The competitor's discoverability win is a single "Visible floors: up to N" slider — it reads as a cutaway and needs no UI. Its cost is that you cannot hide level 1 and show level 2, and it hides the level you are editing with no warning. CasaPlazAI should offer **per-floor eye toggles** (the honest tool) **plus** a "show up to current floor" preset that emulates the cutaway, and it should *never* hide the floor the user is editing without a banner like "Floor 2 is hidden — show it". Since the 3D viewer is a separate consumer of `FloorplanData`, the cut plane can be viewer-only state (like the underlay and snap settings) and need not enter the schema. Effort: low–medium. Value: high, and it directly answers the competitor's weakest area.

4. **A level badge and two level switchers that share one source of truth** *(findings 2.2)*. Their `− / Level n / +` in the 3D toolbar mirrored by the 2D planner's own `fp-level` group, both clamped `[0,50]`, both calling the same `setLevel`, is a clean pattern for CasaPlazAI's *Plan / 3D / Walk* redesign: one `currentFloorId` in editor state, rendered as a compact stepper in each mode's tool card, with a keyboard bind (they have none — an easy win: `PageUp/PageDown` or `Ctrl+↑/↓`). Effort: low. Value: medium-high; near-zero cost in the new tool-card system.

5. **Re-project the plan from 3D per floor, don't store a separate plan per floor** *(finding 2.5)*. `hp-sync` builds the 2D model of the current floor on demand from the 3D meshes and caches it by level in a `plans` map, reusing wall objects by uid so edits round-trip. For CasaPlazAI's Plan↔3D two views this suggests: derive the plan view of a floor from the single `FloorplanData` (filter rooms/items by `floorId`) rather than maintaining a parallel 2D document. The competitor's uid-keyed cache is the part worth copying — it is what keeps wall identity stable across a round trip. Effort: medium. Value: high for correctness of the two-view sync.

6. **Guard "hidden but live" geometry in the editor** *(finding 2.5)*. Because they hide only by `isVisible`, hidden meshes stay `isPickable`/`isEnabled` and different call sites use different predicates, hidden meshes can be hit by raycasts and deleted. CasaPlazAI's editor should derive a single "interactive set" per mode/floor (visible ∧ enabled ∧ on the active floor) and use it for every pick/hover/delete path — one helper, not per-call-site predicates. Effort: low. Value: medium (bug prevention, invisible when correct).

7. **Recompute visibility after every mutation, or make it derived** *(finding 2.4)*. Their bug is that a `silent` build leaves a new mesh visible until some later `refreshVisibility()` fires. In a React/Three.js editor the analogue is a memoised "visible set" derived from `(floors, visibilityState, activeFloor)` on every render — then a mutation can never leave a stale `visible = true`. Worth an explicit test. Effort: low. Value: medium; cheap insurance.

8. **Say what the numbering means, and keep gaps legal** *(findings 2.1, 2.3, 2.4)*. They mix "Level n" indexing with a `1..50` visibility slider, produce an off-by-one cut (slider *k* shows levels `0..k-1` while its own log says "k"), and leave level 50 invisible at every setting. CasaPlazAI should label floors by name **and** elevation (`Floor 1 · +0.00 m`, `Floor 2 · +2.65 m`), express the cut plane in metres rather than an index, and validate that no floor's elevation exceeds its own cut plane. Effort: low. Value: medium — the elevation label is also exactly what a Levels/section view needs.

9. **Roofs and derived geometry are regenerated, not copied** *(finding 2.3)*. `copyElements` skips `autoRoof` so the roof is rebuilt from the new level's geometry. CasaPlazAI already derives ridges at compile time (`roofs` rows, `roof-not-top-floor`); extend the same principle: `copyFloor` copies authored rows only (`rooms`, `openings`, `furniture`, `roofs`), never derived meshes, and re-validate (`roof-not-top-floor` must re-check against the new floor's position). Effort: low (follows existing validator design). Value: medium.

10. **Add a "level/floating element" model check** *(finding 2.1)*. Round 1 already proposed cheap checks; the level-specific one is "element floating above its level" — exactly computable once floors have elevations: an element's base must equal its floor's `elevation` (within tolerance). Their own landing page advertises a model check for "empty levels", which suggests they see this as a product surface too. Effort: low. Value: medium.

### Anti-patterns worth avoiding (learned from the competitor)

- **Do not store the level as a derived Y-position for movable elements.** `levelOf` recomputes `wall/object/door/window` levels from `y`, so a mesh nudged vertically silently changes floors. CasaPlazAI should keep an explicit `floorId` on every entity.
- **Do not let "add level" be indistinguishable from "go to level".** Their `+` creates nothing; users who expect "add storey" get an empty level with no floor slab and no hint.
- **Do not hide the level being edited.** Their cutaway does, with no banner, no dimming of the rest, and no camera move.
- **Do not use the top index.** `setLevel(50)` is advertised by the badge ("50 floors") yet its contents are permanently invisible.
- **Do not leave two divergent pick predicates.** `isEnabled()`-only versus `isPickable && isEnabled()` versus `+ isVisible` means hidden geometry is sometimes clickable and sometimes not.

## 4. Unknowns

1. **The Duplicate dialog copy was exercised, but the exact failure paths were not.** I saw counts, Add/Replace, the success toast and the level switch; I did not force a partial failure (e.g. an opening whose host wall failed to rebuild) to read the `copy.fail` toast or the `failed` count's UI.
2. **The `copy.level.*` strings were read from the shipped i18n map and the live DOM, not from vendor docs.** No vendor help page describing *Duplicate level* was found; the closest is the landing page's "50 floors per project" claim (`DOCUMENTED`).
3. **Level 50's invisibility is inferred from the predicate plus two measured walls (49 visible, 50 not);** I did not exhaustively test every slider value at the top end, nor whether some other code path re-enables level 50.
4. **I did not test whether a hidden mesh can be *selected by the editor's own click path*.** I proved the underlying picking behaviour and predicate inconsistency in the exported API; the exact tool-by-tool click handlers were not each exercised with a synthetic pointer.
5. **`HPBIM.setLevelName`'s editor UI was not located.** I called the API directly; whether the BIM panel exposes a rename field (i18n keys `bim.levelName`, and a `renamelevel` action exists in the BIM tree code) was not walked through.
